# Debug & Tool Error Handling Rules

## User Query Pattern: Tool Errors

当用户报告工具调用错误时，必须遵循以下流程：

### 步骤 1：获取完整错误信息
- **如果用户没有粘贴完整的错误信息**，必须立即要求用户提供完整内容。严禁在缺少关键信息的情况下做出诊断。
- **如果用户只说了"报以下错"等模糊描述**，要追问具体错误内容、复现步骤和环境信息。

### 步骤 2：结构化诊断（按顺序执行）
1. **读取完整错误** — 提取错误码、错误消息、堆栈跟踪
2. **定位根因** — 分析错误属于哪类问题：
   - 参数错误（Invalid params）：检查必填参数是否缺失、类型是否正确
   - 工具未找到（Unknown tool）：检查工具名称拼写、工具是否已注册
   - 权限/策略错误（Governance denied）：检查沙箱白名单、预算、RBAC 权限
   - 超时错误（Timeout）：检查超时配置、工具执行时间
   - 内部错误（Internal error）：检查服务端日志、工具实现代码
3. **提供修复方案** — 针对根因给出具体可操作的建议

### 步骤 3：输出格式
诊断回复必须包含：
- **问题摘要**：一句话描述错误的性质
- **根因分析**：指出具体原因（文件位置、配置项等）
- **解决方案**：分步骤说明如何修复
- **预防措施**：如何避免同类问题再次发生

### 示例

用户：`工具报错说 Invalid params`

AI 应该回复：
```
## 问题分析

Invalid params 表示调用工具时传入了无效参数。

### 常见的根因
1. **必填参数缺失** — 检查工具 input_schema 中的 required 字段
2. **参数类型错误** — 如传了 string 但期待 number
3. **参数格式错误** — 如 JSON 格式不正确

### 需要排查
请粘贴完整的错误信息，包括：
- 调用的工具名称
- 传入的完整参数 JSON
- 错误码和错误消息全文

这样我可以精确定位问题。
```

## 通用原则

- **信息不完整绝不猜** — 没看到错误全文，不给出确定性诊断
- **永远优先追问** — 缺少上下文时，先问清楚再说
- **诊断要具体** — 给出文件路径、配置项、代码行的精确引用
- **不要复读用户输入** — 用户说"报错"，不要只回"报错"，要分析
