# 高級編排

`go-on` 運行時包含一套高級編排模組，用於管理複雜的工作流執行、恢復和診斷。這些元件負責依賴感知排程、容錯恢復、會話上下文管理和彈性故障處理。

---

## 1. DAG 執行引擎

DAG（有向無環圖）執行引擎負責排程和執行具有明確依賴關係的任務。任務被組織為一個圖，其中邊表示資料或控制依賴關係。

### 拓撲執行

引擎在執行前計算 DAG 中所有節點的拓撲順序。沒有依賴關係的節點（根節點）首先被排程，只有當所有前驅節點成功完成後，節點才會被分發執行。

### 依賴管理

每個任務將其依賴關係宣告為一組上游任務 ID。引擎驗證：

- 所有引用的依賴項都存在於 DAG 中。
- 不存在循環依賴（請參閱下面的循環檢測）。
- 依賴項所需的輸出與下游任務的宣告輸入類型匹配。

### 並行組

處於同一拓撲級別的任務（即所有依賴項都已滿足且彼此不依賴的任務）被分組為並行執行批次。引擎並發分發批次中的所有任務，受可配置的並發限制約束。

### 循環檢測

在開始執行之前，引擎使用深度優先搜索（DFS）和遞迴堆疊進行完整的循環檢測。如果檢測到循環，整個 DAG 執行將被中止，並給出一個明確識別衝突邊的錯誤。

## 2. 恢復編排器

恢復編排器（`src/fault_tolerance/`）處理節點級故障，並根據偵測到的故障類型和嚴重度確定最佳恢復動作。它是一個面向叢集健康狀態的引擎：節點註冊心跳，故障記錄為 `FaultEvent`，`FaultToleranceEngine` 將其轉化為可執行的恢復計劃。

### 恢復動作

`RecoveryAction` 恰好有五個變體：

| 動作            | 描述 |
|-------------------|-------------|
| **RestartNode**       | 重新啟動故障節點：心跳記錄恢復為 `Online`，未命中計數清零。 |
| **FailoverToBackup**  | 將流量切換到新領導下的備份節點。 |
| **ScaleUp**           | 記錄擴容動作，用於容量類故障（hang、資源耗盡、限流、延遲尖峰）。 |
| **Rebalance**         | 重新平衡節點，解決損壞類故障。 |
| **NotifyOperator**    | 通知操作員關注；用於無法自動解決的故障（I/O 錯誤、鑑權失敗、部分寫入），嚴重度 ≥ 9 時總是追加。 |

### 故障類型映射

`create_recovery_plan()` 根據節點的活躍 `FaultType` 推導動作集（按故障類別去重）：

| FaultType                                   | RecoveryAction          |
|---------------------------------------------|-------------------------|
| `Crash`、`Oom`、`ProcessCrash`              | `RestartNode`           |
| `Hang`、`ResourceExhaustion`                | `ScaleUp`               |
| `NetworkSplit`、`NetworkTimeout`、`NetworkPartition` | `FailoverToBackup` |
| `RateLimit`、`LatencySpike`                 | `ScaleUp`               |
| `DataCorruption`                            | `Rebalance`             |
| `FileIOError`、`AuthFailure`、`PartialWrite`| `NotifyOperator`        |

高嚴重度故障（`severity >= 9`）總是追加 `NotifyOperator`；沒有具體動作映射的節點預設 `NotifyOperator`。

### 計劃生命週期

編排器透過 `execute_recovery_plan()` 分發每個計劃，執行每個動作的可觀察程序內效果（狀態重置、隔離群組變更、故障解決、操作員通知），然後執行恢復後一致性檢查。只有檢查通過，計劃才會 complete 或 fail——自動恢復要麼真正解決故障，要麼如實報告殘留狀態。

## 3. 會話上下文管理器

會話上下文管理器在多輪互動中維護和優化對話上下文，確保在有限的視窗預算內保留最相關的資訊。

### 概念提取

每條使用者訊息都會被分析以提取關鍵概念——實體、意圖和領域特定術語。提取的概念儲存在與會話關聯的輕量級記憶體索引中。

概念如果不被後續訊息強化，則會隨時間衰減。權重低於可配置閾值的概念會被從會話中修剪。

### 訊息重要性評分

會話歷史中的每條訊息在多個維度上評分：

- **時效性**：較新的訊息獲得較高的分數。
- **相關性**：包含目前查詢中出現過的概念的訊息得分更高。
- **角色**：系統訊息和明確的使用者指令比隨意對話得分更高。
- **可操作性**：觸發了工具呼叫或產生了可觀察副作用的訊息得分更高。

### 連續性標記

連續性標記是注入到上下文視窗中的特殊註釋，用於指示敘述的進展。它們透過總結已完成的工作和剩餘的工作幫助模型在回合之間保持連貫性。標記在關鍵里程碑處自動生成：

- `workflow.execute` / `task.execute` 工作流運行完成後。
- 恢復動作解決故障後。

### 視窗預算

上下文視窗是有限的。會話上下文管理器通過以下方式強制執行預算：

1. 始終保留最近的 `n` 條訊息（可配置，預設：5）。
2. 用得分最高的較舊訊息填充剩餘預算。
3. 當預算超限時，剝離低重要性的訊息。
4. 必要時通過總結來壓縮長訊息。
