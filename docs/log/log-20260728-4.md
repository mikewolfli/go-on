## 二、重复冗余功能排查 (多轮仔细核对)

### 🔴 2.1 `find_files` / `find_path` / `search_files` 三角冗余

**现象**: 
- `search.rs` 第137行声明: `"FindFilesTool has been merged into SearchFilesTool"`
- 但 `tool_descriptors.rs` 中 `find_files` 和 `find_path` 都有独立 descriptor
- `pipeline.rs` 中 `find_files` 和 `find_path` 都在"search"类别下 (第157行)
- 三个工具功能高度重叠: 都是搜索文件路径

**影响**: 重复入口增加AI混淆概率，增加维护负担

**建议**: 
- `find_path` 应直接变为 `search_files` 的别名 (通过 `register_alias`)
- 或者统一为 `find_path` 一个入口，删除 `find_files` 别名层
- 保留 `search_files` 作为主要搜索接口，`find_files` → alias → `search_files`

### 🔴 2.2 `file_move` / `move_path` 别名冗余

**现象**:
- `filesystem.rs` 中 `FileMoveTool::name()` 返回 `"move_path"` (第93行)
- 但同时 `tool_descriptors.rs` 第293行: `"move_path" | "file_move"` 作为别名
- 代码只在 `FileMoveTool` 中实现一次，但暴露两个名字

**影响**: 轻微冗余，但对外暴露两个名字增加AI决策复杂度

**建议**: 统一使用 `move_path`，将 `file_move` 作为别名保留在Registry中，但不在工具列表中显式暴露

### 🔴 2.3 `file_delete` / `delete_path` 别名冗余

**现象**: 与2.2同理，`FileDeleteTool::name()` 返回 `"delete_path"`，但同时有 `file_delete` 别名

**建议**: 与2.2统一处理

### 🟡 2.4 `pipeline.rs` 与 `executor.rs` 职责重叠

**现象**:
- `pipeline.rs`: 提供 `ToolPipeline` 顺序执行+沙箱检查流程(共400行)
- `executor.rs`: 提供 `execute_tools_concurrent` 并发执行+governance检查(共550行)
- 两者都做: tool查找、governance检查、结果聚合
- 但执行模型不同 (顺序vs并发)

**影响**: 代码重复 ~30% (common logic: tool lookup, sandbox check, error handling)

**建议**: 抽取公共执行基座:
- 将 `run_single_tool` (pipeline.rs第322行) 和 `execute_single_tool` (executor.rs第165行) 合并
- 将沙箱检查 `check_tool_in_pipeline` 下沉到 `ToolRegistry` 级别
- 让 pipeline 和 executor 共享同一套执行+沙箱+验证逻辑

### 🟡 2.5 `brain_loop` 与 `full_auto` 的 skill 发现逻辑重叠

**现象**:
- `full_auto/executor.rs`: 包含 `discover_skills` (第54行) + `skill_match_recursive`
- `brain_loop/mod.rs`: 包含 `execute_step` + `reflect` + `replan` 循环
- 两者都有 skill → 匹配 → 评估 的流程

**影响**: `brain_loop` 和 `full_auto` 在 skill matching 层面没有代码复用

**建议**: 将 skill matching 逻辑抽取为共享组件，`full_auto::discover_skills` 和 `brain_loop` 都调用

### 🟢 2.6 `lock_utils.rs` vs `tool/lock.rs` — 不同目的，无需合并

- `lock_utils.rs`: Mutex/RwLock poison recovery macro (辅助宏)
- `tool/lock.rs`: 文件路径级别的 ToolLockManager (文件并发锁)
- 两者目的完全不同，无需合并 ✅

## 三、执行效率优化分析

### 🔴 3.1 `shell_exec` 工具 — 代码重复与低效 (高优先级)

**位置**: `src/orchestration/tool/extended/shell.rs`

**问题**:
1. **GNU timeout vs Rust timeout 代码高度重复** (第96-251行):
   - Command 构建逻辑在两路径中几乎完全重复
   - stdin 处理在两处重复
   - 环境变量设置在两处重复
2. **字符级别的 truncation** (第269-280行):
   - `for ch in stdout.chars().take(MAX_OUTPUT_BYTES)` — 效率极低
   - 应直接 `stdout.truncate(MAX_OUTPUT_BYTES)` (对于纯 ASCII/most UTF-8 足够)
3. **阻塞命令的响应速度**: 
   - 使用 `std::thread::spawn` 做kill线程 (第187-207行)
   - 这本身没问题，但如果在高并发下大量调用，线程开销可观

**建议**:
- 抽取 `build_command()` 公共函数，统一两种 timeout 模式的命令构建
- 输出截断改成 `stdout.truncate(MAX_OUTPUT_BYTES)` 提升10x+速度
- 考虑使用 `tokio::process::Command` 重写异步实现，避免 spawn_blocking

### 🟡 3.2 `web_search` 工具 — 专用Runtime的开销

**位置**: `src/orchestration/tool/extended/web_search.rs`

**问题**:
- 独立 `OnceLock<tokio::runtime::Runtime>` (第16-25行)
- `run()` 方法使用独立 runtime 的 `block_on` (第81行)
- 每次调用创建 `WebSearchClient` (第153行)

**建议**:
- 缓存 `WebSearchClient` 实例，避免每次重新创建
- 或者完全依赖 `run_async` 路径，让调用方负责任务调度

### 🟡 3.3 `executor.rs` 的 circuit breaker — 过于激进

**位置**: `src/orchestration/tool/executor.rs` 第142-147行

**问题**:
- 条件: `failure_count >= circuit_breaker_limit && total_success == 0`
- 当 `total_success == 0` 时，一个失败就会触发熔断
- 默认配置下 `circuit_breaker_limit = 3` 但 `total_success == 0` 条件过于严格

**建议**: 将条件改为 `failure_count >= circuit_breaker_limit`，移除 `total_success == 0` 限制

### 🟢 3.4 `ToolPipeline` 限流策略 — 256上限合理

`pipeline.rs` 第298行: 256 tool call 上限合理，无需改动 ✅

### 🟢 3.5 `execute_tools_concurrent` 信号量机制正确

使用 `tokio::sync::Semaphore` 控制并发度 (executor.rs 第96行)，设计合理 ✅

## 五、串行流程优化建议

### 🔴 5.1 `shell.rs` 中 GNU timeout 探测流程可加速

**现状**: 第110-121行，每次调用 `ShellExecTool` 都检测 `timeout` 命令是否存在:
```rust
let use_gnu_timeout = Command::new("timeout").arg("1")...output().map(|out| out.status.success()).unwrap_or(false);
```

**优化建议**: 使用 `OnceLock<bool>` 只检测一次，缓存结果

### 🟡 5.2 Executor 中 governance 检查串行化

**现状**: 每个 tool call 都走 governance pre-execute 检查 (executor.rs 第460+行)

**优化建议**: 对于低风险工具 (read_file, search_files 等)，实现 governance fast-path bypass，跳过不必要的编辑模式检查

### 🟡 5.3 Pipeline 的 step 可并行化

**现状**: `ToolPipeline::execute` 顺序执行所有 step

**优化建议**: 增加 `parallel_steps: Vec<Vec<PipelineStep>>` 配置，允许将无依赖的 step 并行执行

## 十、结论

本项目整体架构优良，工具系统和技能系统完备，涵盖了从基础文件操作到 CAD/3D/游戏/网络/文档的全方位能力。核心发现:

1. **没有重大阻塞性问题** — 工具/技能链路线完整流畅
2. **冗余集中在命名别名和执行逻辑** — 4处可合并的冗余，但都不影响功能
3. **执行效率优化空间主要在 shell.rs** — 串行timeout探测和代码重复
4. **测试覆盖充足但扩展工具不足** — 核心系统有完善测试，但56个扩展工具大部分只有编译检查
5. **安全性多层覆盖** — Sandbox + Guardian + RBAC + 编辑模式检查，无 block_on 违规
6. **Zed 模式已在 go-on 中实现** — LSP、诊断、格式化、搜索、Git 核心功能均已实现

**总体评估**: 项目已处于较高成熟度，建议优先解决上述高优先级行动项 #1-#3，其余为中低优先级优化。
