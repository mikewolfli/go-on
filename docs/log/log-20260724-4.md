### P2-2: CompactionManager + AdaptiveCompactor 自适应压缩（BLUE71 §10）

**文件**: `src/optimization/compaction.rs`（新建，~450行）

**实现组件**:

| 组件 | 行数 | 说明 |

| `CompactionManager` | 100行 | 基础压缩引擎（sync compact） |
| `AdaptiveThreshold` | 40行 | 动态阈值：高质量→提高（压缩更少），低质量→降低 |
| `AdaptiveCompactor` | 110行 | 自适应学习型压缩器 |
| **测试** | **100行** | **28个测试** |

**CompactionManager 策略对比**:

| 策略 | 压缩方式 | 质量评分 | 适用场景 |
|------|---------|---------|---------|
| SlidingWindow | 移除最旧轮次 | 0.95（几乎无损） | 短对话、快速模式 |
| Summarize | LLM摘要 > 系统消息 | 0.70（有损） | 长对话、高质量需求 |
| Hybrid | 摘要旧轮次+保留新轮次 | 0.80（平衡） | 默认策略 |

**AdaptiveCompactor 学习机制**:

```text
conversation length < 20  → SlidingWindow (快速低成本)
avg quality < 0.6         → Summarize (提升质量)
default                   → Hybrid (平衡)
```

**自适应阈值调整**:
- 平均质量 > 0.9 → 提高阈值（少压缩）
- 平均质量 < 0.6 → 降低阈值（多压缩）
- 用户反馈融合: quality * 0.6 + feedback * 0.4

**测试覆盖**: 28个测试

|---------|------|---------|

| AdaptiveCompactor | 8 | 跳过/策略选择/历史记录/用户反馈/摘要/容量限制/时间戳 |

## 11. 本轮冗余清理

### P0-8: agent_main_loop break → 持久循环

**文件**: `src/agents/communication/agent_thread.rs:364,395`

**问题**: `UserMessage` 和 `ChatRequest` handler 在每条消息后执行 `break;`，
导致 AgentThread 只能处理一条消息就退出。这使得 SessionActor 必须为每条
用户消息创建新的 AgentThread，浪费资源。

**修复**: 移除两个 handler 中的 `break;`（以及对应的 `Completed` 状态设置），
使 AgentThread 成为真正的持久循环。仅通过 `Cancel` 或 channel close 退出。

### P0-9: SessionActor 重用 AgentThread

**文件**: `src/agents/session.rs`

**问题**: `session_main_loop` 为每条 `UserMessage` 调用 `spawn_agent_non_blocking()`
创建新 AgentThread，然后立即等待完成。这完全浪费了 AgentThread 的持久循环能力。

**修复**: 
1. `session_main_loop` 启动时创建**一个** AgentThread 并存储在局部变量
2. 每次 `UserMessage` 通过 `thread.send_input(ChatRequest{...})` 发送到已有线程
3. 通过 `reply_to: oneshot::channel` 收集响应
4. `Cancel` 时发送 `AgentInput::Cancel` 给线程
5. `state.root_agent` 使用完后通过 `.take()` 释放（避免无用字段）

**性能改进**: 从 O(n) 次线程创建 降为 O(1) 次
