## 3. 串行瓶颈 → 可并行化改造

### 3.1 🔴 `PolicyEvaluator::evaluate()` — 7个连续锁 

**文件**: `src/governance/harness_bus/evaluator.rs` L214-487

串行获取7个锁, 每一步等待前一步释放:

```
Step 0:  self.policies.read()                          (RwLock读)
Step P1: reloader.lock() + self.policies.write()       (Mutex→RwLock写)
Step 1:  self.rule_engine.lock()                       (Mutex)
Step 2:  self.budget.lock()                            (Mutex)
Step 3:  self.runtime_control.lock()                   (Mutex)
Step 4:  self.guard.lock()                             (Mutex)
Step 5:  self.security_governor.evaluate()              (内部Mutex)
```

步骤1-5之间**没有数据依赖** — 红线检查、预算检查、运行时控制、理性化守卫和安全治理评估都是相互独立的。

**改造**: 使用 `tokio::join!` 或 `futures::join_all` 将独立检查并行执行。

### 3.2 🔴 `check_tool_call()` — 4个连续锁

**文件**: `src/governance/harness_bus/evaluator.rs` L540-748

```
Step 1: self.sandbox_level.lock()    (Mutex)
Step 2: self.idempotency.lock()      (Mutex)
Step 3: self.budget.lock()           (Mutex)
Step 4: self.rbac_enforcer.read()    (RwLock)
```

沙箱级别、幂等性、预算、RBAC都是独立读取。

**改造**: 可并行获取。

### 3.3 🔴 `HarnessBus::audit()` — 三写入串行

**文件**: `src/governance/harness_bus/mod.rs` L450-518

每次审计调用都串行写入:
1. `self.audit_log.record(...)` — NDJSON
2. `self.audit_trail.lock().entries.push(...)` — 内存Vec + HashChain
3. `self.structured_audit_trail.lock().append_entry(...)` — 结构化审计

**改造**: 使用 `mpsc` channel 将审计写入异步化, 批次写入。

### 3.4 🟠 `PolicyEvaluator::process_timeouts()` — 串行等待

**文件**: `src/governance/approval_engine.rs` L726-753

```rust
let handles = ...; // spawn_blocking for each row
for handle in handles { let _ = handle.await; } // 串行等待!
```

注释说 "Fire feedback concurrently" 但代码是串行 await 每个 handle。

**改造**: 使用 `futures::future::join_all(handles)` 并行等待。

### 3.5 🟠 全局 `HotFailover` Mutex — 所有请求串行

**文件**: `src/intelligence/hot_failover.rs` L256-257

```rust
pub static HOT_FAILOVER_INSTANCE: LazyLock<Mutex<HotFailover>> = LazyLock::new(...);
```

所有通过 `execute_with_failover()` 的下游模型请求序列化在此全局互斥锁上。如果100个请求同时触及故障切换, 它们全部串行执行。

**改造**: 使用 `DashMap` 而非单个 `Mutex`; 或者使用shard锁。

### 3.6 🟠 全局 `TripleFusionBridge` Mutex — 所有融合串行

**文件**: `src/intelligence/triple_fusion.rs` L49-60

```rust
static GLOBAL_TRIPLE_FUSION: OnceLock<Arc<Mutex<TripleFusionBridge>>> = OnceLock::new();
```

所有请求的融合周期序列化在同一个Mutex上。

**改造**: 使用 `RwLock` (读多写少) 或 channel 模式。

### 3.7 🟠 `CapabilityBus::sense()` — 4个连续锁

**文件**: `src/intelligence/capability_bus/sense.rs` L40-138

```
Line 43: lock_guard(&self.capability_graph)           // 锁1
Line 46: read_guard(&self.unified_knowledge_bus)       // 锁2 (持有锁1)
Line 61: read_guard(&self.learning_optimization_bus)   // 锁3
Line 119: lock_guard(&self.transport)                  // 锁4
```

**改造**: 如果这些总线访问不共享状态, 可以并行获取。

### 3.8 🟠 `feedback.rs` 锁7+存储 — 串行写入

**文件**: `src/intelligence/capability_bus/feedback.rs` L38-184

单次 `feedback()` 调用串行写入: LearningOptimizationBus, UnifiedKnowledgeBus, ReinforcementBus, ObservabilityBus, OptimizationBus, ProtocolBus, MemoryBus, DistributedMemoryBus, ProvenanceLedger, SelfModel。每个写入都获取锁。

**改造**: 使用异步channel将反馈发送到后台写入器。

### 3.9 🟠 `continuous_learning.rs` 后台运行时单线程

**文件**: `src/intelligence/continuous_learning.rs` L506-515

`shared_background_runtime()` 创建**单个** `tokio::runtime::Runtime` 给 `llm_distill`。所有异步LLM调用在此单线程上串行。

**改造**: 使用 `tokio::spawn` 在本运行时上, 而非创建独立的单线程运行时。

### 3.10 🟠 `orchestrator::execute_tool_pipeline` 全串行

`tool/executor.rs` L83-155 中存在 `execute_tools_concurrent()` 函数(并行执行工具), 但它是 `pub(crate)` — 未接入 orchestrator 的公共API。

**改造**: 将 `execute_tools_concurrent` 提升为公共API, 并在适当时使用。

### 3.11 🟠 `planner_executor/execution.rs` — 不执行并行步骤

`ExecutionPlan` 有 `parallel_groups` 字段, 但 `Executor::execute_with_cancel` 按声明顺序逐步骤遍历。

**改造**: 解析 `parallel_groups`, 使用 `tokio::join!` 或 `JoinSet` 并行执行独立步骤。

## 5. 非必要锁与同步开销

### 5.1 🔴 `std::sync::Mutex` 在 `await` 点之前保持

多个地方使用 `std::sync::Mutex` 执行可能阻塞的操作:

| 文件 | 行 | 操作 | 问题 |
|------|-----|------|------|
| `harness_bus/audit.rs` | L33-51 | `hash_chain.lock()` → `serde_json::json!` + file I/O | 阻塞tokio工作线程 |
| `governance/audit.rs` | L72-204 | `ThreadSafeAuditLog` 所有方法使用 `std::sync::Mutex` + `append_ndjson_entry` | 每次评估都阻塞 |
| `governance/security_governor.rs` | L601-604 | `self.inner.lock()` 在评估热路径中 | 阻塞tokio工作线程 |

**改造**: 使用 `tokio::sync::Mutex` 或 `mpsc` channel + 专用写入器任务。

### 5.2 🟠 `RbacEnforcer` 双Arc锁

**文件**: `harness_bus/evaluator.rs` L876-881

```rust
let shared_arc = self.rbac_enforcer.read().ok().and_then(|guard| guard.clone());
let inner_guard = shared_arc.as_ref().and_then(|arc| arc.read().ok());
```

`RbacEnforcer` 存储于 `Arc<RwLock<Option<Arc<RwLock<RbacEnforcer>>>>>` — 双重 `RwLock`。每次工具调用增加原子计数开销。

**改造**: 使用 `RwLock<Option<RbacEnforcer>>` 直接。

### 5.3 🟠 `RoleRegistry` 过度加锁

**文件**: `orchestration/roles.rs` L56

## 8. 效率优化建议

### 8.1 审计写入异步化

**问题**: 每次 `HarnessBus::audit()` 同步写入3个审计目标(NDJSON + 内存Vec + hash-chain + 结构化审计), 每个都持锁。

**方案**: 使用 `tokio::sync::mpsc` channel 将审计消息发送到后台专用写入任务。写入任务批次提交, 减少I/O次数。

### 8.2 数据库连接池

**问题**: `memory/cache.rs`, `memory/memory_persistence.rs`, `memory/vector.rs` 都使用 `Mutex<Connection>` 或者 `Mutex<Client>` 来序列化数据库访问。

**方案**: 使用连接池 (`r2d2` for SQLite, `deadpool-postgres` for PostgreSQL), 允许并发数据库访问。

### 8.3 联邦学习发现串行化

**文件**: `intelligence/reinforcement/federated_discovery.rs`

当前单线程发现其他联邦节点。可并行化发现扫描。

### 8.4 计划执行并行组

**文件**: `orchestration/planner_executor/execution.rs`

`ExecutionPlan` 有 `parallel_groups` 字段标记独立步骤组, 但 `Executor` 不利用此信息。解析并使用 `JoinSet` 并行执行。

### 8.5 能力总线感觉方法锁链

**文件**: `intelligence/capability_bus/sense.rs`

4锁顺序获取, 可改为并行或更细粒度。

### 8.6 全局静态Mutex替换

| 位置 | 当前 | 改进 |
|------|------|------|
| `HOT_FAILOVER_INSTANCE` | `LazyLock<Mutex<HotFailover>>` | `RwLock` 或 `DashMap` 分片 |
| `GLOBAL_TRIPLE_FUSION` | `OnceLock<Arc<Mutex<...>>>` | `RwLock` 或 channel |
| `CURRENT_TRANSPORT` | `RwLock<Option<Arc<dyn Transport>>>` | 可接受, 但加速用 `AtomicPtr` |

### 8.7 通过缓存减少I/O

- `gov/pua.rs` `append_learning_record` 每次同步文件I/O → 批量写入
- `gov/audit.rs` NDJSON 每次写入 → 批次+定时刷新

### 8.8 CLI 加速

**文件**: `src/cli/chat.rs` L2733-2737

当前实现已避免 `block_on`。但可进一步减少 `serde_json` 序列化开销, 例如预编译正则。

### 8.9 技能感知模块发现

当前3套技能管理系统各自独立扫描和缓存。统一后可减少启动时间和内存占用。

### 8.10 `tokio::fs` 替代 `std::fs`

所有在异步上下文中使用 `std::fs` 的地方应改为 `tokio::fs` 或 `spawn_blocking`。
