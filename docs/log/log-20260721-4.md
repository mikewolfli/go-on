## 2. ZED Agent Server 集成深度改进

### 2.1 session/prompt 无 StreamObserver (P0)

**文件**: `src/acp/impl/request/protocol_pack/session.rs:162`

**现状**: `process_chat_request(server, &mut chat_params, **None**, &pipeline_trace, None, None)` — `stream_observer` 传入 `None`,导致 ChatPipeline 产生的所有流式事件(emit_stream_chunk、emit_stream_done、emit_phase_event、emit_tool_approval_event)全部被静默丢弃。

**后果**: ZED 等待 300 秒后才看到完整响应,而真正的模型 token 被丢弃,改用后置正则 `<thinking>...</thinking>` 对完整响应文本低质量切块。

**修复**: 创建 StreamObserver,通过 session/update 通知实时转发 token 级事件。

### 2.2 实施: session/prompt 实时流式

**修改文件**: `src/acp/impl/request/protocol_pack/session.rs`

在 `session_prompt_payload` 函数内部:
1. 创建 `mpsc::unbounded_channel::<StreamFrame>()`
2. 构建 `StreamObserver::sse(tx)` 替代 `None`
3. 将 `process_chat_request` 调用改为传入 `Some(observer)`
4. 启动异步任务从 `rx` 接收 `StreamFrame` 并转发为 `session/update` 通知

```rust
use crate::acp::r#impl::chat::streaming::{StreamFrame, StreamObserver};

// ... after building chat_params ...
let (tx, mut rx) = tokio::sync::mpsc::unbounded_channel::<StreamFrame>();
let observer = StreamObserver::sse(tx);

let sid_for_event = session_id_for_notification.clone();
let server_clone = ...; // 注意: &AcpServer 不是 Send,需特殊处理
// 方案: 通过 server 的 Arc 指针转发
let server_arc = /* 从某个 Arc<AcpServer> 获取 */;

// 在 timeout 之前启动转发任务
let fwd_handle = tokio::spawn(async move {
    while let Some(frame) = rx.recv().await {
        if let Some(ref sid) = sid_for_event {
            match frame.event {
                "chunk" => {
                    let token = frame.payload["token"].as_str().unwrap_or("");
                    send_chunk(&server_arc, sid, "agent_message_chunk", token).await;
                }
                "done" => {
                    let response = frame.payload["response"].as_str().unwrap_or("");
                    if !response.is_empty() {
                        send_chunk(&server_arc, sid, "agent_message_chunk", response).await;
                    }
                }
                "phase_start" | "phase_end" => {
                    // 可选: 转发进度指示
                }
                _ => {}
            }
        }
    }
});
```

**问题**: `session_prompt_payload` 的签名是 `pub async fn session_prompt_payload(server: &AcpServer, params: Value)`,无法在 `tokio::spawn` 中捕获 `&AcpServer`。

**根本解决方案**: 将 `server` 改为 `Arc<AcpServer>` 或通过 `server_arc` 克隆。但 `session_prompt_payload` 是 MethodHandler trait 签名的一部分(`fn handle(&self, server: &AcpServer, ...)`),无法直接修改。

**实际可行方案**: 在 `send_chunk` 之前构造好所有需要的 server 状态快照,或将转发逻辑改为同步并在主协程中处理 frame:

```rust
let result = tokio::time::timeout(
    std::time::Duration::from_secs(300),
    process_chat_request(server, &mut chat_params, Some(observer), &pipeline_trace, None, None),
).await;

// 在主协程中 drain rx
drop(tx); // 确保发送端已关闭
let mut last_end = 0;
let mut response_text = String::new();
while let Ok(Some(frame)) = rx.try_recv() {
    if frame.event == "chunk" {
        if let Some(token) = frame.payload["token"].as_str() {
            response_text.push_str(token);
        }
    }
}
// 然后用 session_id_for_notification 发送 session/update 通知
```

**但这是否解决了问题?** 部分。StreamObserver 使 ChatPipeline 能够发射 phase/tool_approval/telemetry 事件(虽然当前在转发任务中被忽略了),但 token 级流式仍然需要通过 `session/update` 通知发送出去。

**实际情况**: ZED 在 ACP stdio 模式下,`session/prompt` 的返回是 JSON-RPC response(非流式),`session/update` 通知才是流式通道。ZED 的 ACP 客户端监听 `session/update` notification 来获取渐进式内容。但 ZED 是否真正支持 `chunk` 级的 session/update?——这取决于 ZED 侧的 ACP 客户端实现。

**关键发现**: ZED 的 ACP 客户端预期 `session/update` 携带 `agent_message_chunk`/`agent_thought_chunk` 类型的结构化内容块,而非细粒度的 token。ZED 原生的 Chat 使用自己的 SSE 端点(`/v1/chat/completions`),所以当 go-on 作为 Agent Server(ZED 通过 ACP stdio 通信)时,ZED 的 UI 依赖的是 `agent_message_chunk` 通知,而不是逐 token 更新。

**结论**: 当前的 regex 后置切块方案在 **ZED ACP 客户端** 下已经是合理的折中。问题不在于方案本身,而在于:
1. **300 秒无任何反馈** — 应添加 phase_start/status 事件(show progress)在 pipeline 运行时提前发送
2. **正则表达式失败率** — `<thinking>` 标签格式依赖模型行为,应同时支持 `__thinking__` 前缀标记

## 4. CLI Chat Loop 改进

### 4.1 stdin 阻塞导致 Ctrl+C 无法中断输入 (P0)

**文件**: `go-on/src/cli/chat.rs:416-432`

**现状**: stdin 读取在 `spawn_blocking` 中执行 `stdin.read_line()`。主循环在 `read_user_input` 中 `rx.recv()` 阻塞,在此期间 Ctrl+C 不会被处理。

**修复**: 使用 `tokio::io::stdin()` 的异步读取替代 `spawn_blocking`:

```rust
let mut lines = tokio::io::BufReader::new(tokio::io::stdin()).lines();

// 在主循环中:
tokio::select! {
    line = lines.next_line() => {
        match line {
            Ok(Some(line)) => { /* 处理行 */ }
            _ => break,
        }
    }
    _ = signal::ctrl_c() => {
        eprintln!("\nInterrupted");
        break;
    }
}
```

### 4.2 Ctrl+C 一次性处理问题 (P1)

**文件**: `go-on/src/cli/chat.rs:1757-1810` 和 `1802-1808`

**现状**: `signal::ctrl_c()` 是一次性 future。第一次 Ctrl+C 消耗后,后续 Ctrl+C 在同一个 `tokio::select!` 中不会再触发。

**修复**: 使用 `tokio::signal::ctrl_c()` 的重复监听模式:

```rust
// 使用 loop + break 或 restore 模式
loop {
    tokio::select! {
        token = rx.recv() => { /* 处理 token */ }
        _ = signal::ctrl_c() => {
            if already_interrupted {
                // 第二次 Ctrl+C 时强制退出
                return Err(anyhow::anyhow!("Interrupted by user"));
            }
            already_interrupted = true;
            chat_task.abort();
            // 继续,让 stream 正常结束
        }
    }
}
```

**文件**: `go-on/src/cli/chat.rs:364-375`

### 6.3 实施: 验证 CURRENT_TRANSPORT 使用

**修复**: 在 `write_json_line` 函数中接入 `CURRENT_TRANSPORT`:

```rust
// src/acp/impl/io.rs 中的 write_json_line 函数
pub(crate) async fn write_json_line(server: &AcpServer, value: &Value) -> Result<()> {
    if let Some(transport) = get_current_transport() {
        transport.write_json_line(value).await
    } else {
        // fallback to legacy RPC_BUFFER or stdout

    }
}
```
