## 二、🟡 串行瓶颈 — 可并行化的工作流

### 2.1 `chat_phases.rs:observe_phase` — URL 串行预取

**文件**: `src/acp/impl/chat_phases.rs:317-530`

**问题**: 每条消息检测到的 URL 在 `for` 循环中逐个 `await` 获取。n 个 URL 的最坏延迟 = 各 URL 获取时间之和。

```rust
// 当前: 串行 for 循环
for url in detected_urls {
    let result = fetch_url(url).await;
}
```

**影响**: 3 个 URL × 3s 超时 = 9s 最坏阻塞

**建议**: 用 `futures::future::join_all()` 或 `JoinSet` 并行获取，每个 URL 独立超时。

---

### 2.2 `chat_phases.rs:act_phase` — 持久化串行

**文件**: `src/acp/impl/chat_phases.rs:1148-1206`

**问题**: `persist_vector_memory()` 在 `tokio::join!`（并行化另外 3 个持久化操作）**之前**单独运行。向量记忆持久化与其他三个操作无数据依赖。

**建议**: 将 `persist_vector_memory` 移入 `tokio::join!`，使四个持久化操作并发执行。

---

### 2.3 `chat_phases.rs:act_phase` — 串行缓存查询

**文件**: `src/acp/impl/chat_phases.rs:843-913`

**问题**: Token 缓存查询（L843-889）和语义缓存查询（L892-913）串行执行，但都是只读的、无相互依赖。

**建议**: 用 `tokio::join!` 并行查询。

### 2.4 `chat_phases.rs:reflect_phase` — 顺序 fire-and-forget

**文件**: `src/acp/impl/chat_phases.rs:1680-1691`

**问题**: 技能创建和工作流生成两个 fire-and-forget 操作顺序执行，本可以并发。

**建议**: 用 `tokio::join!` 同时启动。

## 三、🟡 全局锁竞争瓶颈

### 3.1 `ACP_SESSION_STATE` — 全局 `tokio::sync::Mutex`

**文件**: `src/acp/impl/request/protocol_pack/mod.rs:126-131`

**问题**: 所有会话操作（new/load/set_mode/set_config/resume/close/list）都获取持有这个**单个全局 Mutex** 跨 `.await` 点。50+ 并发请求时成为明确竞争点。

```rust
static ACP_SESSION_STATE: OnceLock<tokio::sync::Mutex<HashMap<String, AcpSessionState>>>;
```

**建议**: 使用 `RwLock<HashMap<String, ...>>`（读多写少），或 per-session 锁。

### 3.2 `conversation_state` — 全局 Mutex

**文件**: `src/acp/server.rs` conversation_state 字段

**调用点**: `checkpoint_pack.rs:14,38,54,67,134,178`, `config_handlers.rs:15`, `chat.rs:1187`

**问题**: 所有 checkpoint 读/写经过同一 Mutex。checkpoint 读（主导操作）不应相互阻塞。

**建议**: `RwLock` 替代 Mutex，读操作并行化。

### 3.3 `WORKFLOW_RUNS` — 全局 Mutex

**文件**: `src/acp/impl/request/exec_pack/workflow.rs:26-33`

```rust
static WORKFLOW_RUNS: OnceLock<StdMutex<Vec<WorkflowRunRecord>>>;
```

**问题**: 所有会话的所有工作流运行记录在一处。

**建议**: 改为 per-session 记录，或使用 `RwLock`。

### 3.4 GUI `sync_channel` 重试循环

**文件**: `gui/src/views/chat/chat_impl/runtime.rs:46-56`

**问题**: `try_send_with_retry` 在 `mpsc::sync_channel(256)` 满时执行指数退避重试。通道是同步的，UI 线程未 drain 时重试永远失败，导致 CPU 空转。

**建议**: 用 `tokio::sync::mpsc::unbounded_channel` 替换。

## 四、🟡 冗余/重复功能合并

### 4.1 `MemoryResponseCache` vs `SemanticResponseCache` — 可合并

**文件**: `src/memory/memory_response_cache.rs` vs `src/memory/semantic_cache.rs`

| 维度 | `MemoryResponseCache` | `SemanticResponseCache` |
|------|----------------------|------------------------|
| 键匹配 | 精确字符串 | hash 精确 + bigram Jaccard 模糊 |
| 存储 | `Mutex<IndexMap<...>>` | `RwLock<HashMap<u64, Vec<...>>>` |
| 最大 | 2048 | 1000 |

### 4.2 `governance::audit` vs `orchestration::audit` — 可统一

| 维度 | `governance::audit::AuditLogEntry` | `orchestration::audit::AuditEntry` |
|------|-----------------------------------|-----------------------------------|
| 焦点 | 合规日志 (NDJSON 文件旋转) | 决策路径追踪 (回放/证据导出) |
| 额外字段 | data_classification, compliance_tags | `decision_path: Vec<DecisionPoint>` |

**建议**: 提取共享 `AuditRecord` 核心结构体，两个输出后端分别继承。

### 4.3 `lib.rs` / `main.rs` 重复导出

**文件**: `src/lib.rs:39-84` vs `src/main.rs:35-79`

~46 行几乎相同的 `pub use` 语句。每次新增/重命名模块需要同步更新两个文件。

**建议**: 集中导出到 `lib.rs` 的专用模块，`main.rs` 用 `pub use go_on::*;`。

### 4.4 `sub-bus-voter-future` 命名误导

## 五、🟡 性能优化 — 重操作/热路径

### 5.1 `fast_path_cache.rs` — SHA-256 作缓存键

**文件**: `src/orchestration/fast_path_cache.rs:216-228`

**问题**: `fingerprint()` 使用 SHA-256（加密哈希，~300-500 MB/s）计算缓存键。缓存键不需要加密安全性。非加密哈希（AHasher/FxHasher）吞吐量 ~2-3 GB/s，约 **100× 快**。

**建议**: 替换为 `std::hash::Hasher` 或 `fxhash::hash64()`。

### 5.2 `vector.rs` — N+1 命中计数 UPDATE

**文件**: `src/memory/vector.rs:818-829` (SQLite backend), `1968-1978` (PG backend)

**问题**: `search()` 为**每个**结果行发一条 `UPDATE hit_count = hit_count + 1 WHERE memory_key = ?`。N 个结果 = N 次 DB 往返。

```rust
// 当前: N 次单独 UPDATE
for row in &rows {
    conn.execute("UPDATE ... SET hit_count = hit_count + 1 WHERE memory_key = ?1", ...)?;
}
```

**建议**: 批处理为单个 SQL — SQLite 用 `WHERE memory_key IN (...)`，PG 用 `WHERE memory_key = ANY($1)`。

### 5.3 `vector.rs` — `upsert` 3 条串行 SQL

**文件**: `src/memory/vector.rs:604-652`

**问题**: INSERT + SELECT 清理候选 + DELETE 超出限制，3 次锁获取和往返。

**建议**: 合并为 CTE 单条 SQL。

### 5.4 大对象克隆热点

| 文件 | 行 | 模式 | 影响 |
|------|----|------|------|
| `src/acp/helpers/governance/vote_executor.rs` | 91, 259 | `agent_messages.to_vec()` 每次投票闭包 | 5-10 次完整历史拷贝 |
| `src/memory/memory_response_cache.rs` | 33 | `MemoryCachedResponse.clone()` 每次缓存命中 | 大响应文本拷贝 |
| `src/orchestration/fast_path_cache.rs` | 258 | `IntentCacheValue.clone()` 每次缓存命中 | Vec&lt;String&gt; 全部拷贝 |

**建议**: 使用 `Arc<T>` 替代 `T` 的 clone。

### 5.5 LRU O(n) 扫描

**文件**: `src/memory/memory_persistence.rs:183-188`

**问题**: `HotCache::get()` 用 `iter().position()` 做 LRU 提升，O(n) 扫描（最多 2048 条目）+ O(n) `remove(pos)` 移位。

**建议**: 用 `LinkedHashMap`（indexmap）做 O(1) LRU。

### 5.6 `semantic_cache.rs` — Bigram 每次分配

**文件**: `src/memory/semantic_cache.rs:80-101`

**问题**: 每次语义缓存获取为大 Jaccard 相似度计算分配 2 个 `Vec` + 2 个 `HashSet`。缓存未命中时（最多 1000 条目），每个条目都做此分配。

**建议**: 在插入时缓存 bigram 集合到条目中。

### 5.7 `pg_pool.rs` — 每次调用创建 Runtime

**文件**: `src/memory/pg_pool.rs:72-88`

**问题**: `pool_get()` 从 `spawn_blocking` 调用时（response_cache.rs 和 vector.rs 中 12+ 调用点），`try_current()` 返回 None，**每次创建新 Runtime**。

```rust
// 每次从 spawn_blocking 调用创建新 Runtime → ~1-2ms 开销
let rt = tokio::runtime::Builder::new_current_thread()
    .enable_all().build()?;
rt.block_on(pool.get())
```

**建议**: 用 `OnceLock<Runtime>` 缓存共享 fallback Runtime。
