## 一、重复/冗余功能分析

### 1.1 ReviewGateOutcome 三重定义 🔴

**原则违反**：Rule #10 — 不允许占位、空函数、逻辑错误；Rule #4 — 注释英文
**原则依据**：重复类型违背了 Rule #5（全链路闭合）的精神—同一概念应只有一个 source of truth。

| 文件 | 定义 | 字段 |
|------|------|------|
| `governance/review_controls.rs:44` | `enum ReviewGateOutcome` (pub(crate)) | `Approved(Vec<ReviewDecision>)`, `Rejected(...)`, `Degraded(...)` |
| `acp/helpers/governance/review_gate.rs:18` | `struct ReviewGateOutcome` (pub) | `passed: bool`, `comments: Vec<String>` |
| `acp/impl/agent.rs:67` | `struct ReviewGateOutcome` (pub, 被 re-export) | `passed: bool`, `comments: Vec<String>`, `reviewer: String`, `duration_ms: u64` |

**分析**：
- `acp/helpers/governance/review_gate.rs` 的 `ReviewGateOutcome` 是 `acp/impl/agent.rs` 的子集（少了 reviewer 和 duration_ms），且该文件仅作为薄包装调用 `run_dual_review_gate()`。
- `governance/review_controls.rs` 的 `ReviewGateOutcome` 使用 enum 风格（Approved/Rejected/Degraded），语义不同。
- `acp/impl/agent.rs` 的 `ReviewGateOutcome` 被 re-export 到 `acp::prelude`，是主要的公共类型。

**建议**：
- 删除 `acp/helpers/governance/review_gate.rs` 中的 `ReviewGateOutcome`，直接使用 `acp::prelude::ReviewGateOutcome`。
- 统一 `governance/review_controls.rs` 的 enum 和 `acp/impl/agent.rs` 的 struct — 考虑将 `governance` 的 enum 改为使用 `acp::prelude::ReviewGateOutcome` 加额外的 `verdict` 字段。

### 1.2 ReviewVerdict 重复定义 🟡

| 文件 | 变体 |
|------|------|
| `governance/review_controls.rs:24` | `Approve`, `Reject`, `Invalid` |
| `intelligence/verification.rs` (类型别名) | `QualityVerdict`: `Approve`, `ApproveWithCaveats`, `Revise`, `Reject`, `InsufficientEvidence` |

**分析**：`governance/review_controls.rs` 的注释明确说"使用 Approve/Reject 语义，不同于公有的 `acp::prelude::ReviewVerdict`（使用 Pass/Fail）"。但没有 `acp::prelude::ReviewVerdict` 这个类型，说明注释已过时。

**建议**：统一使用 `intelligence::quality_models::QualityVerdict`（通过 `intelligence::verification::VerificationVerdict` 别名），删除 `governance/review_controls.rs` 中重复的 `ReviewVerdict`。

### 1.3 治理层过度分离 — 5 个审查/门控系统 🔴

本项目有至少 **5 个独立的审查/门控系统**，功能重叠：

| 系统 | 位置 | 用途 | 活跃 |
|------|------|------|------|
| GuardianReviewer | `governance/guardian.rs` | 独立模型审查工具操作安全 | ✅ 已接线 |
| ReviewGate (双审查) | `acp/helpers/governance/review_gate.rs` → `acp/impl/agent.rs` | 全自动模式双模型审查 | ✅ 已接线 |
| ReviewControls | `governance/review_controls.rs` | 审查裁决解析 | ✅ 在 evaluator 中使用 |
| ApprovalEngine | `governance/approval_engine.rs` | 人工审批工作流 | ✅ 已接线 |
| SecurityGovernor | `governance/security_governor.rs` | 安全策略门控 | ✅ 已接线 |

**分析**：每个系统都有其合理的存在理由（不同抽象级别），但调用链可能过长。一个请求可能经过：
```
pre_route_policy → review_gate(薄包装) → run_dual_review_gate → GuardianReviewer(可选) → ApprovalEngine(可选) → SecurityGovernor(可选)
```

**建议**：
- 明确每个审查系统的职责边界，文档化在各自的模块说明中
- 考虑将 `GuardianReviewer` 集成到 `HarnessBus` 的 `PolicyEvaluator` 中，而不是独立调用
- `review_gate.rs`（薄包装）应精简 — 它只是调用了 `run_dual_review_gate` 然后映射结果

### 1.4 governance/harness_bus 与 acp/helpers/governance 职责重叠 🟡

`governance/harness_bus/` 是"策略引擎"，聚合所有治理组件。但 `acp/helpers/governance/` 中也有：

| acp/helpers/governance 文件 | 功能 | 重叠对象 |
|---|---|---|
| `tool_governance.rs` | 原子计数器 | 与 `governance/status.rs` 中的指标有部分重叠 |
| `tool_governance_defaults.rs` | 默认策略 | 与 `governance/hardening.rs` 中的策略有重叠 |
| `pre_route_policy.rs` | 路由前策略 | 与 `governance/harness_bus/evaluator.rs` 中的策略评估有重叠 |
| `policy.rs` | 策略工具函数 | 与 `governance/reloadable_policy.rs` 有重叠 |

**建议**：
- `acp/helpers/governance/tool_governance.rs`（原子计数器）应合并到 `governance/status.rs` 或 `observability/` 模块中
- 评估 `acp/helpers/governance/` 中哪些逻辑可以下沉到 `governance/` 模块，减少 ACP 层的包装逻辑

### 1.5 两个 circuit breaker 实现 🟡

| 文件 | 类型 | 用途 |
|------|------|------|
| `governance/guardian.rs` | `GuardianCircuitBreaker` | 防止重复拒绝压垮审查系统 |
| `acp/prelude/circuit_breaker.rs` | `CircuitBreakerRegistry` | Prometheus 指标只读快照 |
| `resilience/hyper_resilience.rs` | `HyperResilienceEngine` | 断路器状态机真实来源 |

**分析**：注释说明 `CircuitBreakerRegistry` 仅跟踪 Closed 状态，Open/HalfOpen 状态转换由 `HyperResilienceEngine` 管理。`GuardianCircuitBreaker` 独立跟踪审查拒绝。

**建议**：`CircuitBreakerRegistry` 的 `open_count()` 始终返回 0，此为设计使然但易误导。应添加更明确的状态同步机制，或者移除该 registry 中的 dead code（open_count）。

### 1.6 security/rate_limiter.rs 是薄包装 🟢

`security/rate_limiter.rs`（24 行）本质上是一个薄包装，委托给 `protocol/rate_limit.rs`。虽然不是严重问题，但增加了一个不必要的间接层。

## 二、执行效率分析

### 2.1 执行循环重叠 — 多条路径做类似的事 🔴

本项目至少有 **4 个执行循环**：

| 循环 | 文件 | 逻辑 |
|------|------|------|
| BrainLoop | `orchestration/brain_loop/` | Plan→Execute→Reflect→Replan |
| AutonomyLoop | `acp/helpers/autonomy/autonomy_loop.rs` | plan→act→observe→replan |
| FullAuto | `orchestration/full_auto/` | intent→executor→report |
| ChatPhases | `acp/impl/chat_phases.rs` | observe→think→act→reflect |

**分析**：
- BrainLoop 和 AutonomyLoop 的功能几乎相同（Plan→Execute→Reflect）。AutonomyLoop 通过 `autonomy_loop_adapter.rs` 桥接到 BrainLoop（当 `use_brain_loop=true` 时），但仍然维护自己的独立实现。
- FullAuto 的 `full_auto_plugin.rs` 桥接到 BrainLoop，但 FullAuto 目录本身有独立的 `executor.rs` 和 `environment.rs`。
- ChatPhases 的 `reflect_phase` 调用了 BrainLoop 的 reflection。

**影响**：同一个请求可能经过多个循环层，增加了不必要的延迟。例如，全自动模式可以经过：ChatPhases act_phase → AutonomyLoop → (可选的) BrainLoop。

**建议**：
- 逐步弃用 `autonomy_loop.rs` 中的独立实现，强制所有路径通过 BrainLoop（当 `use_brain_loop=true` 时）
- 评估 `full_auto/executor.rs` 是否可以完全由 BrainLoop + full_auto_plugin 替代

### 2.2 block_in_place + block_on 违反原则 (Rule #23) 🔴

**原则 Rule #23**：所有 `block_in_place + block_on` 必须在 production 热路径中清零。

发现了 **2 处违规**：

| 文件 | 行号 | 代码 |
|------|------|------|
| `memory/pg_pool.rs` | 74 | `tokio::task::block_in_place(|| { ... })` |
| `orchestration/tool/extended/spawn_agent.rs` | 168 | `tokio::task::block_in_place(|| { handle.block_on(...) })` |

**建议**：
- `pg_pool.rs`：检查是否可以使用 `spawn_blocking` 替代（PostgreSQL 客户端初始化通常是 CPU 密集的）
- `spawn_agent.rs`：该文件第 164-165 行的注释说明"为了避免违反原则 #24"，但实际却在违反原则 #23。应使用 `tokio::task::spawn_blocking` + `.await` 替代

### 2.3 Handle::current().block_on() 潜在风险 (Rule #24)

**原则 Rule #24**：必须使用 `try_current() + fallback` 模式。

`spawn_agent.rs:164-168` 使用了 `handle.block_on()`，虽然使用了 `try_current()` 模式，但 `block_on` 本身在异步上下文中仍然有风险。

### 2.4 审查调用链 — 串行瓶颈 🟡

`pre_route_policy.rs` 中审查的当前调用模式是串行的：
```
pre_route_policy → review_gate → run_dual_review_gate (两个审查者依次或并行)
```

但每个审查步骤都阻塞了工具执行。如果 `GuardianReviewer` 和 `run_dual_review_gate` 同时启用，工具执行将等待两个审查都完成。

**建议**：考虑在 HarnessBus 中批量处理审查请求，允许低风险工具旁路审查直接执行（已有 `is_low_risk_tool` 函数但未被 GuardianReviewer 使用）。

## 四、模块组织优化

### 4.1 acp/ 模块过于庞大

`src/acp/` 是最大的模块，包含约 38 + 多个子目录的文件。特别是：
- `acp/impl/chat/` — 10+ 子文件
- `acp/impl/request/` — 20+ 子文件/目录  
- `acp/helpers/` — 7 个子目录

虽然整体组织合理，但 `acp/impl/request/` 包含 `governance_handlers/`、`exec_pack/` 等子目录，使层次变深。

### 4.2 governance/ + acp/helpers/governance/ 分散

两个不同的 `governance` 目录：
- `src/governance/` — 核心治理模块（15 个文件）
- `src/acp/helpers/governance/` — ACP 层的治理辅助工具（7 个文件）

这些分散增加了认知负担。虽然 `acp/helpers/governance/` 是 ACP 协议的特定实现，但应该更清晰地文档化其与 `src/governance/` 的关系。

## 五、可并行化机会 🟢

### 5.1 工具执行中的审查

当 `is_low_risk_tool` 返回 true 时，工具执行不应等待审查。当前 `executor.rs` 已经使用 `is_low_risk_tool` 旁路阻塞审查，但 `GuardianReviewer` 未使用此优化。

### 5.2 MultiAgentPipeline 的 phase 执行

`multi_agent_pipeline.rs` 按顺序执行阶段，但不同阶段可能有独立的任务可并行执行。使用 `JoinSet` 是好的，但阶段间存在不必要的串行化。

### 5.3 缓存与审查并行

`chat_phases.rs` 的 `observe_phase` 串行获取缓存和审查。如果缓存命中，可以更快返回。

### 8.4 AutonomyLoop 与 BrainLoop 评估
