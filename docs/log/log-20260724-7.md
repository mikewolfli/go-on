## 🔴 P0 — 必须立刻合并/修复（功能严重重叠）

### 1. `resilience` vs `fault_tolerance` — 极度重叠（~85%代码重复）

**问题**：两个独立模块实现了几乎相同的功能集，每个都是完整的高度复杂模块。

| 功能 | `resilience` | `fault_tolerance` |
|------|-------------|-------------------|
| 熔断器 | `CircuitBreaker` (关闭/打开/半开) | `FaultToleranceEngine` 内含 |
| 故障检测 | `FaultVote` + `FaultConsensus` (投票共识) | `FaultEvent` + `FaultType` + heartbeat 检测 |
| 恢复计划 | `RecoveryPlan` + `RecoveryPlanStore` | `RecoveryPlan` + `RecoveryAction` |
| 健康监控 | `SystemHealth` + `DegradationLevel` | `ClusterHealth` + `NodeStatus` |
| 故障注入 | `chaos::ChaosEngine` + `FaultType` | (无，但 `FaultType` 已定义) |
| Profile | `ResilienceProfile` | `FaultToleranceProfile` |
| Persistence | `persist_to_db` / `load_from_db` | `persist_sqlite` / `persist_json` / `load_sqlite` / `load_json` |

**关键发现**：
- `resilience::hyper_resilience::HyperResilienceEngine` 包含自己的 `CircuitBreaker`、`FailoverGroup`、`FaultConsensus`、`SelfHealingAction` 等。
- `fault_tolerance::FaultToleranceEngine` 包含自己的节点注册、心跳跟踪、隔离组、升级级别等。
- `orchestration::recovery` 模块 **同时依赖** `HyperResilienceEngine`。
- `resilience::chaos::FaultType` 与 `fault_tolerance::types::FaultType` 重叠。
- `resilience::hyper_resilience` 有 `From<crate::optimization::failure_prevention::CircuitBreaker>` — 这是**第三个**熔断器。

**建议**：
1. 将 `fault_tolerance` 的节点监控功能（心跳、注册、隔离）移入 `resilience`。
2. 将 `resilience` 的熔断器合并为唯一版本，删除 `fault_tolerance` 中的冗余。
3. 将 `resilience::chaos::FaultType` 与 `fault_tolerance::types::FaultType` 统一。
4. 将 `orchestration::recovery` 的依赖统一到合并后的模块。

**影响范围**：~3000+ 行重叠代码，合并可节省 ~1500+ 行。

### 2. 三个熔断器系统 — 极度分裂

```
src/acp/prelude/circuit_breaker.rs       → CircuitBreakerRegistry
src/resilience/hyper_resilience.rs       → CircuitBreaker (内部)
src/optimization/failure_prevention.rs   → CircuitBreaker (有 From impl)
```

**问题**：相同的状态机（关闭/打开/半开）在三个不同位置实现，没有共享代码。

**建议**：
- 将 `acp::prelude::circuit_breaker::CircuitBreakerRegistry` 设为主要公用熔断器。
- 让 `resilience::hyper_resilience::HyperResilienceEngine` 包装 `CircuitBreakerRegistry` 而非重复实现。
- 删除 `optimization::failure_prevention.rs` 中的冗余熔断器定义。

### 3. 三个缓存系统 — 内存响应缓存

| 文件 | 后端 | 用途 |
|------|------|------|
| `memory/cache.rs` | SQLite / PostgreSQL | 通用响应缓存（后端驱动） |
| `memory/memory_response_cache.rs` | In-memory IndexMap | 进程内 TTL 缓存 |
| `memory/semantic_cache.rs` | In-memory bigram Jaccard | 语义近似匹配缓存 |

**问题**：`memory_response_cache` 和 `semantic_cache` 都是内存缓存，语义不同但可以共享基础设施。`cache.rs` 提供后端持久化但接口不同。

**建议**：
- `memory_response_cache` 可以重构为统一内存缓存后端。
- `semantic_cache` 可以实现为包装 `memory_response_cache` 的语义层，而不是独立实现。
- 提供统一的 `CacheBackend` trait。

### 4. 锁工具 — 7+ 重复实现

| 位置 | 函数/宏 | 类型 |
|------|---------|------|
| `shared/lock_utils.rs` | `lock_or_recover!`, `read_or_recover!`, `write_or_recover!` | **宏（推荐）** |
| `intelligence/mod.rs` | `lock_guard()`, `read_guard()`, `write_guard()` | 函数 |
| `intelligence/continuous_learning.rs` | `lock_guard()` (私有) | 函数 |

| `observability/mod.rs` | `lock_mutex()` (公开) | 函数 |

**每个实现都是**：
```rust
match lock.lock() {
    Ok(guard) => guard,
    Err(poisoned) => {
        tracing::warn!("...");
        poisoned.into_inner()
    }
}
```

**建议**：
- 所有位置统一使用 `shared::lock_utils::lock_or_recover!` 宏。
- 删除所有私有的 `lock_guard` 函数。
- 将 `intelligence/mod.rs` 中的 `lock_guard`/`read_guard`/`write_guard` 重写为宏的包装器或直接删除。

**影响**：消除 ~70 行重复的模式匹配代码，约 40 个调用点。

