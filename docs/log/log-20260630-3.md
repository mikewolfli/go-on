### 1. 🔥 PRINCIPLE #23 修复: block_in_place + block_on 清零

**文件:** `src/orchestration/tool/mod.rs` (L2419-2436)

**问题:** `SkillExecuteTool::run()` 同步桥接方法在 hot path 中使用

## 第二轮修复（GUI 空回复 + SSE 流完整性）

### 10. 🔧 GUI Chat 空回复问题修复

#### 10.1 根因分析

**文件:** `gui/src/views/chat/chat_impl/runtime.rs` (L878-890)

**问题:** SSE 流结束后，如果 `final_content` 为 `None`（无 `"result"` 或 `"done"` 事件
携带 `"response"` 字段到达），`ChatCompleted` 发送 `content: ""`。
`process_pending` 中 `if !content.is_empty()` 守卫条件（L1072）阻止了空内容的更新，
导致助手占位符消息保持空白。用户看到空回复，没有任何错误提示。

触发条件:
- `emit_stream_done` 发送 `event: done` 但 payload 不包含 `"response"` 字段
- GUI 匹配 `"result" | "done"` 事件时，`val.get("response")` 返回 None
- `final_content` 保持 `None` → `ChatCompleted` 内容为空

**修复 1 (GUI):** 当 SSE 流结束后 `final_content` 为 None/空 且有关联 agent 时，
发送 `PendingResponse::Error` 而非空的 `ChatCompleted`，用户能看到错误消息。

#### 10.2 SSE done 事件添加 response 字段

**文件:** `src/acp/impl/chat/streaming.rs` (L122-179)

**修复:** `emit_stream_done()` 新增 `response: Option<&str>` 参数，
当有响应文本时将其注入 SSE payload 的 `"response"` 字段。

这样 GUI 在处理 `"done"` 事件时也能提取到响应内容，不依赖独立的 `"result"` 事件。

**同步修改调用者:**
- `agent_runtime.rs` - 传入 `&response`（累积的 agent 响应）
- `chat_phases.rs` - 传入 `&response_text`（投票/回退结果）和 `text`（缓存响应）

### 11. 🔄 sync RwLock/Mutex 在 async 上下文扫描

全项目扫描发现 27 个 hot path 上的同步锁调用。分析结论：

| 文件 | 锁数量 | 持有时间 | 影响评估 |
|------|--------|----------|----------|
| `chat_phases.rs` | 9 | 微秒级 | ☑️ 低（锁快速释放） |
| `agent_preference.rs` | 4 | 微秒级 | ☑️ 低 |
| `pipeline.rs` | 2 | 微秒级 | ☑️ 低 |
| `agent_selection.rs` | 1 | 微秒级 | ☑️ 低 |
| `fallback.rs` | 2 | 微秒级 | ☑️ 低 |
| `knowledge.rs` | 1 | 微秒级 | ☑️ 低 |

tokio 官方文档指出：对于短暂持有的锁，`std::sync::Mutex` 实际上表现良好。
这些锁的持有时间都是内存操作微秒级，不是 I/O 等待。
真正的性能瓶颈在外部（网络 I/O、LLM 调用延迟），而不是这些锁。
因此暂不修改，留作未来优化项。

### 13. 📋 Plan→Act 完整衔接流程

#### 13.1 新增 `PlanOutput` 模块

**文件:** `src/orchestration/plan_output.rs` (全新)

核心数据结构:

```rust
pub struct PlanOutput {
    pub plan_text: String,           // AI 生成的完整计划文本
    pub steps: Vec<PlanStep>,        // 解析出的步骤列表
    pub recommended_mode: String,    // 建议执行模式 (edit/full_auto/safeguard)
    pub risk_score: f64,            // 风险评估 (0.0-1.0)
    pub requires_approval: bool,    // 是否需要用户批准
    pub summary: String,            // 计划摘要
    pub affected_files: Vec<String>, // 涉及的文件
    pub complexity: u8,             // 复杂度 (1-10)
}

pub struct PlanStep {
    pub number: usize,
    pub description: String,
    pub action: Option<String>,  // read/create/edit/test/delete/search/execute
    pub file: Option<String>,    // 目标文件
    pub completed: bool,
}
```

**解析逻辑** (`extract_plan_from_response`):
- 从 Markdown checkbox (`- [ ]`) 和编号列表提取步骤
- 从反引号提取文件引用
- 关键词匹配计算风险评分
- 根据复杂度和风险推荐执行模式

附带 **7 个单元测试** 覆盖:
- 空响应 → `recommended_mode: "edit"`
- 多 checkbox 步骤 → 正确解析 4 个步骤 + 动作分类
- 安全关键词 → `mode: "safeguard"`, `requires_approval: true`
- 复杂计划(8步) → `complexity >= 6`
- Serde 序列化/反序列化 roundtrip
- 动作分类 (read/create/edit/test/delete/search/execute)
