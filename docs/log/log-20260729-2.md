## 3. 执行系统重叠 — 深入分析

### 3.1 6 大执行系统对比

| # | 系统 | 文件数 | 行数(估) | 核心模式 | 与谁重叠 |
|---|------|--------|----------|----------|----------|
| 1 | `brain_loop` | 4 | ~1200 | Plan→Execute→Reflect→Replan | 与 loop_executor, planner_executor |
| 2 | `full_auto` | 5 | ~880 | Intent→Skill Match→Execute→Report | 与 brain_loop 的自动模式 |
| 3 | `loop_executor` | 12 | ~780 | Think→Act→Observe (单工具) | 与 brain_loop, planner_executor |
| 4 | `planner_executor` | 3 | ~460 | Plan→Execute (DAG 分离) | 与 brain_loop (plan+exec) |
| 5 | `multi_agent_pipeline` | 1 | ~300 | Decompose→Parallel Dispatch→Synthesize | 与 brain_loop (拆分) |
| 6 | `evolution_loop` | 5 | ~500 | Trigger→Analyze→Propose→Apply→Verify→Record | 与 brain_loop (反思) |

### 3.2 重叠分析矩阵

```
                brain_loop  full_auto  loop_exec  planner_ex  multi_ag  evolution
brain_loop        —          plan       TAO+x2     plan+exec   dispatch  reflect
full_auto        plan        —          execute    plan        —         —
loop_executor    TAO+x2    execute       —         execute     —         —
planner_exec     plan+exec   plan       execute      —         dispatch   —
multi_agent     dispatch     —           —         dispatch     —         —
evolution       reflect      —           —           —           —        —
```

**核心发现**: 
- `brain_loop` + `loop_executor` + `planner_executor` 三者之间的重叠最严重——**都实现了 tool selection → execution 逻辑**
- `full_auto` 和 `brain_loop` 的 `plan` 阶段重叠——**都做 task parsing → skill matching**
- `evolution_loop` 的 `reflect` 阶段与 `brain_loop` 的 `reflection` 阶段概念重叠

### 3.3 `planner_executor` 的实际角色

深入代码后发现：
- `plan_optimization.rs` 中的 `Planner` 使用 `EmbeddingTaskClassifier` + 关键词启发式进行任务分解
- `execution.rs` 中的 `Executor` 执行 DAG 计划中的步骤
- 这些都与 `brain_loop` 的 `planning.rs` (L1-60) 功能重叠——`brain_loop` 也有 `start_plan()`, `execute_step()`, `reflect()` 的完整实现

**建议**: 
- P1: `planner_executor` 直接作为 `brain_loop` 的 "planning strategy" 插件，而非独立引擎
- P2: `loop_executor` 作为 `brain_loop` 的单步执行器
- P3: `full_auto` 作为 `brain_loop` 的 "automatic mode"

## 4. 缓存系统重叠 — 深入分析

### 4.1 各缓存实际使用情况

| # | 缓存 | 文件 | 行数 | 关键特征 | 是否重叠 |
|---|------|------|------|----------|----------|
| 1 | `GovernanceCache` | `tool/executor.rs:23-57` | 34 | HashMap+VecDeque, max 1000, 按 session+tool 缓存 | 与 #2 重叠 |
| 2 | `FastPathCache` | `fast_path_cache.rs` | ~300 | 泛型 TTL 缓存，按 sha256 key，3 种值类型 | 与 #1 重叠 |
| 3 | `MemoryResponseCache` | `memory/memory_response_cache.rs` | (待确认) | LLM 响应缓存 | 与 #4 缓存层面不同 |
| 4 | `SemanticCache` | `memory/semantic_cache.rs` | (待确认) | 语义向量缓存 | 与 #3 数据可能重复 |
| 5 | `Cache (sqlite)` | `memory/cache.rs` | (待确认) | SQLite 持久缓存 | 与 #1,#2 互补 |
| 6 | `SessionCompressor` | `session_compressor.rs` | ~100 | 会话摘要压缩 | 不是缓存—是压缩器 |

### 4.2 实际重叠检测

深入代码检查后发现：
- `GovernanceCache` 和 `FastPathCache` 确实都实现了 `HashMap + TTL(或FIFO淘汰)` 的缓存模式
- `MemoryResponseCache` 和 `SemanticCache` 服务于 memory 系统的不同层，共享数据但缓存粒度不同
- `SessionCompressor` 被误分类为"缓存"——它确实是压缩器，不是缓存
- SQLite cache 是持久层，与其他内存缓存不同层面

**修正分类**: 原 6 套缓存中，1 套误分类(SessionCompressor)，实际 5 套缓存中 GovernanceCache+FastPathCache 严重重叠。

## 7. 全链路效率瓶颈发现

### 7.1 深度审查 — 串行瓶颈

#### 🟡 `loop_executor.rs:650` — `block_in_place` 用于 CPU 密集的 `think()`

```rust
let think_result = block_in_place(|| {
    think(task, &tool_candidates, &retry_counts, config, recommender.as_deref())
});
```

**分析**: 这是合法的 CPU 卸载（`think()` 是 CPU 密集同步操作），符合 principle 第 23 条的唯一例外条件。但在 LLM 驱动的版本中，`think()` 的内部实现如果涉及 LLM 调用(即异步 I/O)，`block_in_place` 会阻塞工作线程。建议：
- 如果 `think()` 包含 LLM 调用，改为纯 async 实现
- 如果 `think()` 纯 CPU 计算（如 token 匹配），保留 `block_in_place` 更高效

#### 🟡 `planner_executor/execution.rs` — `spawn_blocking` 的使用

`execution.rs` 使用 `spawn_blocking` + `join_all` 执行多步骤，这是正确的，但步骤间的依赖解析是串行的（O(n²) 的「已完成集合」检查）。在大量步骤时可能成为瓶颈。

#### 🟢 Governance 链 — 15+ 变量的级联状态

`governance_handlers/status.rs` 中 `governance_status_payload()` 有 15+ 的 `_ready` 布尔变量级联链。这虽不是性能瓶颈，但增加了认知负荷和维护成本。

### 7.2 编译速度分析

由 `Cargo.toml` 可见：
- Release: `lto = "fat"`, `codegen-units = 1` — 最大优化但编译最慢
- Dev: `opt-level = 0`, `debug = true` — 最快编译
- Test: `opt-level = 0`, `lto = "off"` — 最快编译

**发现**: `workspace.members = [".", "gui", "sdk/rust", "test_i18n", "crates/mermaid-render", "crates/go-on-web-search", "crates/go-on-latex"]`
- `test_i18n` 是一个独立的 workspace member，只有 1 个 test.rs 文件
- 建议合并 `test_i18n` 为 `tests/` 目录下的一个集成测试，减少一个 workspace member 的编译开销

### 7.3 序列化/反序列化开销

在 `tool/executor.rs` 中：
```rust
let parsed_args: Value = serde_json::from_str(tool_args_str).unwrap_or_default();
// 以及后续大量 Value 操作
```

在高频路径上（chat, vote, debate），每次工具调用都解析 JSON。建议对高频工具（read_file, write_file, search_files 等）使用零拷贝或缓存解析后的 schema。
