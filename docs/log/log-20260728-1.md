## 2. 重复冗余功能 — 合并建议

### 2.1 🔴 11 处重复的 `now_ms()` 函数

以下模块各自定义了一个完全相同的 `now_ms()` 函数，均委托给 `shared::timestamps::now_ts_ms()`：

| 文件 | 行号 |
|------|------|
| `src/agents/communication/lifecycle.rs` | L167 |
| `src/agents/communication/message.rs` | L20 |
| `src/agents/session.rs` | L569 |
| `src/governance/reloadable_policy.rs` | L236 |
| `src/intelligence/mod.rs` | L18 |
| `src/observability/provenance.rs` | L218 |
| `src/optimization/compaction.rs` | L617 |
| `src/orchestration/tool/extended/code_index.rs` | L582 |
| `src/protocol/session_sync.rs` | L696 |
| `src/protocol/transport.rs` | L715 |
| `src/shared/provenance_helpers.rs` | L36 |

**建议**: 删除全部 11 处副本，改用 `crate::shared::timestamps::now_ts_ms()` 直接调用。每处节省约 3 行代码，减少函数调用的间接开销。

### 2.2 🟡 `acp/prelude/functions.rs` 的 `now_ts_ms()`

```rust
pub fn now_ts_ms() -> i64 {
    crate::shared::timestamps::now_ts_ms()
}
```

**建议**: 直接调shared版本或内联，节省间接代价。

### 2.3 🟡 `intelligence/mod.rs` 的锁包装函数

```rust
pub fn lock_guard<T>(mtx: &std::sync::Mutex<T>) -> std::sync::MutexGuard<'_, T> {
    crate::lock_or_recover!(mtx, "intelligence")
}
pub fn read_guard<T>(...)
pub fn write_guard<T>(...)
```

这三个函数与 `shared::lock_utils` 宏完全重复，增加间接层和二进制体积。全项目搜索发现它们只被 `intelligence` 模块内部使用了约 5 处。

**建议**: 删除这三个包装函数，调用处直接使用 `crate::lock_or_recover!` 宏。

### 2.4 🟢 `security::severity::DetectionSeverity`

已成功合并（原 `content_safety` 和 `prompt_injection` 各有自己的私有enum）。现在统一使用 `DetectionSeverity`。✅

### 2.5 🟢 `shared::alert_severity::AlertSeverity`

已成功提取到 `shared`，打破循环依赖。✅

### 2.6 🟡 `fault_tolerance` vs `resilience` 模块重叠

| 模块 | 关注点 |
|------|--------|
| `fault_tolerance` | 节点检测、心跳、隔离、恢复计划 |
| `resilience::hyper_resilience` | 熔断、降级、自愈、级联故障 |

虽然概念层面有重叠，但实现的具体机制不同。`fault_tolerance` 关注节点级别，`resilience` 关注服务级别。保留但建议增加文档说明两者区别，避免未来开发者困惑。

## 3. 性能执行效率优化

### 3.1 🔴 Hub 模块（死代码）占用编译资源

`hub/mod.rs` + `client.rs`(148行) + `server.rs`(298行) + `discovery.rs`(103行) ≈ 550 行代码，全部编译但未运行。

**建议**: 从 `lib.rs`/`main.rs` 移除 `pub mod hub;` 声明，将代码移到 `artifacts/` 或 `docs/blueprints/` 作为设计参考。预计节省 1-2 秒编译时间。

### 3.2 🔴 `compaction.rs` 全部为死代码

整个文件约 620 行（ConversationHistory + CompactionManager + AdaptiveCompactor + 全部测试），**所有类和方法都被 `#[allow(dead_code)]` 覆盖**。

**建议**: 如果短期内不会使用整个 compaction 方案，删除此文件及其测试，节省编译时间和维护成本。

### 3.3 🔴 `omnipotent.rs` —— 完整实现但未接入工作流

`OmnipotentMode` 实现了完整的令牌颁发/撤销、会话管理、审计日志。但 `orchestrator.rs` / `main/mod.rs` 均未将其接入。
- 没有 `Arc<OmnipotentMode>` 被创建并传递给任何运行时
- 没有中间件或路由检查 omnipotent 模式
- 所有测试仅测试该模块自身（未验证集成）

**建议**: 要么完整接线（创建一个顶层 omnipotent 实例并注入到 ModeRuntime），要么按设计储备移出编译路径。

### 3.4 🟡 串行工作流优化机会

**`tool/loop_executor.rs` (Think-Act-Observe 循环)**:
- 当前是严格串行的：Think→Act→Observe→Think→...
- 在有多工具可用时，可以提前并行"观察"多个候选工具的可行性（Act 阶段可以并行执行无副作用的只读工具）

**`planner_executor/execution.rs`**:
- 已经有 "多 ready 步骤并发执行" 的模式（通过 `futures::future::join_all` 和 `spawn_blocking`）
- 建议将此模式扩展到 **整个执行图层面**：当多个分支步骤都 ready 时，自动并行化

**`acp/helpers/agent_selector.rs`**:
- 现在单次选择一次评估一个agent。如果 `enable_multi_agent` 开启，可以改为并行评估候选代理
