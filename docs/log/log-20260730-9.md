### 3.2 问题分析

CapabilityBus 的模式是：**每个独立模块（Observability、Memory、Optimization等）在主模块目录中有一份实现，同时在 CapabilityBus 下又有一份"总线包装"**。

例如：
- `src/observability/` → `src/intelligence/capability_bus/observability_bus.rs`
- `src/memory/` → `src/intelligence/capability_bus/memory_bus.rs`
- `src/orchestration/` → `src/intelligence/capability_bus/orchestration_bus.rs`
- `src/optimization/` → `src/intelligence/capability_bus/optimization_bus.rs`
- `src/protocol/` → `src/intelligence/capability_bus/protocol_bus.rs`
- `src/agents/` 的发现/匹配 → `src/intelligence/capability_bus/discovery.rs`

这些总线包装器平均 400-600 行，本质上是**适配器模式**——它们将主模块包装为 CapabilityBus 可调用的接口。

### 3.3 评估结论

- **这些总线包装不是功能冗余**，而是架构设计模式（适配器），为 CapabilityBus 的统一调度接口服务。
- **但可以精简**：如果 CapabilityBus 直接调用主模块接口（通过 trait），则无需中间总线包装，可节省约 3,500 行。
- **由于 CapabilityBus `evolve()`方法是核心调度循环**，整合这些总线的工作量大、回归风险高，建议保留当前模式。
