## 2. 识别出的冗余模块与功能

### 2.1 🔴 关键冗余 (必须修复)

#### R1: config 双重加载 — 最大性能杀手

- **位置**: `src/main/mod.rs L270` (第一次) → `src/main/server.rs` → `src/acp/transport_factory.rs L296` (第二次)
- **详情**: `handle_validation_mode()` 调用 `AppConfig::load(&config_path)` 返回 `Arc<AppConfig>`。
  到 `dispatch_server()` 内部 `flow_manager()` 又调用一次 `AppConfig::load(config_path)`。
- **修复**: 将 `Arc<AppConfig>` 传入 `dispatch_server()` → `flow_manager(app_config)`，
  消除第二次磁盘读取+TOML解析 (~15-30ms)。
- **状态**: 当前已定义了参数位 `app_config: Option<Arc<AppConfig>>` 在 `new_acp_server()` 中，
  但 `dispatch_server` 并未传递。

## 5. 与 Zed 源码深度对比分析

### 5.1 Zed agent_servers 架构优势

Zed 的 agent_servers 设计哲学是 **最小权限 + 最大懒惰**：

1. **Zero server-side initialization**: Zed 不初始化任何认知模块，只是 spawn 子进程 + 连接 stdio pipe
2. **Everything is a protocol exchange**: 所有能力通过 `initialize` response 的 `capabilities` 字段协商
3. **Process per agent server**: 每个 agent 独立进程，故障隔离
4. **No startup IO**: 不读数据库、不建索引、不扫描文件系统

### 5.2 我们可以借鉴的模式

```
Zed:              settings.json → Command{path,args,env} → spawn → connect
                                                          ↓
                                                    子进程启动
                                                          ↓
go-on (当前):     CLI parse → config load → bootstrap → memory → CLC → start_server → cache init → dispatch → wire → STDIN
                                 ↑__________________ 300-1500ms ______________↑
                                                          
go-on (优化后):   CLI parse → config load → dispatch → STDIN (5ms)
                                                        ↑
                                                 后台: spawn→bootstrap→cache→wire...
```

## 8. 结论

go-on 作为一个全功能 ACP 服务器，提供了远超 Zed 自身 agent_servers 的能力 (tool system, multi-agent, governance, memory, orchestration, security scanning)。但正是这种"全能"设计导致了启动延迟远超应有的水平。

**核心矛盾**: 在作为 Zed agent_server 的场景下，go-on 加载了其全部功能栈，而 Zed 实际需要的只是：
1. 响应 `initialize` (告知 protocol version + capabilities)
2. 响应 `tools/list` (列出可用工具)
3. 响应 `session/prompt` (生成回答 + 调用工具)
4. 响应 `tools/call` (执行工具调用)

**优化方向**: 将所有非即时需要的初始化推入后台，确保 stdin JSON-RPC 循环在进程启动后 **5ms 内** 开始服务请求，与 Zed 原生体验持平。
