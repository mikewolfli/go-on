## 1. 死代码清理 (Dead Code Cleanup)

根据 principle #14-16，以下为经核实的有意义死代码：

### 1.1 `drain_oldest()` — `go-on/src/optimization/compaction.rs:84`

```rust
#[allow(dead_code)]
pub fn drain_oldest(&mut self, n: usize) -> Vec<ConversationTurn> {
```

- `ConversationHistory::drain_oldest()` 从未被任何代码调用
- 已有 `drain_to_max_tokens()` 和 `truncate_to_max_content_size()` 作为替代接口
- **建议**: 删除此方法及 `#[allow(dead_code)]` 注解

### 1.2 `TokenBucket` 死字段和方法 — `go-on/src/shared/token_bucket.rs`

| 项 | 行号 | 说明 |
|---|---|---|
| `last_refill_ms` 字段 | L24 | `#[allow(dead_code)]` — 仅用于 API 兼容性，内部不使用 |
| `new_ms()` 构造函数 | L52 | `#[allow(dead_code)]` — 迁移后未使用 |
| `refill_ms()` 方法 | L75 | `#[allow(dead_code)]` — 同上 |
| `BucketMap::is_empty()` | L162 | `#[allow(dead_code)]` — 未使用 |

**建议**: 删除以上 4 项。

### 1.3 `CircuitBreakerStage::Open/HalfOpen` — `go-on/src/acp/prelude/circuit_breaker.rs:60-70`

```rust
#[expect(dead_code, reason = "reserved for future HyperResilienceEngine sync; never constructed yet")]
```

- 两个 enum 变体标记为 `dead_code`，永远不会被构造
- 注释说明"保留给未来 HyperResilienceEngine 同步"
- 但 `resilience/hyper_resilience.rs` 已经有完整的 `CircuitBreaker` 实现并可以同步
- **建议**: 如果 ACP 的电路断路器实际从未进入 Open/HalfOpen，删除这两个变体；否则实际接线到 HyperResilienceEngine

### 1.4 `Hub` 模块 — `go-on/src/hub/`

- 整个 hub 模块（client + discovery + server）已确认是 **故意保留的设计储备**，不是意外死代码
- `hub/mod.rs:23-28` 明确说明不要删除
- **建议**: 保留不变，不做清理

### 1.5 `ApprovalPolicySuggester` — `go-on/src/governance/approval_learning.rs:443-576`

- 约 **130 行** 生产质量的策略建议引擎被 `#[cfg(test)]` 锁定
- `suggest_policies()` 分析历史审批数据、计算通过率、检测异常审批者——所有逻辑在生产中不可达
- **建议**: 移除 `#[cfg(test)]` 限制，实际接入 governance 管线

### 1.6 `ReputationStore` — `go-on/src/intelligence/reputation.rs`

- 文件头部明确说明"Production routing uses UnifiedKnowledgeBus"
- ~70% 的 API 在生产中不可达
- **建议**: 删除此文件，或确认是否有外部队列依赖其类型签名

## 2. 重复冗余功能合并去重

### 2.1 三套独立电路断路器系统 🔴

| 位置 | 类型 | 状态 |
|---|---|---|
| `go-on/src/optimization/failure_prevention.rs` | `CircuitBreaker` + `CircuitBreakerState` | 遗留实现 |
| `go-on/src/resilience/hyper_resilience.rs` | `CircuitBreaker` (完整) + `CircuitState` (重导出) | 主要实现 |
| `go-on/src/acp/prelude/circuit_breaker.rs` | `CircuitBreakerRegistry` + `CircuitBreakerStage` | ACP 专用 |

- `failure_prevention.rs` 保留 `CircuitBreakerState::Open/HalfOpen/Closed` 枚举但已被 hyper_resilience 替代
- hyper_resilience.rs L62 `pub use crate::optimization::failure_prevention::CircuitBreakerState as CircuitState` 重导出来消除类型冲突
- ACP 的 `CircuitBreakerRegistry` 有自己的独立状态管理，不与 hyper_resilience 通信
- **建议**: 删除 `failure_prevention.rs` 中的 `CircuitBreaker` 类型定义，完全迁移到 hyper_resilience；将 ACP 的 `CircuitBreakerRegistry` 与 hyper_resilience 打通

### 2.2 两套并行锁恢复 API 🟡

| API | 位置 | 使用频率 |
|---|---|---|
| `lock_or_recover!` / `read_or_recover!` / `write_or_recover!` | `go-on/src/shared/lock_utils.rs` | ~40+ 处使用 |
| `with_acp_lock()` / `with_acp_lock_async()` | `go-on/src/acp/prelude/lock_helpers.rs` | ~19 处使用 |

两者功能完全相同：加锁 + 中毒恢复。开发者需要选择两种 API。

**建议**: 统一为一种模式。推荐保留宏（更简洁），并让 `with_acp_lock` 内部调用宏。

### 2.3 三个审计系统共存 🔴

| 审计系统 | 位置 |
|---|---|
| `ThreadSafeAuditLog` | `go-on/src/governance/audit.rs` |
| `HarnessAuditTrail` + `PuaGovernanceProfile` | `go-on/src/governance/harness_bus/audit.rs` |
| `HashChainAuditor` | `go-on/src/security/audit_integrity.rs` |

HarnessAuditTrail 可选地委托给 HashChainAuditor，但 ThreadSafeAuditLog 完全独立。PuaGovernanceProfile 维护自己基于计数器的"审计"。

**建议**: 整合为一个统一的审计管线。ThreadSafeAuditLog 应被弃用并删除，所有审计通过 HarnessAuditTrail + 可选的 HashChainAuditor 链路完成。

### 2.4 Bigram Jaccard 相似度重复实现 🟡

| 位置 | 实现 | 类型 |
|---|---|---|
| `memory/semantic_cache.rs:80` | 字节级 bigram (`as_bytes().windows(2)`) | `Vec<&[u8]>` |
| `intelligence/quality_models.rs:180` | 字符级 bigram (`chars().zip(chars().skip(1))`) | `HashSet<(char, char)>` |

两者都计算 Jaccard bigram 相似度，仅表示形式不同。

**建议**: 在 `shared/` 下创建一个 `string_similarity` 工具模块，统一为一种实现。

### 2.5 6 处独立 LRU 淘汰逻辑 🟡

| 位置 | 类型 |
|---|---|
| `protocol/rate_limit.rs` — `RateLimitMiddleware::lazy_evict()` | HashMap |
| `protocol/session_sync.rs` — `SessionRegistry::cleanup_inactive_sessions()` | HashMap |
| `fault_tolerance/detector.rs` — `FaultToleranceEngine` 多方法 | HashMap |
| `resilience/hyper_resilience.rs` — `FaultConsensus::evict_stale()` | HashMap |
| `optimization/failure_prevention.rs` — `FailurePrevention::evict_oldest_request_entry()` | HashMap |
| `memory/memory_response_cache.rs` — `MemoryResponseCache::put()` | IndexMap |

**建议**: 没有一个 `LruHashMap` 工具类。创建一个 `shared/lru_map.rs` 统一所有 LRU 淘汰逻辑。注意：`memory_response_cache.rs` 使用 IndexMap（已有 LRU 能力），其他使用 HashMap。

### 2.6 两个重复的 `PolicyVerdict` / `AuditEntry` 类型 🟡

- `harness_bus/types.rs` 定义 `PolicyVerdict` 和 `AuditEntry`
- `security_governor.rs` 也定义 `PolicyVerdict` 和 `AuditEntry`
- 同名不同类型，`evaluator.rs` 必须手动转换

**建议**: 统一为一个类型定义。

## 3. 全项目执行效率优化

### 3.1 串行工作流并行化

#### (A) `bootstrap.rs::perform_bootstrap()` — 启动步骤串行 🔴

当前 5 步全串行：
1. 初始化 telemetry
2. 初始化 i18n
3. Debug 日志
4. 初始化 intermediate 目录
5. 发现 skills

步骤 1、2、4 无数据依赖，可 `tokio::join!`。估计节省 ~50-100ms 启动时间。

#### (B) `HarnessBus::audit()` — 4 把锁串行获取 🔴

```rust
audit_log.record()      // Mutex
audit_trail.lock()      // Mutex
structured_audit_trail.lock()   // Mutex
profile.lock()          // Mutex
```

**建议**: 合并为一个统一的审计写入点。

#### (C) `cancel_subtree()` — 串行取消传播 🟡

`go-on/src/agents/communication/messenger.rs:200-216` 串行发送取消消息给每个子树节点。

**建议**: 使用 `join_all` 并行发送。

#### (D) `MemoryRetrievalEngine::retrieve_relevant_memories()` — hot + warm 串行 🟡

热存储和温存储是独立数据源，可以并发查询。

### 3.2 性能瓶颈

#### (A) `SseBufferPool` 在 async 上下文使用 `std::sync::Mutex` 🔴

`go-on/src/agents/sse_optimizer.rs:29-48` — SSE 流式处理中的 buffer pool 使用同步 Mutex，阻塞 async worker 线程。

**建议**: 改用 `tokio::sync::Mutex` 或锁自由池。

#### (B) `MemoryResponseCache::get()` — 双重克隆 + 双重查找 🔴

```rust
let entry = entry.clone();          // 克隆 #1
guard.swap_remove(key);             // 移除
guard.insert(key.to_string(), entry.clone());  // 克隆 #2 + 插入（重新哈希）
```

**建议**: 使用 `get_mut()` + `shift_ordering()` 替代 remove+reinsert。

#### (C) `MemoryResponseCache::put()` — 双重查找 🟡

```rust
guard.shift_remove(&key);  // 查找 #1
guard.insert(key, ...);     // 查找 #2
```

**建议**: 使用 `entry()` API 避免二次哈希。

#### (D) `Messenger::deliver_single()` — 写锁粒度太大 🔴

`go-on/src/agents/communication/messenger.rs:249-256` 每次消息投递获取全 `inboxes` 的写锁。

**建议**: 使用 `DashMap` 或分片策略。

#### (E) `IdempotencyCache::insert()` — O(n) LRU 淘汰 🔴

`go-on/src/governance/hardening.rs:554-635` 使用 `Vec<String>` 做 FIFO，`remove(0)` 是 O(n)。

**建议**: 使用 `VecDeque`。

#### (F) `localize_validation_message()` — O(n) 链式字符串匹配 🟡

`go-on/src/core/config_validation.rs:54-227` 使用 ~15 个 `if message == "..."` 字符串比较。

**建议**: 改用 `HashMap<&'static str, &'static str>` 做 O(1) 查找。

#### (G) `build_prometheus_metrics()` — 每行单独分配 🟡

`go-on/src/acp/server/metrics_exporter.rs:188-337` 构建 `Vec<String>` 然后 `join("\n")`。

**建议**: 使用 `write!` 到单个 `String`。

#### (H) `Hardening::check_can_start` vs `check_and_start_task` — 80% 重复逻辑 🟡

`go-on/src/governance/hardening.rs:101-141` 和 `146-188` 重复相同的三项检查。

**建议**: 将 `check_can_start` 内联到 `check_and_start_task` 中。

#### (I) `memory_response_cache` vs `cache::ResponseCache` — 重复 TTL/淘汰逻辑 🟡

两者各自独立实现 TTL 检查和过期清除。

**建议**: 提取共享的 TTL 管理辅助函数。

#### (J) `ACL::write()` — 每次写入获取两次写锁 🟡

`ProvenanceLedger` 的 `write()` 方法获取锁 → 追加 → 释放，然后 `digest()` 再次获取锁。

**建议**: 在单次锁持有期间完成追加和摘要计算。

### 3.3 `block_in_place` + `block_on` 和 `Handle::current().block_on()` 审查

根据 principle #23-24，已经过全面审查：

| 位置 | 模式 | 判定 |
|---|---|---|
| `cli/diagnostics.rs` | 使用 `spawn_blocking` | ✅ 合规 |
| `orchestration/tool/builtin_tools.rs:1147` | `skill_runtime().block_on()`（专用 runtime） | ✅ 合规 |
| `orchestration/tool/extended/spawn_agent.rs:160` | `spawn_agent_runtime().block_on()`（专用 runtime） | ✅ 合规 |
| `orchestration/tool/extended/lsp.rs:387` | `lsp_runtime().block_on()`（专用 runtime） | ✅ 合规 |
| `orchestration/tool/extended/web_search.rs` | `web_search_runtime().block_on()`（专用 runtime） | ✅ 合规 |
| `server_builder.rs:796-800` | 注释确认已移除 `block_in_place + block_on` | ✅ 已修复 |

**结论: 全项目零违规。**
