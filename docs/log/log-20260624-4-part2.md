# Deep Scan: Skills Environment + Discovery System

**Date:** 2026-06-24
**Scope:** Full audit of skill system, sandbox integration, discovery engine, global skills directory, management APIs, and thread safety.

## A. Skill Sandbox Integration

### How skill execution flows through governance

```
execute_mcp_tool_call() in tools_pack.rs
  ├── HarnessBus check_tool_call(name, args)     ← whitelist check by tool NAME
  │     └── "skill_execute" → SandboxPolicy::can_execute_read_file(level)   ← always allowed
  │     └── "skill_list"    → SandboxPolicy::can_execute_read_file(level)   ← always allowed
  │     └── "skill-finder"  → SandboxPolicy::can_execute_read_file(level)   ← always allowed
  │
  ├── Budget tracking (wall-clock + PUA tokens)
  │
  ├── Route by tool name:
  │     ├── "skill-finder" → uses SkillDiscovery (Mutex<SkillDiscovery>) + registry.read()
  │     ├── "import_skill" → uses SkillImportStore
  │     ├── Known tools    → ToolRegistry → spawn_blocking → Tool::run()
  │     │     ├── SkillListTool    → SKILL_REGISTRY.read() → list()
  │     │     └── SkillExecuteTool → SKILL_REGISTRY.read() → get() → block_on(execute())
  │     └── Unknown name    → resolve from skill_registry (best_match_with_input)
  │                           → skill.execute(arguments).await
  │                           → registry.write().record_outcome()
```

### Key finding: tools ARE sandbox-checked by name, but individual skills are NOT

The HarnessBus `check_tool_call()` in `evaluator.rs` (line 461) does a **single string match on the tool name** (`skill_execute`, `skill_list`). It does NOT inspect the actual skill name being executed. The relevant lines:

- Line 478: `"skill_list"` → `SandboxPolicy::can_execute_read_file(level)` — allowed at all levels
- Line 495: `"skill_execute"` → `SandboxPolicy::can_execute_read_file(level)` — allowed at all levels
- Line 493: `"skill_creator"` (note: different name) → `SandboxPolicy::can_execute_read_file(level)`
- Line 565: `"skill-creator"` → `SandboxPolicy::can_execute_write(level)` — restricted at Strict+

**Consequence:** Any skill registered in the registry, regardless of the operation it performs, can be executed through `skill_execute` without additional sandbox scrutiny. A skill that writes to the filesystem or executes shell commands is not sandboxed individually—it relies solely on the prompt template's safety.

### `SkillExecuteTool` vs inline skill execution

There are **two paths** for skill execution:

1. **`SkillExecuteTool`** (tool/mod.rs line 2001-2078): A `Tool` trait implementation. Accessed via `global_tool_registry().get("skill_execute")` → `spawn_blocking(...)`. Internally uses a **separate tokio runtime** (`SKILL_RUNTIME`, line 1990-1998) and `block_on()`. Gets the skill from the global `SKILL_REGISTRY` static.

2. **Inline resolution** (tools_pack.rs lines 620-695): When a tool name is not found in the ToolRegistry, the code falls back to looking up the name in the skill registry directly. This path calls `skill.execute(arguments).await` directly on the async runtime (no `block_on`), and records outcomes on the `server.orchestration_deps.skill_registry`.

**Issue:** The `SkillExecuteTool` path does NOT record outcomes (no `record_outcome` call). Only the inline path does. So if an LLM uses `skill_execute`, there are no stats tracked for scoring/evolution.

### `skill_execute` required argument: only `skill_name` validated

The argument validation (tool_descriptors.rs line 552-556) checks only that `skill_name` is present. The `input` field is entirely optional and is defaulted to `{}`. There is no schema validation of the skill input against the skill's `input_schema`.

## B. Skill Discovery Bottlenecks

### Architecture

```
SkillDiscovery (Mutex-protected global)
  ├── SkillIndex (Vec<SkillIndexEntry>)
  │     ├── build(registry) — rebuilds ALL entries from registry.list()
  │     └── search(query, top_k) — tokenize + similarity + sort + truncate
  ├── Cache (HashMap<String, CachedResult>) — TTL 5 min, max 200 entries, FIFO eviction
  └── registry_ref: Option<Arc<RwLock<SkillRegistry>>>
```

### Index rebuild is lazy and never auto-refreshes

- `discover()` (line 298-301): **Only** rebuilds when `self.index.is_empty()`. This means once built, the index is NEVER rebuilt even if the registry gains new skills.
- No invalidation hook: When `create_skill_from_prompt` or `register` adds a skill, there's no signal to the `SkillDiscovery` to rebuild its index.
- **Practical impact:** If a new skill is added via `skill.create` RPC after the first `skill-finder` call, discovery will still have the stale index. The old index will be used until the server restarts.

### Cache granularity

- Cache key: `"{query}:{top_k}"` (e.g., `"data analysis:5"`). Case-normalized.
- When a cache entry for a query exists and is fresh (<5 min), the result is returned directly—no interaction with registry at all.
- **Subtle bug:** The cached results include runtime stats (total_calls, success_rate, etc.) that are snapshots. These become stale during the 5-minute TTL.

### Performance concerns

1. **Double iteration** in `discover()`: Line 315 does `registry.list()` (which clones all descriptors) to enrich results, even though `self.index.search()` already computed scores. This is wasteful—the enrichment could be integrated into the search step.

2. **Tokenization repeated on every query**: For every `search()` call, both name tokens and description tokens are recomputed via `tokenize()` in `SkillIndexEntry::similarity()` (lines 94, 108). These tokens are already stored in `SkillIndexEntry.tokens` but only for the combined `name + description` string. The split `name_tokens` and `desc_tokens` are not cached.

3. **Lock contention pattern**: `discover()` is called while holding `Mutex<SkillDiscovery>`, and also acquires `RwLock<SkillRegistry>` (read). If another thread holds the write lock on the registry (e.g., background refresh), discovery blocks.

4. **Stop-word list redundancy**: The `tokenize()` function (line 369) and `tokenize_text()` in execution.rs (line 408) both filter stop words and short tokens differently. `tokenize()` uses a curated stop-word list (87 words), while `tokenize_text()` uses only length (`>= 3`). This means discovery scoring and semantic similarity scoring in `best_match_with_input` use different token sets.

## C. Global Skills Directory Integration

### Path resolution

`default_agents_skills_dir()` in registry.rs (line 715-721):

```rust
fn default_agents_skills_dir() -> PathBuf {
    if let Ok(home) = std::env::var("HOME") {
        PathBuf::from(home).join(".agents").join("skills")
    } else {
        PathBuf::from(".agents/skills")
    }
}
```

- Correctly resolves `~/.agents/skills/` from `$HOME`.
- Fallback to `.agents/skills` relative to CWD—works in CI/docker where `$HOME` may be unset.
- Used by both `discover_and_register_local_skills()` and `spawn_skill_refresh_task()`.

### Discovery flow

1. **Bootstrap** (server.rs line 1126-1134): `discover_and_register_local_skills(None)` is called during `ServerBuilder::build()`. This blocks the startup until the scan completes (synchronous).

2. **Background refresh** (server.rs line 1145-1148): `spawn_skill_refresh_task()` is called, which runs a tokio task that rescans `~/.agents/skills/` every **60 seconds**.

3. **Hot-reload via mtime** (registry.rs lines 587-608): Each SKILL.md file's modification time is cached in `skill_file_mtimes`. If the mtime hasn't changed, the file is skipped.

### CRITICAL BUG: Modified SKILL.md files are NOT hot-reloaded

In `discover_and_register_local_skills()` (line 637-656):

```
// If we get here, the file has changed (or is new)
// ... 
if self.skills.contains_key(&manifest.name) {
    // Produces conflict warning and SKIPS!
    skipped += 1;
    continue;
}
```

The code flow is:
1. Check if mtime changed → if changed, proceed to parse
2. Parse SKILL.md → get manifest
3. Check if name already registered → **SKIP with a conflict warning**

So if you modify an existing SKILL.md file, the **mtime check passes** (file is newer), but the **name collision check** rejects it as a duplicate. The modified skill is never re-registered. The mtime tracking only helps with **new** skills that weren't registered before.

**To fix:** The code should `unregister()` the old skill before `register()`-ing the new one when a modified file is detected, or check the mtime map to distinguish "new file" from "modified file".

### SKILL.md parsing

`parse_skill_md()` in skill_import.rs (line 584-694):
- Parses YAML frontmatter between `---` delimiters
- Extracts `name`, `description`/`title`, `version`
- Falls back to `# Heading` for name, first paragraph for description
- Sanitizes name: lowercase, spaces→hyphens, strips non-allowed chars
- Sets `prompt_template` to the **full raw markdown** content

### What global skills can do

Global skills are registered as `PromptBasedSkill` with:
- `timeout_secs: 30` (compared to 120 for programmatically created skills)
- `input_schema: HashMap::new()` (no input schema—all LLM prompt work is done by the agent)
- `max_retries: 2`
- They require a `PromptSkillAgent` to be set (LLM provider). Without one, execution fails with a clear error.

### Skills folder index (`skills_folder.rs`)

- Exists as a separate subsystem: `SkillsFolderIndex` scans a `skills/` directory for `.txt`/`.list` files listing URLs.
- It only stores URLs; it does NOT fetch or register skills automatically.
- It's a `#[cfg(test)]`-gated module (`mod implementation` is only compiled in test mode). In release builds, this module is entirely absent.
- **Not integrated** with the main skill discovery or registry. No tools expose its content.

## D. Missing Skill Management

### What exists

| Operation | Path | Notes |
|-----------|------|-------|
| **Create** | `SkillCreatorSkill` (built-in), `create_skill_from_prompt` RPC, `handle_skill_create` (protocol_pack.rs) | Saves to disk if persistence_path set |
| **Compose** | `compose_skills()` RPC, `handle_skill_compose` | Pipelines A→B, with snapshot registry |
| **List** | `SkillListTool`, `skill_list` tool descriptor, governance status endpoint | Returns descriptors with stats |
| **Read/Discover** | `skill-finder` MCP tool, `SkillDiscovery` | Semantic search |
| **Execute** | `SkillExecuteTool`, inline resolution | Two paths (see A) |
| **Delete** | `remove_prompt_skill()`, `handle_skill_remove` RPC | Removes from registry + disk |
| **Update** | `goon_skill_update` MCP tool | Updates imported skill manifest fields |
| **Import** | `import_skill` MCP tool | With SHA-256 verification, allowlist |
| **Market** | `SkillMarketRegistry` | GitHub search, install/uninstall |
| **Evolve** | `skill_evolution()`, version history | Capped at 50 records |

### What's MISSING

1. **No tool to create/modify local SKILL.md files.** AI cannot write a SKILL.md to `~/.agents/skills/<name>/` through the tool interface. It would need to use `write_file` or an RPC, but there's no dedicated `skill.create_local` or `skill.write_md` tool.

2. **No enable/disable toggle for local/registered skills.** `SkillImportStore` has `set_enabled()` but this only applies to imported skills. Regular registered skills (including global directory skills) cannot be disabled without unregistering.

3. **No per-skill input schema validation at execution time.** The `skill_execute` tool accepts any `input` JSON, even if it doesn't match the skill's `input_schema`. There's no validation step before `skill.execute()`.

4. **No version rollback for prompt-based skills.** `goon_skill_version_rollback` exists only for imported skills. Prompt-based skills' evolution history is append-only with no rollback mechanism.

5. **No built-in skill to update `~/.agents/skills/` files.** The `SkillCreatorSkill` stores skills in the registry's persistence path (a JSON file), not as SKILL.md files in `~/.agents/skills/`. These are separate persistence mechanisms.

6. **Full-auto flow's `run_full_auto_flow` is partially wired.** It creates its own `ToolRegistry` (line 204: `Arc::new(ToolRegistry::new())`) rather than using the global tool registry. This means tools like `skill_execute` may not be available in full-auto mode.

## E. Skill Registry Thread Safety & Lock Analysis

### Lock architecture

```
SkillRegistry (no internal locks) 
  → Wrapped in Arc<std::sync::RwLock<SkillRegistry>>
  → Shared via:
      ├── server.orchestration_deps.skill_registry (primary)
      ├── SKILL_REGISTRY (OnceLock<Arc<RwLock>>) in tool/mod.rs (clone of primary)
      ├── SkillDiscovery.registry_ref (Option<Arc<RwLock>>) (clone of primary)
      ├── SkillCreatorSkill.registry (clone of primary)
      ├── SkillImportStore.skill_registry (clone of primary)
      └── SkillMarketRegistry.skill_registry (clone of primary)
```

### Identified issues

#### 1. Background refresh holds write lock for entire scan duration

`spawn_skill_refresh_task()` (registry.rs line 773):
```rust
match registry.write() {
    Ok(mut reg) => match reg.discover_and_register_local_skills(Some(&dir)) {
```

The write lock is held for the entire duration of scanning `~/.agents/skills/`, reading each SKILL.md, parsing frontmatter, and registering. On a slow filesystem or with many skills, this blocks ALL readers (including `skill-finder`, `skill_execute`, `skill_list`) for potentially seconds.

#### 2. Two-phase locking pattern in discovery

In `execute_mcp_tool_call` (lines 469-478):
```rust
let mut discovery = skill_discovery().lock()...;  // Lock A
let registry = server.orchestration_deps.skill_registry.read()...;  // Lock B
let scored = discovery.discover(query, top_k, &registry);
drop(registry);
drop(discovery);  // Intentionally or not, held until end of block
```

This acquires `Mutex<SkillDiscovery>` then `RwLock<SkillRegistry>` (read). If the background task holds `RwLock<SkillRegistry>` (write) and another task tries to acquire `Mutex<SkillDiscovery>`, there's no deadlock (different lock order), but there IS contention: discovery blocks on registry read lock, which blocks on background write lock.

#### 3. `ComposedSkill` uses an isolated snapshot registry

`compose_skills()` (registry.rs lines 384-396) creates a separate `Arc<RwLock<SkillRegistry>>` with cloned skills. This snapshot does NOT update when the original skills are modified or updated. Any evolution to skill_a or skill_b after composition is invisible to the composed skill.

#### 4. `SkillExecuteTool` uses a separate `block_on` runtime

```rust
static SKILL_RUNTIME: OnceLock<tokio::runtime::Runtime> = OnceLock::new();
// ...
let rt = skill_runtime();
rt.block_on(skill.execute(&skill_input))
```

This spawns a **current-thread** tokio runtime and blocks the calling thread (the `spawn_blocking` thread from tools_pack.rs) until the skill completes. For `PromptBasedSkill`, this means the LLM call runs on a separate runtime. This is unnecessary since `execute_mcp_tool_call` is already async—the inline path (line 649) uses `.await` directly and is more efficient.

#### 5. `OnceLock` for SKILL_REGISTRY can only be set once

```rust
static SKILL_REGISTRY: OnceLock<Arc<RwLock<SkillRegistry>>> = OnceLock::new();
```

This is set via `set_skill_registry()` during server build. If the registry needs to be replaced (e.g., hot-reload with new schemas), this can't be updated. The `OnceLock` prevents replacement. This is by design (singleton pattern), but means tests that build multiple servers with different registries can't use this global path.

#### 6. `PromptSkillAgent` is a global singleton

```rust
static PROMPT_SKILL_AGENT: OnceLock<Arc<dyn PromptSkillAgent>> = OnceLock::new();
```

This can only be set once. Tests cannot swap it. Server restart is required to change the LLM agent for skill execution.

### Lock hierarchy (recommended ordering)

Current implicit ordering observed:
1. `Mutex<SkillDiscovery>` (acquired first in `execute_mcp_tool_call`)
2. `RwLock<SkillRegistry>` read (acquired second in discovery)
3. `RwLock<SkillRegistry>` write (background refresh, skill creation)

**Risk:** If any code path acquires the registry write lock first, then tries to acquire the discovery mutex, a deadlock becomes possible. There is no enforced lock ordering documentation.
