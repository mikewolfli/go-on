### 1.2 Zed 的 ACP 客户端架构

**文件**: `zed/crates/agent_servers/src/acp.rs`

Zed 的 `AcpConnection` 管理 ACP 传输，支持 stdio 和 HTTP 两种传输方式。

**初始化序列**:
1. Zed → Agent: `initialize`（支持能力协商）
2. Agent → Zed: `InitializeResponse`（协议版本 + agent 能力 + 认证方式）
3. Zed → Agent: `session/new`（创建对话 session）
4. Zed → Agent: `session/prompt`（发送用户消息，接收流式响应）

**agent-to-client 请求**（agent 可以主动向 Zed 发起请求）:
- `handle_write_text_file` — agent 请求 Zed 写文件
- `handle_read_text_file` — agent 请求 Zed 读文件
- `handle_create_terminal` — agent 请求 Zed 创建终端
- `handle_kill_terminal` — agent 请求 Zed 终止终端
- `handle_terminal_output` — agent 请求 Zed 获取终端输出
- `handle_request_permission` — agent 请求 Zed 用户审批

### 1.3 Zed 的工具调用方式

**文件**: `zed/crates/agent/src/thread.rs`

Zed 的 chat loop (`run_turn_internal`) 流程：
1. compaction（压缩历史）
2. 构建请求消息（system prompt + 历史）
3. 从 LLM 流式获取 completion
4. 处理事件（text/tool calls/thinking）
5. 等待工具结果
6. 如果工具有结果 → 回到步骤 2（下一轮）
7. 如果 end_turn → 停止

**关键差异**: Zed 的 chat loop **在本地运行**，工具由 Zed 自己执行。go-on 的 autonomy loop **在服务端运行**，工具由 go-on 执行。

### 1.4 Zed 的工具注册

**文件**: `zed/crates/agent/src/tools.rs`（AgentTool trait）

Zed 的每个工具是一个独立文件：

## 三、Tool Calling 系统问题（P0-P1）

### 🔴 P0-1: `edit_file` 工具有描述符但无实现

| 检查项 | 结果 |
|--------|------|
| `tool_descriptors.rs` | ❌ 无此工具的描述符 |
| `ToolRegistry::new()` | ❌ 未注册 |
| `builtin_tools.rs` / extended/ | ❌ 没有 `EditFileTool` 结构体 |
| `validate_required_arguments` | ❌ 无此工具的验证 |

**影响**: LLM 调用 `edit_file` 时路由到通用 MCP 处理，执行失败。Zed 原生支持 `edit_file`（接受 `old_text`/`new_text` 进行精确替换）。

**修复**: 添加 `EditFileTool`，参数包含 `path`、`old_text`、`new_text`，实现字符串替换。

### 🔴 P0-2: `find_path` 是别名而非独立工具

`find_path` 被映射为 `search_files` 的别名（glob 路径搜索），但语义上 `find_path` 是"按文件名模式查找路径"。`search_files` 实际是内容搜索。

**影响**: LLM 调用 `find_path` 时执行的是路径搜索而非内容搜索，但别名机制导致正确执行。问题在于 `tool_descriptors.rs` 中没有独立的 `find_path` 描述符。

### 🔴 P0-3: `search_files` 名称误导

`search_files` 的描述是 "Search for files matching a glob pattern"，这实际上是 `find_path` 的功能（按路径模式搜索），但名称暗示内容搜索。

**影响**: LLM 可能混淆 `search_files`（路径搜索）和 `grep`（内容搜索）。

### 🔴 P0-4: Autonomy Loop 工具参数验证失败时反馈不足

**文件**: `go-on/src/acp/helpers/autonomy/autonomy_loop.rs:410-451`

之前：错误消息只告诉模型 "Required parameters were not provided"，模型不知道应该传什么参数。

**已修复**: 已添加 schema 提示和 tool call 可见性标记（本轮修复）。

### 🟡 P1-1: `apply_patch`、`run_tests`、`inspect_git_diff` 缺少 input_schema

| 工具 | `input_schema` | 实际支持的参数 |
|------|---------------|---------------|
| `apply_patch` | `{"type": "object"}` | `path`、`patch_content`、`format` |
| `run_tests` | `{"type": "object"}` | `directory`、`filter`、`features` |
| `inspect_git_diff` | `{"type": "object"}` | `directory`、`staged`、`files` |

**影响**: LLM 不知道如何正确调用这些工具。

### 🟡 P1-2: Autonomy Loop 工具重试未使用 `RetryPolicy`

`ToolRegistry.new()` 中每个工具都有 `RetryPolicy`（`max_retries`、`retry_on_failure`），但 autonomy loop 的 `execute_tool_calls` 没有使用这些策略，而是使用全局 `consecutive_failures` 计数器。

### 🟡 P1-3: CLI `filter_tool_calls_by_mode` 硬编码默认工具列表

当 mode_runtime 为 None 时，默认只允许 6 个工具（`read_file`、`search_files`、`write_file`、`apply_patch`、`run_tests`、`inspect_git_diff`、`shell_exec`），大量工具被静默阻塞。

**影响**: CLI 模式下大量工具不可用。

### 🟡 P1-4: tools 在 ACP handler 和 agent_options 中双重装配

- `build_mcp_tool_descriptors`（`tools_pack.rs:51-425`）用于 ACP `tools/list`
- `assemble_agent_options`（`agent_options.rs:36-145`）用于 LLM function calling

两套路径都从 `tool_descriptor()` 获取 schema，但装配方式不同。`agent_options.rs:121-136` 使用全局 `ToolRegistry` 作为 LLM 工具，而 `build_mcp_tool_descriptors` 也使用全局 `ToolRegistry`。理论上一致，但有代码重复。

## 五、GUI / CLI Chat Loop 问题（P0-P2）

### 🔴 P0-5: GUI `SyncSender` 退避阻塞 SSE 读取

**位置**: `go-on/gui/src/views/chat/chat_impl/runtime.rs:46-59`

`try_send_with_retry` 使用 `SyncSender`（容量 256），当主循环处理不及时时触发退避（5ms→200ms），阻塞 tokio 任务（包括 SSE 读取循环），累积 TCP 缓冲区。

**建议**: 改用 `UnboundedSender` 或批量合并 StreamChunk。

### 🟡 P1-7: CLI 消息全量 `to_vec()` 克隆

**位置**: `go-on/src/cli/chat.rs:1970`

`run_agent_streaming_phase` 中 `messages.to_vec()` 在长对话场景下产生大量堆分配。

**建议**: 使用 `Arc<[Message]>` 共享历史。

### 🟡 P1-8: GUI session 全量 clone + 全量写盘

**位置**: `go-on/gui/src/views/chat/chat_impl/storage.rs:148`

`save_sessions_to_disk` 每次写入克隆所有 sessions 并全量序列化。

**建议**: 增量写入或异步队列。

### 🟡 P1-9: CLI `run_followup_phase` 与 ACP 路径不一致

**位置**: `go-on/src/cli/chat.rs:2314-2423`

CLI followup 没有 timeout、没有 skill dedup、没有 token 限制，与 ACP 侧的 `run_followup_after_tool_observation` 完全不同。

### 🟢 P2-2: GUI/SyncSender 退避替代方案

建议将 [UnboundedSender 方案] 或 [批量合并 StreamChunk 方案] 作为备选。
