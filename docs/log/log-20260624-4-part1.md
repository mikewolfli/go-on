## A. Missing Sandbox Whitelist — `_ => false` Catch-All in `SandboxPolicy::check()`

### The Problem

**File:** `src/governance/hardening.rs`, lines 733–747

```rust
pub fn check(level: SandboxLevel, operation: &str) -> bool {
    match operation {
        "read" | "read_file" => Self::can_execute_read_file(level),
        "search" | "grep" | "find_path" => Self::can_execute_search(level),
        "write" | "write_file" | "apply_patch" | "create_directory" => Self::can_execute_write(level),
        "shell" | "execute_command" | "terminal" | "bash" => Self::can_execute_shell(level),
        "network" | "http_request" | "dns_lookup" | "ping" | "port_scan" => Self::can_execute_network(level),
        _ => false,  // <--- CATCH-ALL DENIES EVERYTHING
    }
}
```

The `_ => false` catch-all means any tool not explicitly listed gets **denied at any sandbox level above None**. This directly contradicts the requirement that unknown tools should default to "ask user" (inline confirmation dialog).

### Where `check()` Is Called

1. **`enforce_action()`** at `hardening.rs` L777 — used by `HarnessBus::enforce_action()` (L490-524 in mod.rs). This is the older code path that categorizes via `GovernanceAction` enum, not via `check()`.

2. **`PolicyEvaluator::check_tool_call()`** at `evaluator.rs` L461-598 — this is the **primary** tool validation path. It has its **own separate mapping** with a different default:
   ```rust
   let allowed = match tool {
       // ... exhaustive mapping ...
       _ => SandboxPolicy::can_execute_read_file(level),  // <--- defaults to READ (allowed)
   };
   ```

### Critical Divergence: Two Different Mappings

There are **two parallel mappings** of tool names to sandbox actions:

| Function | Location | Default for Unknown | Effect at Strict |
|---|---|---|---|
| `SandboxPolicy::check()` | `hardening.rs:733` | `false` — Deny | Blocks unknown tools |
| `check_tool_call()` | `evaluator.rs:471` | `can_execute_read_file()` — Allow | Allows unknown tools |

The actual **ACP tool execution path** (`tools_pack.rs:execute_mcp_tool_call`) calls `check_tool_call()`, not `check()` directly. However, other callers of `enforce_action()` or `check()` will get the deny behavior.

### What's Missing: "Ask User" Concept

Neither path supports an "ask user" (aka "RequireReview" / inline confirmation) outcome. The `PolicyVerdict` enum has `Review(ReviewReason)` but it's never returned from `check_tool_call()`. The result is a binary `ToolVerdict { allowed: bool }`:

```rust
// evaluator.rs L592-597
ToolVerdict {
    allowed,
    idempotent,
    budget_ok,
    permitted,
}
```

A "RequireReview" state would need to either:
- Add a new variant to `ToolVerdict` (e.g. `require_review: bool`)
- Or return a `PolicyVerdict` instead of `ToolVerdict` from `check_tool_call()`

Then the caller (`execute_mcp_tool_call` in `tools_pack.rs` L311-347, or the TAO loop) would need to handle "RequireReview" by emitting an inline confirmation prompt rather than bailing with an error.

### Recommended Fix

1. **Add a `require_review` field to `ToolVerdict`**, e.g.
   ```rust
   pub struct ToolVerdict {
       pub allowed: bool,
       pub require_review: bool,  // NEW: true = ask user before proceeding
       pub idempotent: bool,
       pub budget_ok: bool,
       pub permitted: bool,
   }
   ```

2. **In `check_tool_call()`**, change the fallthrough `_ =>` to return `require_review: true` instead of defaulting to read access:
   ```rust
   // For tools that are not explicitly categorized
   "unknown_tool" => {
       ToolVerdict {
           allowed: false,       // not auto-allowed
           require_review: true, // ask user permission
           ...
       }
   }
   ```

3. **In `execute_mcp_tool_call()`** (tools_pack.rs L311), handle `require_review` by sending a confirmation event back through the stream observer and waiting for user response.

## C. ToolLockManager — `std::thread::sleep()` in Async Contexts

**File:** `src/orchestration/tool/lock.rs`

### Current State

```rust
// acquire() — BLOCKING (line 175)
std::thread::sleep(Duration::from_micros(sleep_us));

// acquire_async() — NON-BLOCKING (line 218)
tokio::time::sleep(Duration::from_micros(sleep_us)).await;
```

### How Tools Actually Use Locks

Every tool implementation uses `try_acquire()` (non-blocking), NOT `acquire()`:

- **`ReadFileTool`**: `tool_lock_manager().try_acquire(...)` — falls back to no lock if contended (L1535-1538)
- **`WriteFileTool`**: `tool_lock_manager().try_acquire(...).ok_or_else(|| ...)` — returns error if contended (L1585-1595)

This is the correct pattern — tools never call the blocking `acquire()`. The lock acquisition is best-effort.

### Who Calls `acquire()`?

A grep for `\.acquire\(|\.acquire_async\(` across the codebase shows that `acquire()` is only called in tests (lock.rs tests). No production code calls the blocking `acquire()`.

### Assessment

The blocking `acquire()` is not currently used in production paths, so it's not causing runtime issues. However, it's a footgun:

1. If any future code calls `acquire()` from an async context (e.g., inside an `async fn` running on tokio), it will block the entire runtime thread.
2. The `acquire()` method's 30-second timeout with `std::thread::sleep()` means a stray call to it would block a tokio worker for up to 30 seconds.
3. **Recommendation**: Make `acquire()` panic or emit a compile-time warning so developers don't accidentally use it in async contexts. Or remove the synchronous `acquire()` entirely and keep only `try_acquire()` + `acquire_async()`.

## D. Missing Tools Compared to Current Zed/IDE Capabilities

- **What it does**: Retrieves compiler/linter diagnostics (errors, warnings) for a project or specific file.
- **Why it's missing**: The platform has `cargo_check` which compiles code, but no tool to fetch the current set of diagnostics from the language server.
- **Where to add**: New tool in `tool/mod.rs` or `extended/mod.rs`.

- **What it does**: Renames a symbol (variable, function, type) across all references.

### 3. `format_code` / `format`
- **What it does**: Format a file using the project's formatter (rustfmt, prettier, etc.).
- **Why it's missing**: No tool for triggering code formatting.
- **Where to add**: Could be a subcommand of `cargo_check` or a standalone tool.

### 4. `hover` / `get_definition` / `get_references`
- **What it does**: LSP-based code intelligence — get symbol definition, references, type at position.
- **Why it's missing**: Requires LSP integration.
- **Where to add**: New group of tools in `extended/`.

### 5. `completions` / `get_completions`
- **What it does**: Get code completions at a cursor position.
- **Why it's missing**: LSP-based feature that IDE agents use.

- **Why it's missing**: `grep` searches file contents, but there's no structured symbol search.

### 8. `read_file_range` / `read_file_lines`
- **What it does**: Read specific line ranges of a file, not the whole file.
- **Why it's missing**: `read_file` reads the entire file. For large files, the ability to read specific line ranges would be useful.

### 9. `environment_info`

- **Where to add**: New metadata tool.

### 10. Actual Tool Execution (not just logging)

**Critical finding in `task.rs` L1110-1139**: The function `execute_model_tool_calls()` does NOT execute tools. It only **formats observation strings**:

```rust
fn execute_model_tool_calls(...) -> Vec<String> {
    let mut observations = Vec::new();
    for (idx, tc) in tool_calls.iter().enumerate() {
        let observation = format!(
            "[Tool call {idx}] tool={tool_name} args={args} task={task} ..."
```

This means the TAO (Think-Act-Observe) loop in the agent runtime **logs tool calls but doesn't execute them through the registry**. The actual tool execution happens through the separate `execute_mcp_tool_call()` path in `tools_pack.rs`. This dual-path architecture means:
- Tool calls from native AI function calling go through `execute_mcp_tool_call()` (tools_pack.rs) — governance-aware
- Tool calls from the TAO loop go through the `ToolRegistry::run_with_fallback()` (mod.rs) — NOT governance-aware
- The `execute_model_tool_calls()` in task.rs just logs — it doesn't execute

## E. Lock Contention Analysis

### 1. ToolLockManager — Low Contention Risk

The `ToolLockManager` (lock.rs) uses per-path read/write locks with `try_acquire()` (non-blocking). Path-level granularity means:
- `read_file` and `write_file` on different paths → no contention
- Multiple `read_file` on same path → allowed (readers don't block each other)
- `read_file` while `write_file` on same path → write blocks readers, but `try_acquire` returns immediately

**Verdict**: Low contention risk. The non-blocking `try_acquire()` pattern is appropriate. No `acquire()` (blocking) is called in production code.

### 2. HarnessBus / PolicyEvaluator — Medium Contention Risk

In `evaluator.rs:check_tool_call()` (L461-598), the following sequential locks are acquired:

```rust
let level = *self.sandbox_level.lock().unwrap_or_else(...);
// ... tool matching ...
let idempotent = self.idempotency.lock().unwrap_or_else(...).get(tool).is_some();
let budget_ok = self.budget.lock().unwrap_or_else(...).record_tool_call().is_ok();
let permitted = self.check_permission(tool, _args);  // May acquire more locks
```

Each is a separate `Mutex` on the `PolicyEvaluator` struct. Since they are acquired sequentially (not held simultaneously), the contention risk is moderate — each lock is held only briefly, but in a high-throughput scenario (many parallel tool calls), all callers will contend on the same `self.sandbox_level`, `self.budget`, and `self.idempotency` mutexes.

**The bigger issue**: In `evaluator.rs:evaluate()` (L192-458), the flow acquires locks in sequence:
1. `self.policies.read()` — RwLock read
2. (possibly) `self.policies.write()` — RwLock write (upgrade)
3. `self.rule_engine.lock()` — Mutex
4. `self.budget.lock()` — Mutex
5. `self.runtime_control.lock()` — Mutex
6. `self.guard.lock()` — Mutex

This sequential locking in `evaluate()` can slow down evaluation for each tool call. However, since `evaluate()` is typically called once per task (not per tool call), the throughput impact is acceptable.

### 3. `governance_action_for_tool()` — Name-Heuristic Race Condition (Removed)

The comment in `tools_pack.rs` L394-401 notes that the old `governance_action_for_tool()` + `enforce_action()` double-check was removed because it duplicated the `check_tool_call()` mapping. This was a sound cleanup — the single authoritative mapping in `check_tool_call()` is the right approach.

### 4. Bloom Filter / Idempotency Cache Contentions

`IdempotencyCache` uses `std::sync::Mutex` internally with infrequent writes. Low contention.

### Summary of Lock Issues

| Lock | Location | Contention | Notes |
|---|---|---|---|
| `ToolLockManager` inner mutex | lock.rs | Low | Per-path, `try_acquire()` only |
| `PolicyEvaluator.sandbox_level` | evaluator.rs L462 | Medium | Every tool call |
| `PolicyEvaluator.idempotency` | evaluator.rs L574 | Medium | Every tool call |
| `PolicyEvaluator.budget` | evaluator.rs L583 | Medium | Every tool call |
| `PolicyEvaluator.policies` (RwLock) | evaluator.rs L196/L213 | Low-Medium | Task-level evaluation |
| `PolicyEvaluator.rule_engine` | evaluator.rs L247 | Low | Task-level evaluation |
| `PolicyEvaluator.runtime_control` | evaluator.rs L278 | Low | Task-level evaluation |
| `PolicyEvaluator.guard` | evaluator.rs L356 | Low | Task-level evaluation |
| `HarnessBus.profile` | harness_bus/mod.rs L181 | Medium | Per tool-call |
| `ToolRegistry` tools vec | mod.rs | None | Immutable after construction |

**Recommendation**: For high-throughput scenarios, replace `Mutex` on `sandbox_level` with an `AtomicU8` (since SandboxLevel is a simple 4-value enum). The `idempotency` and `budget` locks are harder to convert but could use `RwLock` or sharding if profiling shows them as bottlenecks.
