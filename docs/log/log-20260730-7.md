## 1. URL 预取并行化

### 问题
`chat_phases.rs:317-530` 的 `for` 循环逐个顺序获取 URL，每个有 3s 超时。3 个 URL = 最坏 9s。

### 方案
将获取拆为两阶段：
1. **并行获取** — 收集所有 URL 的 async future，用 `join_all` 并发执行
2. **串行处理** — 遍历结果做 SPA 检测、API 探测、消息插入（保持原有逻辑不变）

### 收益
N 个 URL 的最坏延迟从 `N × 3s` 降为 `~3s`（并行取最大值）。

## 2. governance/orchestration audit 统一

### 问题
`governance::audit::AuditLogEntry` 和 `orchestration::audit::AuditEntry` 各定义一套审计记录类型，字段有重叠。

### 方案
在 `governance/audit.rs` 中定义统一的 `AuditRecord`（两个类型字段的超集）+ `DecisionPoint`，并添加双向 `From` 转换：

```
AuditLogEntry ←→ AuditRecord ←→ orchestration::AuditEntry
```

`orchestration/audit.rs` 加一行 `pub use crate::governance::audit::AuditRecord;`。

**不改变任何现有 API**，所有旧类型继续可用。新代码可逐步迁移到 `AuditRecord`。

## 3. memory_response_cache double-lock 消除

### 问题
`MemoryResponseCache` 内部持有 `SemanticResponseCache`（自带 `RwLock`），但在 `MemoryBus` 中被 `Arc<StdMutex<MemoryResponseCache>>` 包裹，形成双层锁。

### 方案
去掉外层 `StdMutex`，仅保留 `Arc` 共享：

| 文件 | 改动 |
|------|------|
| `memory_bus.rs` | `Arc<StdMutex<MemoryResponseCache>>` → `Arc<MemoryResponseCache>` |
| `acp/server.rs` | `Arc<StdMutex<MemoryResponseCache>>` → `Arc<MemoryResponseCache>` |
| `acp/background.rs` | 同上 + 移除 `.lock().unwrap_or_else(...)` |
| `acp/impl/request/health_pack.rs` | 直接调用 `.clear_all()` |

### 收益
每次缓存操作减少一次 `StdMutex::lock()` 调用，简化锁定层级。

## 4. lib.rs/main.rs 导出统一 (替代方案)

### 尝试的方案
`main.rs` 中 `pub use go_on::*;` 替代 46 行 `pub use`。

### 失败原因
二进制 crate 需要 re-export `pub(crate)` 函数（如 `resolve_secret`），这些不被 `pub use go_on::*;` 覆盖。直接使用会导致 `E0603: function is private`。

### 替代方案（建议后续采用）
在 `lib.rs` 中定义一个 `pub(crate) mod reexports { ... }` 模块，同时在 lib.rs 和 main.rs 中 `use reexports::*;`。这需要在两个文件中各加一行 `use` 而不是目前的 46 行 `pub use`，但需要确保 `pub(crate)` 可见性正确。
