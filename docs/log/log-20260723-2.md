## 2. 架构哲学对比

### CodeWhale 的「单一运行时」原则

```
                    ┌───────────────────────┐
                    │ headless agent runtime  │
                    │ (full tools + sub-spawn)│
                    └───────────────────────┘
                      ▲          ▲          ▲
                      │          │          │
              ┌───────┴──┐ ┌────┴────┐ ┌───┴──────────┐
              │ TUI turn │ │codewhale│ │ Agent Fleet   │
              │interactive│ │ exec   │ │(durable:      │
              │in-process│ │(headless│ │ ledger, SSH,  │
              │          │ │ CLI/CI) │ │ scheduling)   │
              └──────────┘ └─────────┘ └───────────────┘
```

**核心思想**：只有一个 headless agent runtime，所有交互面（TUI、CLI、Fleet）都调用同一个核心。不存在"多端分裂"。

### go-on 的 14-bus 架构

```
HarnessBus (Governance) → CapabilityBus (Intelligence)
                        → ToolBus / ObservBus / OptimizBus / MemoryBus / ProtocolBus
                        → OrchestBus / DistMemBus
```

**核心思想**：通过专业化的 Bus 分离关注点，每个 Bus 有 Builder 模式 + Profile 结构 + health 端点。

### 对比

| 维度 | go-on | CodeWhale |
|------|-------|-----------|
| **分层粒度** | 14 个专业 Bus，每个有独立生命周期 | Agent Loop + Workflow + Fleet 三层 |
| **可观测性** | 每个 Bus 有 health 端点 + governance.status | Prometheus metrics + OTLP tracing |
| **复杂度管理** | Bus 模式在模块多时保持一致性，但 14 个 Bus 引入大量的 Builder/Profile 样板代码 | 更扁平的架构，单 Agent Loop 核心 |
| **单点故障风险** | Bus 链路过长时单点故障风险 | 单运行时核心，故障范围集中 |
| **扩展方式** | 加新 Bus → 实现 Builder → with_*_bus 注入 | 加 crate → 注册到 Agent Loop |

**分析**：go-on 的 14-bus 架构更正式、更系统化，适合需要细粒度治理的场景。CodeWhale 的架构更务实——单一运行时 + 两层编排（Workflow + Fleet），减少样板代码，更快迭代。

## 3. Sub-Agent 系统深度对比

这是 **CodeWhale 领先最显著** 的领域。

| 特性 | CodeWhale | go-on | 差距 |
|------|-----------|-------|------|
| **角色分类** | 7 种角色 (general/explore/plan/review/implementer/verifier/custom) | 无分类（纯 spawn） | 🔴 |
| **每角色模型** | 可为不同角色分配不同 provider/model | 单一模型 | 🔴 |
| **Token 预算** | 子代理树共享 aggregate token ceiling | 无 | 🔴 |
| **上下文 fork** | `fork_context: true` 保留父级 KV 缓存 | 无 | 🔴 |
| **工作树隔离** | `worktree: true` 创建隔离的 git worktree | 无 | 🔴 |
| **超时** | 可配置每步超时（默认 120s）+ heartbeat 超时（5min） | 无 | 🔴 |
| **重试** | 临时 provider 失败自动重试 + backoff | 无 | 🔴 |
| **provider profiles** | 每个 provider 独立配置并发/深度/预算 | 无 | 🔴 |
| **持久化** | `.codewhale/state/subagents.v1.json` 重启恢复 | 无 | 🔴 |
| **结构化输出** | SUMMARY/CHANGES/EVIDENCE/RISKS/BLOCKERS | 纯文本转录 | 🔴 |
| **并发上限** | 128 并发，1024 排队 | Zed 提供 | 🔴 |

### 可借鉴的设计

CodeWhale 的 `fork_context` 是一个极好的设计——当子代理从父代理 fork 时，保留父级的 KV 前缀缓存（针对 DeepSeek 优化），大幅降低子代理的推理成本。go-on 如果引入子代理系统，应该考虑这个模式。

## 4. Workflow 引擎对比

| 维度 | CodeWhale | go-on |
|------|-----------|-------|
| **工作流定义** | `.workflow.js` / `.workflow.ts`（编译到 IR） | JS sandbox |
| **执行模型** | 通过 Fleet 的 agent 进程执行（真实模型调用） | JS 沙箱内代码执行 |
| **权限** | 无 shell/filesystem/network/import 权限 | 沙箱内有受限权限 |
| **检入文件** | `workflows/` 目录，9 个样例 | 无 |
| **软自动检测** | Act/Operate 模式下模型自动识别何时需要 workflow | 无 |
| **扩展节点** | agent/branch/sequence/reduce/teacher_review/loop_until/cond/expand | 无 |
| **预算控制** | budget() 节点内建 | 无 |
| **扩展验证** | 100 workers 上限、5 层 Fleet rings、max_iterations 强制 | 无 |

**分析**：CodeWhale 的 Workflow 实际上是一个**编排策略层**（orchestration policy），而不是代码执行引擎。工作流定义的是"让 agent 做什么"，而不是"让 JS 做什么"。这是更安全的模型——真实工作始终通过模型进程完成，JS 只描述拓扑结构。go-on 可以借鉴这个思路，把现有的 JS sandbox 改造为"编排描述语言 + Fleet 执行"，而不是"JS 代码执行"。

## 5. Fleet / 持久化执行对比

**CodeWhale 独有的能力**。go-on 没有对应功能。

| 特性 | CodeWhale | go-on |
|------|-----------|-------|
| **CLI 命令** | fleet init/run/status/inspect/logs/artifacts/interrupt/restart/resume/stop | 无 |
| **持久化** | `.codewhale/fleet.jsonl` append-only ledger | 无 |
| **重启恢复** | `fleet resume` 跨进程/重启恢复 | 无 |
| **SSH 主机** | 通过 system ssh 远程执行 | 无 |
| **告警** | Slack/webhook/PagerDuty | 无 |
| **信任模型** | sandbox/local/remote-verified/operator 四级 | 无 |
| **密钥管理** | FleetSecretRef（env/keyring/file，日志脱敏） | 无 |
| **任务规格** | 类型化 JSON/TOML（id/instructions/role/tools/budget/artifacts） | 无 |
| **主机适配器** | Local + SSH | 无 |

### 可借鉴的设计

Fleet 是 CodeWhale 最独特的能力——它是一个**本地优先的持久化执行平面**。go-on 的 agent_servers 可以通过 Zed 的 ACP 发包实现类似功能，但没有 Fleet 的持久化、SSH 远程、密钥管理等配套能力。

**建议 go-on 关注的方向**：如果 go-on 要做持久化 agent 执行，可以借鉴 Fleet 的 append-only ledger + 重启恢复模式，但不一定需要 SSH 主机适配器（go-on 的定位是本地代理，不是远程执行引擎）。

## 6. 消息网桥对比

**CodeWhale 独有的能力**。go-on 没有对应功能。

| 网桥 | 技术栈 | 功能 |
|------|--------|------|
| Feishu/Lark | Node.js + Lark SDK，长连接模式 | 聊天/审批/远程控制 |
| Telegram | Node.js | 聊天/远程控制 |
| WeCom (企业微信) | Node.js | 聊天/远程控制 |
| Weixin | Node.js | 聊天/远程控制 |
| **桥接核心** | `@codewhale/bridge-core` | ThreadStore / RuntimeClient / SSE parser / 命令路由 |

**统一架构**：
```
消息平台 → Bridge (Node.js) → codewhale serve --http (127.0.0.1:7878) → Agent Loop
                              ↑
                          bridge-core 共享库
```

关键优势：
- codewhale 服务端始终绑定到 `127.0.0.1`，不暴露公网
- Bridge 在中间层处理平台特定的认证/轮询/事件
- 所有 bridge 共享 `bridge-core` 的会话管理、消息去重、SSE 解析

### 可借鉴的设计

go-on 已经通过 `agent_servers` 支持 ACP 协议，理论上有代理能力。但如果要做消息网桥，应该借鉴 CodeWhale 的 **bridge-core 模式**——把通用逻辑抽取为共享层，平台特定适配器作为薄壳。

## 7. Skills 系统对比

| 特性 | CodeWhale | go-on |
|------|-----------|-------|
| **SKILL.md 加载** | ✅ 多根目录发现 | ✅ 自定义路径 |
| **来源追溯** | ✅ `.installed-from` v2 JSON schema（content_digest + spec） | ❌ 无 |
| **摘要验证** | ✅ `content_digest` 是 bounded package tree hash | ❌ 无 |
| **冲突检测** | ✅ Active/Shadowed/Duplicate/Conflict 四状态 | ❌ 无 |
| **多根优先级** | ✅ SkillRootCatalog 单源排序 | ❌ 无 |
| **变异控制器** | ✅ 唯一写入者，TOCTOU 安全的安装模式 | ❌ 无 |
| **TUI 管理** | ✅ `/skills inspect/install/update/uninstall/trust` | ❌ 无 |
| **只读兼容** | ✅ `.claude/skills/` `.cursor/skills/` `.opencode/skills/` | ❌ 无 |
| **审计模式** | ✅ `.codex/skills` 只审计不加载 | ❌ 无 |
| **信任标记** | ✅ 摘要绑定的 .trusted（advisory） | ❌ 无 |
| **内置技能数量** | 文档有但需核实 | 18 个 |

1. **`.installed-from` provenance** — 每个 skill 安装时记录来源和摘要
2. **兼容只读路径** — 读取 `.claude/skills/` 等已存在的 skill 目录

4. **冲突检测** — Active/Shadowed/Duplicate/Conflict 状态机

## 8. 治理：Constitution vs PUA 规则

| 维度 | CodeWhale Constitution | go-on PUA Rules |
|------|-----------------------|-----------------|
| **本质** | 权威排序 + 不变式约束 | 行为护栏 + 升级协议 |
| **层次** | 4 层（bundled/user-global/repo-local/AGENTS.md） | 2 层（RULES 运行时加载 + .github bootstrap） |
| **运行时影响** | **不改变**权限策略（独立于 sandbox/shell/network 配置） | **直接改变** agent 行为（红线/升级/冰山区规则） |
| **强制执行** | `protected_invariants` 编译为写前钩子（机械性 write holds） | PUA 规则引擎在运行时注入 prompt |
| **绕过** | 不可绕过（mode 不能关闭 protected_invariants） | 可通过 config.reload 绕过 |
| **升级机制** | `escalate_when` 列表（特定行为触发升级） | L0-L4 Pressure Escalation（基于失败次数） |
| **质量检查** | `verification_policy`（发布前验证） | Quality Compass（交付前 5 项检查） |
| **设计哲学** | "告诉 agent 什么更重要" | "强制 agent 按标准执行" |

**分析**：两者是互补而非竞争关系。

CodeWhale 的 Constitution 擅长：
- 项目级别的权威排序（"当前用户请求 > 活代码 > 记忆"）
- 机械性的不变式保护（某些文件不可写、某些操作不可执行）
- 不会侵入运行时配置

go-on 的 PUA 规则擅长：
- 主动的 agent 行为纠偏（"不要猜测事实"、"提供测试证据"）
- 分级升级（失败越多，要求越严格）
- 交付前质量门禁

**可借鉴的设计**：
1. **`protected_invariants` + 写前钩子** — 在工具执行前检查文件匹配规则，比 PUA 规则更底层、不可绕过
2. **权威排序** — 当多个规则冲突时，Constitution 提供明确的优先级：当前请求 > 代码 > 记忆

## 9. Modes / 权限系统对比

| 维度 | CodeWhale | go-on |
|------|-----------|-------|
| **Modes** | Plan（只读）/ Act（读写+审批）/ Operate（同 Act，调度侧重） | 5 种 Chat Modes（Ask/Plan/Edit/SafeGuard/FullAuto） |
| **权限姿态** | suggest（审批）/ auto（自动）/ bypass（完全访问）/ never（阻止） | 模式级工具限制 |
| **模式切换** | Tab 键循环；Shift+Tab 循环姿态 | `/mode` 命令 |
| **Workflow 覆盖** | Operate 模式下优先走 Fleet | 无 |
| **模式与权限解耦** | ✅ 模式和权限是正交的两个维度 | ❌ 模式和权限绑定在一起 |

**分析**：CodeWhale 将**模式（mode）**和**权限姿态（posture）**解耦为两个独立维度，这是一个更灵活的设计。go-on 的 5 种 mode 包含了权限逻辑，但 mode 切换同时改变行为和权限，不够灵活。

**可借鉴的设计**：
1. **Mode/Posture 解耦** — 将"做什么"（模式）和"怎么批准"（权限姿态）拆分为两个独立设置
2. **只读模式** — Plan mode 禁止所有写操作，适合审查场景

## 10. Sandbox 沙箱对比

| 维度 | CodeWhale | go-on |
|------|-----------|-------|
| **macOS** | Seatbelt (`sandbox-exec`) | 依赖 OS 级限制 |
| **Linux** | Bubblewrap（opt-in）/ process hardening（默认） | gVisor (runsc) 容器级 |
| **Windows** | 无 | 无 |
| **外部沙箱** | OpenSandbox 兼容 | 无 |
| **沙箱模式** | read-only / workspace-write / danger-full-access / external-sandbox | 进程级隔离 |
| **隔离强度** | Bubblewrap：mount namespace（中等） | gVisor：完整内核隔离（高） |
| **诚实报告** | ✅ 明确标注限制和回退路径 | 未明确文档化 |
| **拒绝归因** | 保守：无法确定时不归因于沙箱 | 未明确 |

**分析**：go-on 的 gVisor 集成提供了更强的隔离，但 CodeWhale 在 macOS 和 Linux process hardening 方面更全面。CodeWhale 的"诚实报告"哲学（明确文档化限制和回退路径）值得 go-on 借鉴。

## 12. go-on 已领先的领域（须保持）

| 领域 | go-on 优势 | CodeWhale 状态 |

## 综合结论

CodeWhale 和 go-on 虽然都是 Rust AI agent 编排系统，但定位不同：

- **CodeWhale** 是一个**编码助手运行时**，强调单一运行时跨交互面、workflow 编排、持久化执行（Fleet）、消息网桥、技能管理。它更注重"让 agent 好用地工作"。
- **go-on** 是一个**AI agent 代理/编排平台**，强调 14-bus 架构、PUA 规则引擎、治理层（RBAC/审计/租户）、多协议支持。它更注重"安全地编排 agent"。

### 最值得 go-on 借鉴的 3 件事

1. **Sub-agent 系统增强** — CodeWhale 的子代理角色分类、token 预算、上下文 fork、心跳超时是 go-on 目前完全缺失的能力。这是最大差距。
2. **Skills provenance + digest** — 低工作量、高安全性收益。加 `.installed-from` 和 `content_digest` 就能大幅提升 skill 系统的可信度。
3. **Mode/Posture 解耦** — 将权限审批从 mode 中拆出，提升模式灵活性，不需要大改架构。

### 需要后续确认的债务

- go-on 的 `block_in_place + block_on` 清零状态（principle.md 第 23-24 条）
- go-on 的测试全面审计（无 ignore/fail）
- CodeWhale 的 18 个 crate 如何在单一二进制中组合（对比 go-on 的 4 个 profile）
