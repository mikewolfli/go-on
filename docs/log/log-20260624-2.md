## Round 6 — Branch Link Deep Scan (2026-06-24 2nd Pass)

### Issues Found & Fixed

#### B1. Plugin::on_error default returns error (stub anti-pattern)
- **File**: `src/orchestration/plugin_system.rs:141-145`
- **Problem**: Default `on_error()` implementation returned `Err(...)` — any plugin without explicit override would FAIL when `on_error` was called. Violation of principle #9 (no stubs/placeholders).
- **Fix**: Changed to log a warning + return `Ok(())`. Errors are logged, never fail the caller.

#### B2. set_skill_registry silently drops duplicate calls
- **File**: `src/orchestration/tool/mod.rs:42-44`
- **Problem**: `OnceLock::set()` returns `Err` on second call but `let _ = ...` discarded it silently.
- **Fix**: Added explicit check that logs a warning on duplicate set.

#### B3. SkillDiscovery initialized but never connected to skill-finder
- **File**: `src/acp/impl/request/tools_pack.rs:456-532`
- **Problem**: `SKILL_DISCOVERY` global and `SkillDiscovery` engine were fully initialized at startup (`init_skill_discovery`), but the `skill-finder` handler had its own inline `Vec<Value>` implementation that never used the discovery engine. The entire `SkillIndex` + tokenizer + cache was dead code in production.
- **Fix**: Replaced the inline implementation with a call to `SkillDiscovery::discover()`, which uses proper token-based similarity scoring, runtime stats enrichment, and result caching.

#### B4. Dead tests removed
- **File**: `src/acp/impl/request/tools_pack.rs` (tests)
- **Problem**: 2 tests (`skill_finder_empty_query_returns_zero_score`, `skill_finder_direct_match_gets_boost`) tested the now-removed inline matching logic.
- **Fix**: Removed the dead tests.

## Round 7 — Ultra-Deep Branch Link + Blocking Pattern Scan (2026-06-24 3rd Pass)

### Issues Found & Fixed

#### C1. Tool dispatch blocks tokio runtime thread
- **File**: `src/acp/impl/request/tools_pack.rs:599-611`
- **Problem**: `tool.run()` called synchronously inside `async fn execute_mcp_tool_call`. Tools like `shell_exec` (up to 60s) and `cargo_test` (up to 300s) would block the tokio worker thread for their entire duration.
- **Fix**: Wrapped in `tokio::task::spawn_blocking()` so the tool runs on a blocking thread pool.

#### C2. Tool lock blocking acquisition in hot path
- **File**: `src/orchestration/tool/mod.rs:1531-1588`
- **Problem**: `ReadFileTool` and `WriteFileTool` called `tool_lock_manager().acquire()` which uses `std::thread::sleep()` in its exponential backoff loop. When called from async context (via execute_mcp_tool_call), this blocks the tokio worker thread while waiting for the lock.
- **Fix**: Changed both tools to use `try_acquire()` — non-blocking. Read proceeds without lock if contended (OS provides coherence for concurrent reads). Write returns a transient error that the TAO loop can retry.

### Verification

| Check | Before | After |
|-------|--------|-------|
| MCP tool dispatch blocking | `tool.run()` blocks tokio thread | `spawn_blocking` wraps tool execution |
| ReadFileTool lock blocking | `acquire()` with `thread::sleep` | `try_acquire()` — zero blocking |
| WriteFileTool lock blocking | `acquire()` with `thread::sleep` | `try_acquire()` — returns immediately or fails |

#### C3. SkillExecuteTool creates new tokio runtime every call
- **File**: `src/orchestration/tool/mod.rs:2018-2021`
- **Problem**: `SkillExecuteTool` created a new `tokio::runtime::Builder` on every invocation — expensive allocation of thread-local storage, I/O driver, and timer heap.
- **Fix**: Replaced with lazily-initialized `static SKILL_RUNTIME: OnceLock<Runtime>` — shared across all skill executions.
