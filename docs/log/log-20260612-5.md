## Round 1 — CRITICAL & HIGH 修复 (完成)

### R1-1 ✅ [CRITICAL] mcp_http 模式缺少 ACP Server 接线

**问题**: `transport_factory.rs` 中 `mcp_http` 分支创建 `McpHttpServer::new()` 时未传递 ACP Server 引用，导致所有 ACP 依赖的 MCP HTTP 操作（workflow, prompts, templates, RBAC, CORS, rate limiting）全部失效。
**修复**: 在 `mcp_http` 分支中创建 `AcpServer` 并通过 `McpHttpServer::new_with_acp()` 传递。
**文件**: `src/acp/transport_factory.rs`
**验证**: `cargo check --features local` ✅

### R1-2 ✅ [CRITICAL] OrchestrationProvider 假实现修复

**问题**: `DefaultOrchestrationProvider::register_skill()` 仅记录日志，不实际存储 skill；`record_capability_execution()` 同样为空操作。这是"永动机no-op"反模式。
**修复**: 
- 为 `DefaultOrchestrationProvider` 添加内部 `skills: Mutex<HashMap<...>>` 和 `stats: Mutex<HashMap<...>>` 存储
- `register_skill` 实际插入 HashMap
- `record_capability_execution` 实际追踪执行统计
- 新增 `capability_stats()` 方法用于查询统计
- 同步修复 `OrchestrationProviderImpl` 实现
**文件**: `src/core/provider.rs`, `src/orchestration/provider_impl.rs`, `src/core/bootstrap.rs`
**验证**: `cargo check --features local` ✅ | 移除 `#[derive(Default)]` 改为手动实现

### R1-3 ✅ [CRITICAL] Consensus 互斥锁中毒无法恢复

**问题**: `hub.rs` 中 `consensus_vote_on()` 在 `GLOBAL_CONSENSUS` 锁中毒时仅返回 `(approve, 0.3)` 并从不解锁，导致永久共识失败。
**修复**: 改用 `.unwrap_or_else(|poisoned| { poisoned.into_inner() })` 模式恢复中毒的锁。
**文件**: `src/intelligence/hub.rs`
**验证**: `cargo check` ✅ | 与项目内其他地方的恢复模式一致

### R1-4 ✅ [HIGH] DeepSeekVoter API 故障时 Fail-Open

**问题**: `DeepSeekVoter::vote()` 在 HTTP 请求错误时返回 `approves: true, confidence: 0.2`，即"故障即批准"反模式。网络分区或 API 中断会导致所有提议被静默批准。
**修复**: 改为 `approves: false, confidence: 0.0` + `tracing::error!` 日志，实现"故障即拒绝"安全模式。
**文件**: `src/intelligence/voter_impls.rs`
**验证**: `cargo check` ✅

### R1-5 ✅ [HIGH] gRPC _timeout_s 参数完全忽略

**问题**: `call_execute_remote()` 和 `call_health_check()` 接受 `_timeout_s: u64` 参数但从不在 `tokio::time::timeout` 中使用。调用者传入的 `default_timeout_s` 零效果。
**修复**: 将 HTTP 调用包装在 `tokio::time::timeout(Duration::from_secs(timeout_s), future)` 中，实现真正的每请求超时控制。
**文件**: `src/protocol/grpc.rs`
**验证**: `cargo check --features full` ✅

### R1-6 ✅ [HIGH] temp_env 死特征标志

**问题**: `temp_env` 特征标志在所有4个 profile 中启用，但 src/ 中没有任何 `#[cfg(feature = "temp_env")]` 正向门控。仅有的使用是 `#[cfg(not(feature = "temp_env"))]` 测试兼容模块。启用该特征零效果。
**修复**: 从所有4个 profile (local, simple-server, multi-users-server, full) 中移除 `temp_env`。保留特征定义以保持向后兼容。
**文件**: `Cargo.toml`
**验证**: 所有4个 profile 编译通过 ✅

### R1-7 ✅ [HIGH] SemanticResponseCache 后台清理从未启动

**问题**: `SemanticResponseCache` 有 `start_background_cleanup()` 方法但从未在生产中调用。过期条目仅在被 `get()` 时惰性驱逐，在低命中场景下导致无限内存增长。
**修复**: 在 `server_builder.rs` 的 `wire_server()` 中添加后台清理启动调用。
**文件**: `src/acp/impl/runtime/server_builder.rs`
**验证**: `cargo check` ✅

## Round 2 — MEDIUM 修复 (完成)

### R2-1 ✅ [MEDIUM] FaultConsensus 法定人数死锁

**问题**: `FaultConsensus::evaluate()` 要求 `unhealthy >= quorum_size(3)`，当投票者少于3时，即使100%报告不健康也永远无法声明故障。
**修复**: 添加 `effective_quorum = quorum_size.min(total.max(1))` 上限。
**文件**: `src/resilience/hyper_resilience.rs`
**验证**: `cargo check` ✅

### R2-2 ✅ [MEDIUM] 内存持久化 TOCTOU 竞争条件

**问题**: `summarize_hot_entries()` 在 `hot_entries()` 克隆和 `hot.clear()` 之间不持有锁，导致在此期间添加的条目被静默丢失。
**修复**: 在整个读取-检查-摘要-替换操作期间持有热缓存锁。
**文件**: `src/memory/memory_persistence.rs`
**验证**: `cargo check` ✅

### R2-3 ✅ [MEDIUM] 进化循环无操作 `let _ = &self`

**问题**: `with_default_trigger_sources()` 中 `let _ = &self; // borrow so we can chain` 是无操作。方法接收 `self` 按值传递，借用立即丢弃。
**修复**: 移除该行。
**文件**: `src/orchestration/self_evolution/evolution_loop/mod.rs`
**验证**: `cargo check` ✅

### R2-4 ✅ [MEDIUM] 协商者文档与代码不一致

**问题**: `negotiate()` 的文档注释声称 "Fails fast with a clear error"，但实际行为是默默返回默认模式。
**修复**: 更新文档以匹配实际行为：未识别的提示被记录且返回服务器活动模式，`auto_detected = false`。
**文件**: `src/protocol/negotiator.rs`
**验证**: 文档现在与代码匹配 ✅

### R2-5 ✅ [LOW] Vosk 音频处理器未使用参数警告

**问题**: `transcribe_vosk()` 中 `audio: &[u8]` 参数在 `full` profile 下产生未使用变量警告。
**修复**: 重命名为 `_audio`。
**文件**: `src/multimodal/audio_processor.rs`
**验证**: `cargo check --no-default-features --features full` -- 零警告 ✅
