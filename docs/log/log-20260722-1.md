## 2. 多轮交叉验真结论

本轮不采信旧日志“已完成”自证，直接对比真实代码路径后，确认以下结论：

### 2.1 已真实存在

- `session/config/set`、`session/config/get`、`session/delete` 方法路由已存在。
- `session/prompt` 已具备 `StreamObserver` 桥接，能把文本/思维 chunk 通过 `session/update` 发给 ACP 客户端。
- GUI 自身的 `chat.stream.tool_approval` + `tool.approve` 路径是通的。

### 2.2 旧日志未说清、实际仍有缺口

- **ACP 标准审批链未闭环**：
  - go-on 原先只发自定义 `tool_approval` 流事件；
  - `session/request_permission` 仅保存 `optionId`，并未把批准结果真正回接到治理层；
  - 因此在 Zed agent servers 模式下，审批协议与 Zed 原生 ACP 授权流不完全对齐。
- **config option 当前值返回不准确**：
  - `build_model_config_options()` 原先固定把 `current_value` 设为 `auto`；
  - `session/set_config_option` 回包固定 `config_options: []`；
  - 这会导致 ACP 客户端拿不到当前选中的真实模型。

## 3. 本轮已完成修复

### 3.1 ACP 标准权限请求出站接线

修改文件：
- `src/acp/impl/request/protocol_pack/mod.rs`
- `src/acp/impl/request/protocol_pack/session.rs`

修复内容：
- 新增 `PendingPermissionRequest` 状态，按 `session_id` 记录当前待确认工具请求。
- 在 `session/prompt` 的流式桥接中，检测到 `tool_approval` 帧后：
  - 先 flush 已累积的 `agent_thought_chunk` / `agent_message_chunk`；
  - 再发出标准 ACP `SessionUpdate::PermissionRequest`；
  - 同时记录待处理工具审批上下文。

效果：
- go-on 现在不再只依赖自定义 `chat.stream.tool_approval` 才能表达审批需求；
- ACP 客户端至少能收到标准 `permission_request` 语义事件。

### 3.2 ACP 权限响应入站回接治理层

修改文件：
- `src/acp/impl/request/protocol_pack/session.rs`

修复内容：
- `session/request_permission` 现在不再只是写入 `optionId`；
- 当收到 `approve` 时，调用 `harness_bus.evaluator.approve_tool()`；
- 当收到 `deny` 时，调用 `harness_bus.evaluator.revoke_tool_approval()`；
- 消费并清理对应 `PendingPermissionRequest`。

效果：
- ACP 协议返回的审批选择现在能够真实影响治理层工具许可状态；
- 避免“前端已批准，但后端治理状态没有变化”的假闭环。

补充说明：
- 这一条当前仍基于 go-on 已有的 `session/request_permission` handler 语义成立；
- 但经过本轮继续核对 Zed 源码确认，Zed 原生 ACP 的 `session/request_permission` 实际是**agent -> client 的 JSON-RPC request**，不是简单的 client -> agent request 回调；
- 因此 go-on 还不能声称“已完整对齐 Zed 原生授权请求方向”。

### 3.3 session config 当前值真实回传

修改文件：
- `src/acp/impl/request/protocol_pack/mod.rs`
- `src/acp/impl/request/protocol_pack/session.rs`

修复内容：
- `build_model_config_options(server, current_model)` 改为接收当前模型值；
- `session/load` / `session/resume` 从 session 状态里恢复当前 model；
- `session/set_config_option` 在设置 `model` 后，返回真实 `currentValue`；
- 同时发出标准 `SessionUpdate::ConfigOptionUpdate`。

效果：
- ACP 客户端能拿到当前真实模型，而不是永远看到 `auto`；
- 这对 Zed 的 config option 同步和状态展示是必要修复。

### 3.4 删除/关闭会话时清理 pending 审批状态

修改文件：
- `src/acp/impl/request/protocol_pack/session.rs`

修复内容：
- `session/close`
- `session/delete`

现在都会清理 `acp_pending_permission_requests()`。

效果：
- 避免会话关闭后残留待审批状态，影响后续请求链路通畅性。

### 3.5 PermissionOption schema 向 Zed 当前协议对齐

修改文件：
- `src/schema/client.rs`
- `src/acp/impl/request/protocol_pack/session.rs`

修复内容：
- 将本地 `PermissionOption` 从旧的 `id/label` 语义升级为与 Zed 当前 ACP 更接近的 `optionId/name/kind`；
- 保留对旧字段名的反序列化兼容（`id`、`label` alias），避免破坏现有链路；
- `session/prompt` 发出的审批选项现在带 `AllowOnce` / `RejectOnce` 语义。

效果：
- go-on 发给 Zed 的审批选项结构更接近其当前客户端预期；
- 这是低风险、高收益的协议兼容增量，不依赖尚未实现的 outbound request/response 骨架。

### 3.6 stdio ACP client response 分流骨架落地

修改文件：
- `src/acp/server.rs`
- `src/acp/impl/runtime.rs`

修复内容：
- 在 stdio ACP 循环中先按原始 JSON 分辨 request 与 response；
- 新增 pending client response registry 的最小骨架；
- 当收到带 `id + result/error` 的 JSON-RPC message 时，可匹配并回收对应 pending response；
- 增加窄测试验证 pending response 能被正确送达。

效果：
- go-on 不再是“只能消费 request、完全不识别 client response”的单向 ACP stdio 实现；
- 这为下一轮真正外发 `session/request_permission` JSON-RPC request 提供了必要底座；
- 当前仍只是底座，不等同于 Zed 原生授权链已闭环。

## 5. 与 Zed 对齐后的现状评估

### 5.1 本轮已对齐并提升的点

- ACP `session/prompt` 的会话流式体验更接近 Zed 的 `session/update` 预期。
- ACP `session/config` 的当前模型状态同步更准确。
- ACP 权限应答不再是空写入，已经回接到治理许可状态。
- ACP 审批选项字段形状更接近 Zed 当前协议。
- stdio ACP 已具备 client response 分流基础能力。
- 清理逻辑更完整，不会因为 pending 审批状态污染链路。

### 5.2 仍未完全闭环的点

以下问题**本轮没有谎报为已完成**：

1. **真正的 Zed 原生授权请求链**尚未完整落地。
  - 本轮继续深挖后确认：Zed 的 `session/request_permission` 是 server 发给 client 的 JSON-RPC request，client 返回 response；
  - go-on 当前已经具备 pending response registry 和 inbound response 分流骨架；
  - 但 outbound `session/request_permission` request 发送、response 解析、tool gate 接线仍未完成；
  - 因此本轮没有把“工具执行前等待批准”硬接进主链，避免在真实 Zed 模式下引入 300 秒超时卡死；
  - 当前真实状态是：保留审批语义通知、治理状态回接、config 状态修复，但**未宣称已达到 Zed 原生 request/response 级授权闭环**。

2. **favorite_config_option_values** 仍未实现。
   - Zed 平台层明确支持配置值收藏；
   - go-on 当前仍无对应 schema 元数据与 toggle 接口；
   - 这会影响 Zed 中的配置偏好体验，但不影响主链路通畅。

## 6. 风险控制判断

本轮改动遵循“不断链、不降速、最小改动面”：

- 没有改动主工具执行器的大结构。
- 没有改变 GUI 既有 `tool.approve` 路径。
- 只在 ACP 协议桥接层补标准语义和状态清理。
- 验证范围限定在 session 相关协议路径，避免无关面回归。

本轮没有做“看起来实现了”的假修复，而是把两条真实缺口先补成了**可验证的协议闭环增量**：
