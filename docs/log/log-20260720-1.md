## Area 1: CLI Chat — Critical Gaps

**File:** `go-on/src/cli/chat.rs` (1240-line `run_terminal_chat`, 344-line `run_agent_with_tools`)

### 1.1 No `/mode` Command (only `/model` exists)

The CLI chat banner (lines 276-281) lists available commands:

```
Commands: /help /quit /clear /save /load /cost /compact
 /diff /commit /plan /model /models /retry /context /tools /skills
 /stats /find_path
```

There is **no `/mode` command**. The `/model` command (line 1060-1085) switches the *agent*, but there is no equivalent for switching the *mode* (ask/plan/edit/safeguard/full_auto). The mode is implicitly always "edit" behavior via `run_agent_with_tools`. agent=edit.

Code evidence: line 1060-1085 is the only command handler for `model`, and there is no `mode` handler anywhere.

### 1.2 No ModeRuntime Integration

`run_terminal_chat` calls `run_agent_with_tools` directly (line 1159) without any mode constraints:

```rust
// chat.rs line 1155-1159
let principles = build_cli_principles();
match run_agent_with_tools(&current_agent, &mut messages, principles).await {
```

There is **zero usage** of `resolve_mode_runtime`, `GenericModeRuntime`, or any `ModeRuntime` trait in the CLI chat. Every message runs through the same unrestricted agent-tool loop.

### 1.3 No Mode-Aware Tool Execution

`run_agent_with_tools` (line 1248-1592) has no concept of:

- **`allowed_tools()`** — Every registered tool can be called. There is no per-mode tool filter.
- **`max_tool_calls()`** — There's a `MAX_CONCURRENT_TOOLS` constant (line 50, set to 6) but this limits *concurrency*, not total calls per turn. In `ModeRuntime`, Edit allows 20, FullAuto allows 50, Ask allows 0.
- **`user_approval_required()`** — Tools execute immediately with no approval step (lines 1400-1453). There is no approval gate for Edit mode.
- **`is_high_risk_operation()`** — No risk assessment before tool execution.

### 1.4 No SafeGuard Risk Score Display

SafeGuard mode's `compute_risk_score()` and `evaluate_degradation()` (defined in `mode.rs`) are never called from the CLI. There is no display of risk scores, degradation policies, or any SafeGuard-specific UX.

### 1.5 No FullAuto Execution Step Visibility

FullAuto's `FullAutoFlow::run()` produces an `AutoExecutionReport` with `ExecutionStep` entries, but the CLI never calls `FullAutoFlow`. All messages go through `run_agent_with_tools` → `agent.chat()` → tool loop, which is the standard "Edit" path.

### 1.6 Session Persistence Doesn't Include Mode

`ChatSession` struct (lines 170-173):

```rust
struct ChatSession {
    messages: Vec<Message>,
    agent_name: String,
}
```

No `mode` field. Sessions saved via `/save` and loaded via `/load` lose the mode context entirely. On load (lines 416-464), only `agent_name` is restored.

### 1.7 `/plan` Command Is Standalone

The `/plan` command (lines 830-881) calls `chat_simple()` directly to generate a text plan from conversation context. It does **not** use the `Plan` mode from `ModeRuntime`, which has specific constraints (`allowed_tools: vec!["read_file", "search_files"]`, `max_tool_calls: 3`, `use_chat: true`).

## Area 3: Mode Runtime — Design Gaps

**File:** `go-on/src/orchestration/mode.rs` (877 lines total)

### 3.1 FullAuto: `use_chat()` Returns `false`

Lines 497-499:

```rust
fn use_chat(&self) -> bool {
    matches!(self.kind, ModeKind::Ask | ModeKind::Plan)
}
```

This means `FullAuto` and `SafeGuard` modes use `Agent::run_task()` instead of `Agent::chat()`. However, the `FullAutoFlow::run()` method (in `full_auto/executor.rs`) expects to be called directly with a task string, not through the `ModeRuntime::run()` trait interface. The `FullAutoFlow` is a separate orchestration system from `BaseModeRuntime::run()`.

The `BaseModeRuntime::run()` method (line 244) dispatches to `execute_agent_run_task_async()` for non-chat modes, which calls `agent.run_task()`. But `run_task()` for FullAuto should use `FullAutoFlow`, not the standard agent task execution. This creates a **tier-2 gap**: the mode strategy says "use run_task" but FullAutoFlow is not wired into that path.

### 3.2 Edit: `user_approval_required()` Returns `true` but Frontend Controls Approval

Line 816-818:

```rust
fn user_approval_required(&self) -> bool {
    matches!(self.kind, ModeKind::Edit)
}
```

This returns `true` for Edit mode, but there is **no mechanism** to actually communicate the approval requirement to the frontend. The `pre_execute` method's `is_high_risk_operation()` check (line 557) only blocks for high-risk keywords like "delete", "remove", "drop", "truncate" — it does not gate *all* Edit mode operations.

The design intent is that **every** Edit mode tool call requires user approval, but the code only gates high-risk operations in `pre_execute()`.

### 3.3 SafeGuard: `allowed_tools()` Is Static, Should Be Dynamic

Lines 792-804:

```rust
fn allowed_tools(&self) -> Vec<String> {
    match self.kind {
        ModeKind::Ask => vec![],
        ModeKind::Plan => vec!["read_file".to_string(), "search_files".to_string()],
        ModeKind::Edit | ModeKind::FullAuto | ModeKind::SafeGuard => vec![
            "read_file".to_string(),
            "search_files".to_string(),
            "apply_patch".to_string(),
            "run_tests".to_string(),
            "inspect_git_diff".to_string(),
        ],
    }
}
```

For SafeGuard mode, the allowed tools should change dynamically based on the `degrade_policy`:
- `Block` → `vec![]`
- `ReadOnly` → `vec!["read_file", "search_files", "inspect_git_diff"]`
- `AllowWithAudit` → all tools, but with extra audit
- `ConfirmRequired` → all tools, with approval gate

Currently, `allowed_tools()` ignores `degrade_policy` entirely.

### 3.4 `evaluate_degradation()` — Low Risk (<0.4) Returns `AllowWithAudit`

Lines 471-481:

```rust
pub fn evaluate_degradation(&self, risk_score: f64) -> AutoDegradePolicy {
    if risk_score > 0.95 {
        AutoDegradePolicy::Block
    } else if risk_score > 0.70 {
        AutoDegradePolicy::AllowWithAudit
    } else if risk_score > 0.40 {
        AutoDegradePolicy::ReadOnly
    } else {
        AutoDegradePolicy::AllowWithAudit  // <-- LOW risk gets AllowWithAudit?
    }
}
```

The docstring says:
- `< 0.4` = low risk (safe operations) → should be `AllowWithAudit` or no degradation
- `0.4–0.7` = medium risk → `ReadOnly`
- `0.7–0.95` = high risk → `AllowWithAudit`
- `> 0.95` = extreme → `Block`

The issue: **low risk** (<0.4) returns `AllowWithAudit`, which is the same as **high risk** (0.7-0.95). Low risk should return the *least* restrictive policy — either no special policy or a very mild audit. The `AllowWithAudit` for low risk creates unnecessary audit noise.

Additionally, the `evaluate_degradation()` in `pre_execute` is called differently: the inline logic (lines 585-593) evaluates `allow_degrate` first, then falls back to hardcoded thresholds. This duplicates the logic.

### 3.5 Edit Should Require Approval "For All" But Code Only Requires for High-Risk

The `pre_execute` for Edit (lines 556-581) only short-circuits when `is_high_risk_operation()` returns true. But the design says Edit mode should require user approval for *all* operations. The `user_approval_required()` returns true but nothing actually blocks non-high-risk Edit operations from executing.

## Area 4: Server Mode (ACP stdio/SSE) — Zed Integration Gaps

**Files:** `go-on/src/acp/impl/chat.rs`, `chat_phases.rs`, `streaming.rs`

### 4.1 SSE Events Flow But Tool Approval Events Not Properly Streamed

The SSE event stream (handled in `chat_phases.rs` via `act_phase` and `run_mode_runtime_and_multi_agent`) calls `emit_stream_chunk`, `emit_stream_done`, `emit_phase_event`, etc. But there is **no `tool_approval` event type** in the SSE specification.

The GUI SSE parser (in `runtime.rs` lines 622-850) handles these event types:
- `chunk` / `""` — text tokens
- `telemetry` — token economy
- `sub_agent` — sub-agent events
- `command` — command output
- `result` / `done` — completion
- `error` — errors

There is **no `tool_approval` event type**. When Edit mode needs user approval, the mode runtime returns `AgentTaskResult` with `status: "pending_approval"`, but this result is not translated into a streamed SSE event — it's buried in the final response.

### 4.2 No `tool_approval` in ACP Protocol Events

The ACP protocol's governance layer (`acp/helpers/governance/tool_governance.rs`, `policy.rs`, `review_gate.rs`) handles tool approval at the policy level, but there is no mechanism to pause the SSE stream, emit a `tool_approval` event, wait for a user response, and resume.

### 4.3 ACP Events Lack Mode Metadata

The `StreamEventMeta` struct (in `streaming.rs`) carries:
- `agent_name`
- `phase_name`
- `trace_id`

But does **not** carry:
- `mode` — which mode (ask/plan/edit/safeguard/full_auto) produced this event
- `risk_score` — SafeGuard risk assessment
- `degrade_policy` — current degradation policy
- `tools_allowed` — what tools the mode permits

The GUI has no way to display mode-specific UI (risk badges, approval buttons, tool restrictions) because the events don't carry this metadata.

## Area 5: FullAuto — Visibility & Integration Gaps

**Files:** `go-on/src/orchestration/full_auto/mod.rs`, `executor.rs`

### 5.1 `FullAutoFlow` Exists But Not Used from CLI/GUI

`FullAutoFlow` is a sophisticated autonomous skill-execution pipeline (discover → prepare → execute → report) but it is **never instantiated** in the CLI or GUI paths. The CLI always calls `run_agent_with_tools()`. The GUI sends messages to `/chat/stream` which goes through `ChatPipeline` → `act_phase` → autonomy loop, bypassing `FullAutoFlow` entirely.

The `BaseModeRuntime::run()` for `FullAuto` mode calls `agent.run_task()` instead of `FullAutoFlow::run()`. There is no bridge between the mode runtime trait and the FullAutoFlow pipeline.

### 5.2 No Visibility into Sub-Agent Execution from CLI

`FullAutoFlow::run()` produces `ExecutionStep` entries in its report, but these are never surfaced to the CLI user. The CLI has no sub-agent panel, no progress indicators, no step-by-step execution log.

### 5.3 Steps/Progress Not Streamed to GUI

The `FullAutoFlow::run()` method runs synchronously (within its async context) and returns a complete `AutoExecutionReport`. It does not emit incremental progress events that could be streamed to the GUI. The GUI's `SubAgentEvent` and `CommandOutput` SSE event types exist but `FullAutoFlow` doesn't emit them.

In `streaming.rs`, add a new emitter function:

```rust
/// Emit a tool_approval event to the SSE stream, pausing execution
/// until the user approves or denies the tool call.
pub(crate) async fn emit_tool_approval_event(
    server: &AcpServer,
    observer: Option<&StreamObserver>,
    meta: StreamEventMeta<'_>,
    tool_name: &str,
    tool_args: &Value,
    mode: &str,
    risk_score: Option<f64>,
) -> Result<StreamFrame> {
    let Some(observer) = observer else {
        return Ok(StreamFrame { event: "tool_approval", payload: json!({}), status: None });
    };

    let payload = json!({
        "tool_name": tool_name,
        "tool_args": tool_args,
        "mode": mode,
        "risk_score": risk_score,
        "status": "pending",
    });

    observer.sender.send(StreamFrame {
        event: "tool_approval",
        payload,
        status: Some("pending"),
    }).await.map_err(|_| anyhow::anyhow!("stream closed"))?;

    // Wait for approval response via a oneshot channel
    let rx = observer.approval_tx.as_ref().map(|tx| tx.subscribe());
    if let Some(mut rx) = rx {
        tokio::select! {
            result = rx.recv() => {
                match result {
                    Ok(value) if value.get("approved").and_then(|v| v.as_bool()).unwrap_or(false) => {
                        Ok(StreamFrame {
                            event: "tool_approval",
                            payload: json!({"status": "approved", "tool_name": tool_name}),
                            status: Some("approved"),
                        })
                    }
                    _ => {
                        Ok(StreamFrame {
                            event: "tool_approval",
                            payload: json!({"status": "denied", "tool_name": tool_name}),
                            status: Some("denied"),
                        })
                    }
                }
            }
            _ = tokio::time::sleep(Duration::from_secs(300)) => {
                Ok(StreamFrame {
                    event: "tool_approval",
                    payload: json!({"status": "timeout", "tool_name": tool_name}),
                    status: Some("timeout"),
                })
            }
        }
    } else {
        Ok(StreamFrame {
            event: "tool_approval",
            payload: json!({"status": "no_observer", "tool_name": tool_name}),
            status: Some("no_observer"),
        })
    }
}
```
