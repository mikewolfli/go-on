## Finding 1: `#[allow(dead_code)]` on `SessionCompressor` impl 🔴

**File**: `src/orchestration/session_compressor.rs:124-127`

```rust
#[allow(
    dead_code,
    reason = "F-GAP reserved — session compression not yet wired into pipeline"
)]
impl SessionCompressor {
```

**Problem**: The previous scan (log-20260624-3.md) claimed **zero** `#[allow(dead_code)]` in production code. This suppression was missed. The entire `impl SessionCompressor` block (all ~300 lines of methods) is protected from dead code warnings.

**Impact**: All public methods on `SessionCompressor` receive `#[allow(dead_code)]` — any method could become dead without detection. This suppresses the compiler from telling us which methods are actually unused.

**Recommendation**: Either wire the session compressor into the pipeline, or suppress only the specific methods that are actually called externally. Better: remove the blanket `#[allow(dead_code)]` and fix or remove unused methods.

## Finding 2: `update_incremental` is a no-op stub 🔴

**File**: `src/orchestration/session_compressor.rs:316-322`

```rust
pub fn update_incremental(&self, compressed_count: usize, summary: &str) {
    // Since Self is behind &, we use interior mutability conceptually.
    // In practice the caller manages state, but for thread-safe mutation, the IncrementalState is cloned and reassigned.
    let _ = compressed_count;
    let _ = summary;
}
```

**Problem**: This method accepts two parameters and discards both without performing any work. The comment explains the design choice (caller manages state via `with_incremental_state` / `advance_incremental`), but the side effect is that `inject_compressed_context` (line 312) calls `self.update_incremental(...)` believing state is being persisted, when in fact nothing happens.

**Impact**: The incremental compression feature is silently broken. After `inject_compressed_context`, the `IncrementalState` inside the compressor is never updated. On the next call to `compress`, the `incremental_count` will be wrong.

**Recommendation**: Either:
1. Remove the call to `update_incremental` from `inject_compressed_context` entirely (it's misleading), or
2. Make `update_incremental` actually mutate the `incremental` field (requires changing `&self` to `&mut self`).

## Finding 4: Dead struct fields `_key` and `_first_seen_ms` in `IdempotencyRecord` 🟠

**File**: `src/orchestration/tool/transaction/types.rs:83-88`


**Problem**: Both `_key` and `_first_seen_ms` are prefixed with underscore, which suppresses the "unused field" warning. These fields are:

**Recommendation**: Remove both fields. They serve no purpose.

## Finding 6: `patches_generated` and `patches_applied` use `Arc<Mutex<usize>>` instead of `AtomicU64` 🟠

**File**: `src/security/security_advisor.rs:225-227`

```rust
pub struct SecurityAdvisorAgent {
    config: SecurityAdvisorConfig,
    alerts: Arc<Mutex<Vec<SecurityAlert>>>,
    patches_generated: Arc<Mutex<usize>>,
    patches_applied: Arc<Mutex<usize>>,
    ws_senders: Arc<Mutex<Vec<tokio::sync::mpsc::Sender<SecurityAlert>>>>,
    last_digest_time: Arc<Mutex<Option<SystemTime>>>,
}
```

**Problem**: `patches_generated` and `patches_applied` are simple monotonically-increasing counters. They are only ever incremented via `*count += 1` and read via `*counter.lock().await`. Using a `tokio::sync::Mutex` around a `usize` for a counter is overkill — `AtomicU64` (or even `AtomicUsize`) provides:
- Lock-free increments (`fetch_add(1, Relaxed)`) — no context switch, no contention
- Lock-free reads (`load(Relaxed)`) — no `async` call needed
- No poisoning risk

**Impact**: Each increment on `patches_generated` acquires and releases an async mutex, which involves:
- Waker allocation
- Atomics for the mutex itself
- Suspension point (if contended)

An atomic counter eliminates all of this. `patches_applied` and `patches_generated` would drop from 3 async function calls to zero.

**Recommendation**: Change `patches_generated` and `patches_applied` from `Arc<Mutex<usize>>` to `AtomicU64`. Update the getter/setter methods accordingly (they'd no longer need to be `async`).

## Finding 7: Per-tool-call `Arc` allocation on every success 🟡

**File**: `src/orchestration/tool/transaction.rs:125-132`

```rust
scope.register_completion(
    tool_name,
    std::sync::Arc::new(move || {
        tracing::warn!(...);
    }),
);
```

**Problem**: For every successful tool in a transaction, this code allocates an `Arc<dyn Fn() + Send + Sync + 'static>` on the heap containing a closure that only does `tracing::warn!`. This is called on the hot path (every tool execution).

**Impact**: Heap allocation + dynamic dispatch per tool call even though:
- The closure does nothing meaningful (only logs)
- The `Arc` is only needed for the `CompensateFn` type alias which requires `Send + Sync`
- The comment explicitly acknowledges it's a "no‑op compensation"

**Recommendation**: Consider using a static no-op compensation function (zero allocation) or a smaller enum rather than boxing every closure. At minimum, the `Arc` allocation is wasteful.

## Finding 9: Triple-duplicated LRU eviction logic 🟡

**File**: `src/optimization/failure_prevention.rs:169-265`

The exact same eviction pattern appears 3 times:

```rust
if self.total_requests.len() >= MAX_REQUESTS
    && !self.total_requests.contains_key(service_name)
{
    if let Some(oldest) = self.total_requests.keys().next().cloned() {
        self.total_requests.remove(&oldest);
        self.successful_requests.remove(&oldest);
    }
}
```

This block appears in `record_failure` (line 172-179), `record_success` (line 214-221), and `record_outcome` (line 244-251). The only difference is which additional maps are cleaned up.

**Recommendation**: Extract to a helper method:

```rust
fn evict_oldest_request_entry(&mut self, service_name: &str) {
    if self.total_requests.len() >= MAX_REQUESTS && !self.total_requests.contains_key(service_name) {
        if let Some(oldest) = self.total_requests.keys().next().cloned() {
            self.total_requests.remove(&oldest);
            self.successful_requests.remove(&oldest);
        }
    }
}
```

## Finding 11: Multiple lock acquisitions in FastPathCache operations 🟡

**File**: `src/orchestration/fast_path_cache.rs:275-358`

Each cache operation (`get_intent`, `set_intent`, `get_skills`, `set_skills`, `get_env`, `set_env`, `match_route`, `register_route`) acquires and releases `self.inner.lock()` independently. If callers perform sequences like `get_intent → get_skills → get_env`, that's 3 separate lock acquisitions.

**Impact**: Each lock acquisition/ Release involves atomic operations on the Mutex. For sequential cache lookups that are logically atomic from the caller's perspective, this adds unnecessary overhead.

**Recommendation**: Consider adding a batch method that acquires the lock once and performs multiple lookups:

```rust
pub fn get_all_cached(&self, task_text: &str, prerequisites: &[String]) -> (Option<IntentCacheValue>, Option<SkillCacheValue>, Option<EnvCacheValue>) {
    let mut inner = self.inner.lock().expect("...");
```

## Finding 13: Comment says "no‑op compensation" — not a real rollback 🟢

**File**: `src/orchestration/tool/transaction.rs:119-131`

```rust
// Register a no‑op compensation by default. In a real
// system each tool would provide its own inverse.
let name = tool_name.clone();
let txn_id = txn_id_for_closure.clone();
scope.register_completion(
    tool_name,
    std::sync::Arc::new(move || {
        tracing::warn!(
            "compensating tool '{}' for txn '{}' (no‑op)",
            name,
            txn_id,
        );
    }),
);
```

**Problem**: The transaction system registers compensation actions, but all current compensations are no-ops that only log. When a transaction fails, the `rollback()` method iterates through compensations and calls them — but nothing actually undoes the tool's side effects (e.g., a `write_file` tool would leave the written file in place).

**Impact**: The transaction system creates the illusion of atomic rollback without actually performing it. This is a known architectural gap documented in the code itself, but it's worth flagging as a structural issue.

**Note**: Verifying this isn't a quick fix — it would require each `Tool` to provide its own `compensate()` method. Flagged for awareness.

## Finding 14: `RefCell<HashMap<...>>` in ComplexityEstimator 🟢

**File**: `src/orchestration/complexity_estimator.rs:114`

```rust
history: RefCell<HashMap<String, u8>>,
```

The `RefCell` is used so that `estimate()` can take `&self` while still recording to history. In practice, `ComplexityEstimator` is used in single-threaded contexts, so the `RefCell` adds runtime borrow-checking overhead (minimal) and makes the struct non-`Sync`.

**Recommendation**: Consider whether `&mut self` is acceptable for `estimate()`. If so, drop the `RefCell` and use `HashMap<String, u8>` directly.
