## 1. 🔴 Critical Bug — hub/server.rs 编译错误

### 1.1 `PathBuf::write()` 不存在

**文件**: `src/hub/server.rs` 第 82 行
**代码**:
```rust
self.discovery_path.write(&self.bind_addr, &self.api_token, &self.hub_id)?;
```

**问题**: `self.discovery_path` 的类型是 `PathBuf`（定义在 `HubServer` 结构体第 33 行），它没有 `.write()` 方法。这是 copy-paste 错误——应该是调用 `HubDiscovery::write()`，但 `HubDiscovery` 结构体已经被创建为 `discovery` 变量并在第 75 行使用过了。第 82 行是第 75 行之后的重复/冲突代码。

### 1.2 闭包捕获了 `self` 的字段但 `self` 不能 move

**文件**: `src/hub/server.rs` 第 85-110 行
**代码**:
```rust
tokio::spawn(async move {
    loop {
        match listener.accept().await {
            Ok((stream, peer)) => {
                let vault = vault.clone();     // vault is self.vault but not extracted
                let api_token = api_token.clone(); // same
                ...
```

**问题**: `self` 是 `&mut HubServer`，不能 move 进 `tokio::spawn` 闭包。`vault`, `api_token`, `hub_id`, `rpc_count`, `start_time` 都是 `self` 的字段，不是局部变量。需要在 spawn 之前提取为局部变量。

### 1.3 顺序错误：`set_nonblocking` 在 `from_std` 之后

**文件**: `src/hub/server.rs` 第 78-79 行
**代码**:
```rust
listener.set_nonblocking(true)?;          // 第78行 - std TcpListener
let listener = tokio::net::TcpListener::from_std(listener)?;  // 第79行 - 转换后覆盖
```

**问题**: `set_nonblocking` 是对 `std::net::TcpListener` 的调用，但 `from_std` 也需要 `std::net::TcpListener`。第79行的赋值覆盖了 `listener` 变量，所以 `set_nonblocking` 实际上对原始 listener 生效了，但从代码逻辑看，`set_nonblocking` 应该在 `from_std` 之前调用（是的 `from_std` 内部会设置非阻塞），但 `from_std` 的文档明确指出不需要手动设置非阻塞。

**但是真正的问题是**: 第78行在 `let listener = tokio::net::TcpListener::from_std(listener)?;` 之前调用 `set_nonblocking` 没有问题——因为 `from_std` 接收 `std::net::TcpListener` 的所有权，它会接管这个 listener。但是第79行重新绑定了 `listener`，所以第78行和第79行的顺序实际上是OK的。不过最佳实践是不调用 `set_nonblocking` 而让 `from_std` 处理。这是一个 minor 问题。

### 修复方案 — hub/server.rs

需要重写 `HubServer::start()` 方法，提取 `self` 的字段到局部变量后再 spawn。

## 2. 🟡 性能瓶颈

### 2.1 `loop_executor.rs` 热路径 `block_in_place`

**文件**: `src/orchestration/tool/loop_executor.rs` 第 650 行
**代码**:
```rust
pub async fn execute_loop_async(...) {
    for iteration in 0..config.max_iterations {
        let think_result = block_in_place(|| {
            think(task, &tool_candidates, &retry_counts, config, recommender.as_deref())
        });
```

**违反原则**: **#23** — 在 production 热路径（chat、vote、debate、request）中禁止 `block_in_place + block_on`。

**影响**: 每次 TAO 循环迭代的 think 阶段都会阻塞 tokio 运行时的工作线程。虽然 `think` 函数是 CPU 密集型选择逻辑，`block_in_place` 比 `spawn_blocking` 轻量，但仍然会占用工作线程。

**建议修复**: 将 `think` 函数改为异步（async fn），或使用 `spawn_blocking` 并在 think 内部使用 `blocking` 方式。实际上更好的方案是让 `think` 返回 `Future`：

```rust
// 方案 A: 让 think 本身就是 async
async fn think_async(...) -> Option<ThinkResult> { ... }

// 方案 B: 使用 spawn_blocking
let think_result = tokio::task::spawn_blocking({
    let task = task.clone();
    let candidates = tool_candidates.clone();
    move || think(&task, &candidates, &retry_counts, &config, recommender)
}).await.unwrap();
```

## 3. 🟡 冗余执行系统重叠

经全项目普查，存在 **5 套重叠的执行引擎**，它们的功能有显著交叉：

| 执行系统 | 文件位置 | 核心功能 | 重叠分析 |
|----------|----------|----------|----------|
| **TAO Loop** | `orchestration/tool/loop_executor.rs` | Think→Act→Observe 工具执行循环 | 是基础工具执行链路 |
| **BrainLoop** | `orchestration/brain_loop/` | Plan→Execute→Reflect→Replan 迭代循环 | 与 planner_executor 高度重叠 |
| **PlannerExecutor** | `orchestration/planner_executor/` | Planner 分解 + Executor DAG 执行 | 与 brain_loop 重叠度 **75%** |
| **AutonomyLoop** | `acp/helpers/autonomy/` | ACP 模式下的自治循环 | 包装 brain_loop 或 TAO loop |
| **FullAutoFlow** | `orchestration/full_auto/` | 意图解析→技能发现→自动执行管道 | 与 multi_agent_pipeline 重叠 |

### 3.1 BrainLoop + PlannerExecutor 深度重叠分析

| 功能 | BrainLoop | PlannerExecutor |
|------|-----------|-----------------|
| 任务分解 | `planning.rs` 中的 `auto_decompose_task` | `Planner::decompose_task` |
| 步骤执行 | `execution.rs` 中的 `execute_step` | `Executor::execute_plan` |
| DAG 支持 | 串行 steps 列表 | 完整的 `DagMetrics` 并行组 |
| 失败处理 | `reflect` + `replan` | `plan_optimization` |
| 上下文传播 | `BrainLoopStep.context` | `ExecutionGraph` 上下文 |

**结论**: `BrainLoop` 和 `planner_executor` 的 `Planner` + `Executor` 组合本质上做同一件事——分解任务、执行、处理结果。`BrainLoop` 更偏向迭代式（Plan→Execute→Reflect→Replan），而 `planner_executor` 更偏向一次分解+DAG 执行。两者应该统一。

### 3.2 FullAutoFlow + MultiAgentPipeline 重叠

| 功能 | FullAutoFlow | MultiAgentPipeline |
|------|-------------|-------------------|
| 任务解析 | `parse_task()` | `TaskDecomposer.decompose()` |
| 多步执行 | `run()` 顺序执行 | `execute_pipeline()` 并行执行 |
| 代理分配 | 通过 skill 分配 | 通过 agent 注册表分配 |

**结论**: FullAutoFlow 是为单用户本地场景优化的快速路径，而 MultiAgentPipeline 是为多代理场景设计的。两者有相似的目标但实现路径不同，保留合理。

```
工具识别 (AI 模型选择工具)
  → ToolRegistry::get(name) [HashMap O(1)]
    → ToolHookRegistry::run_pre_async (并行 hooks)
      → GuardianHook::async_pre_execute (安全审查)
      → AgentCommunicationHook::pre_execute (通信记录)
    → Tool::run_async / Tool::run (实际执行)
    → ToolHookRegistry::run_post (后处理)
  → ToolOutput 返回
```

**状态**: ✅ 链路完整，`run_pre_async` 已实现并行 hooks

```
技能识别 (用户请求或 skill_finder 工具)
  → SkillRegistry::find (模糊匹配)

      → Skill::execute (异步执行)
  → Value 结果返回
```

**状态**: ✅ 链路完整，`discovery_cache` 提供缓存
