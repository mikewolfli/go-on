## 2. 性能优化与串行瓶颈改造

### 2.1 P0 - 并行工具执行从未被真正使用

`orchestration/orchestrator.rs:L219`:
```rust
let parallel_groups = Vec::new();
```
`ToolPipeline::execute()` 的并行组字段被硬编码为空。整个 `Pipeline` 阶段2的并行组支持(L158-225)从未被填充，永远是顺序执行。

**修复**: 在 `orchestrator.rs` 中根据工具依赖关系构建并行组。

### 2.2 P0 - `allowed_tools()` 每次调用分配~80个String

`orchestration/mode.rs:L930-1086`:
`plan_tools()` (L932-958)、`all_execution_tools()` (L964-1042)、`read_only_tools()` (L1045-1072) 每次调用都创建3个新的 `Vec<String>`，这在工具执行循环中可能频密发生。

**修复**: 使用 `OnceLock<Vec<&'static str>>` 或 `LazyLock` 静态初始化。

### 2.3 P1 - `compute_risk_score` 多次冗余小写

`orchestration/mode.rs:L540-587`:
- L547: `objective.to_lowercase().contains(kw)` 为每个极端关键词创建小写字符串
- L571: `word_boundary_match(objective, kw)` 在内部再次分割 `objective` (L592-594)

复杂度: O(N×M)，其中 N=目标长度次数，M=关键词数量。

**修复**: 预计算 `let lower = objective.to_lowercase()` 一次传递。

### 2.4 `sse_optimizer.rs` — 功能已验证但可优化SSE解析器直接支持 `&[u8]`

`agents/sse_optimizer.rs:L12-48`:
`SseBufferPool` 被 `acp/impl/chat/streaming.rs` 使用(`SseBufferPool::acquire()`/`release()` 各有调用点)。已验证不是死代码。

**优化方向**: `SseEventParser` 目前接受 `String`，可以扩展直接接受 `&[u8]` 以减少压缩SSE路径中不必要的String分配(当前: 解压→Vec<u8>→String→Parser的链式分配, `mod.rs:L505-534`)。

### 2.5 P1 - SSE压缩仅由OpenAI支持

`agents/openai.rs:L181-194` 检查 `"sse_compress": true`。
DeepSeek、Anthropic、Gemini、Cohere**不**支持此功能。DeepSeek尤其可受益于大型流。

### 2.6 P1 - 压缩SSE路径中不必要的3-4次String分配

`agents/mod.rs:L505-534`:
1. 解压 → `Vec<u8>`
2. 转换为 `String` (L514-516)
3. 推送到 `SseEventParser`
4. 解析器管理自己的 `String` 缓冲区

**修复**: `SseEventParser` 可直接接受 `&[u8]` 避免中间String分配。

### 2.7 P1 - `pipeline.rs` 中工具预算在检查沙箱前计入

`orchestration/tool/pipeline.rs:L165-166`:
```rust
let group_count = group.len() as u32;
tool_calls_used += group_count;
```
预算在工具执行之前被计入，即使某些工具可能因沙箱检查失败而无法运行。

### 2.8 P2 - 同步 `think()` 在异步上下文中阻塞

`orchestration/tool/loop_executor.rs:L646-651`:
同步 `think()` 函数在 `execute_loop_async` 内部被调用，阻塞异步运行时。

**修复**: 将 `think()` 改为异步或 spawn_blocking。

### 2.9 P2 - 技能发现是串行的

`skill/registry.rs` 中的 `discover_and_register_local_skills` 顺序扫描 SKILL.md 文件。对于大量技能目录，可以使用 `tokio::fs` 或 rayon 并行化。

### 2.10 P2 - `FlowManager::resolve` 顺序解析代理

`orchestration/flow.rs:L123-212`:
当没有配置代理时，获取所有注册代理名称后为每个名称单独调用 `registry.get()`，可以批量处理。

### 2.11 P2 - `OptimizerRegistry::list_optimizers` 为提取名称而运行优化

`orchestration/workflow_optimizer.rs:L433-453`:
通过使用空上下文调用 `opt.optimize(&dummy_ctx)` 来提取名称。为 `WorkflowOptimizerPlugin` trait添加 `fn name(&self) -> &str` 即可消除这些死调用。

### 2.12 P3 - `task_decomposer.rs` 重复调用 SystemTime::now()

`orchestration/task_decomposer.rs:L89-145`:
`SystemTime::now()` 被调用了三次(L92-95, L112, L142-145)。每次都是一个系统调用。

### 2.13 已确认无block_on违规（Principle #23/#24）

经搜索确认:
- 所有7个production `block_on` 使用点均使用专用阻塞运行时模式（不是 `Handle::current().block_on()`）
- 零个 `block_in_place` 实际使用（仅存在于注释中说明为什么**避免**此反模式）
- ✅ 合规

## 5. 从Zed源码可借鉴的新工具/技能模式

对照 `/home/mikeli/workspace/zed` 源码分析:

### 5.1 P0 - `schemars::JsonSchema` 自动工具Schema生成

**Zed模式**: 每个工具定义关联类型 `type Input: JsonSchema + DeserializeOwned`，通过 `schemars::schema_for!(Self::Input)` 自动生成JSON Schema。

**go-on现状**: 手动在 `shared/tool_descriptors.rs` (1576行) 和各个工具中维护 `input_schema()` 返回值。

**收益**: 消除代码与Schema之间的漂移，实现编译时验证。

### 5.2 P0 - `tools!` 宏实现编译时工具注册

**Zed模式** (`agent/src/tools.rs`):
```rust
tools! {
    ReadFileTool, WriteFileTool, GrepTool, ...
}
```
自动生成 `ALL_TOOL_NAMES`、编译时重复名称检测、`tool_supports_provider()`、`tool_allowed_in_restricted_mode()`、`built_in_tools()`。

**go-on现状**: 手动 `register_with_profile()` 调用，无编译时名称唯一性保证。

### 5.3 P1 - 流式 `ToolInput<T>` 通道

**Zed模式** (`agent/src/thread.rs:4928`):
```rust
pub struct ToolInput<T> {
    rx: mpsc::UnboundedReceiver<ToolInputPayload<serde_json::Value>>,
}
pub enum ToolInputPayload<T> {
    Partial(serde_json::Value),  // 增量更新
    Full(T),                     // 最终反序列化输入
    InvalidJson { error_message: String },
}
```
支持模型在生成参数时开始发送，感知流的工具可使用 `next()` 获取部分数据。

**go-on现状**: 简单的同步 `&ToolInput` 引用，无流式支持。

### 5.4 P1 - `ToolCallEventStream` 进度/取消

**Zed模式**: 每个工具 `run()` 接收 `ToolCallEventStream`，提供:
- `ToolCallEvent::ToolFinished` — 通知模型已完成
- `ToolCallEvent::ToolAction { label, detail }` — 进度更新
- `stream.cancelled_by_user()` — Future，在用户取消时resolved

**go-on现状**: 单个 `ToolOutput` 返回，无进度流或取消信号。

### 5.5 P1 - 技能作用域前缀 (`:<scope>`)

**Zed模式**:
- 全局技能: `/:name` (如 `/:code-review`)
- 项目本地技能: `/<worktree>:name` (如 `/my-project:code-review`)
- `SkillSource.matches_scope()` 明确处理作用域匹配

**go-on现状**: 仅 `/<name>`，无法处理多项目同名技能冲突。

### 5.6 P2 - `disable-model-invocation` 技能选项

**Zed模式**: 技能可设置 `disable-model-invocation: true`，从模型目录隐藏，仅用户通过 `/` 命令手动调用。

**go-on现状**: 无此功能，所有技能自动进入模型目录。

### 5.7 P2 - `InitializedContextServerProtocol` 两阶段MCP初始化

**Zed模式** (`context_server/src/protocol.rs`):
```rust
let protocol = client.initialize(client_info).await?;
// 之后: protocol.capable(ServerCapability::Tools)
//       protocol.request(...)
//       protocol.notify(...)
```
两阶段(`Client → Initialized`)确保版本协商完成后再发送请求。

**go-on现状**: go-on有 `mcp` 模块和 `protocol/mcp_server.rs`，但无标准化的两阶段初始化流程。

### 5.8 P2 - 编译时内嵌技能体

**Zed模式**: 内置技能的SKILL.md主体编译进二进制(`embedded_body: Option<&'static str>`)，避免运行时文件系统读取。

**go-on现状**: 所有技能(包括内置的)在运行时从文件系统读取。

### 5.9 P2 - `request!()` / `notification!()` 类型化MCP宏

**Zed模式** (`context_server/src/types.rs`):
```rust
request!("tools/call", CallTool, CallToolParams, CallToolResponse);
notification!("notifications/initialized", Initialized, ());
```
编译时类型化请求/通知定义，自动实现 `Request` trait。

**go-on现状**: MCP请求是手动的 `serde_json::Value` 操作。

### 5.10 P3 - XML信封渲染与注入防护

**Zed模式**: 技能内容包装在 `<skill_content name="...">` XML标签中，并有注入防护防止敌对技能文件注入虚假标签。

**go-on现状**: 使用纯Markdown模板。
