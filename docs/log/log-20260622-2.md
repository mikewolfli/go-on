## ⚡ CRITICAL FINDING: Test Time Regression Root Cause

**Problem: Full test suite regressed from ~3 minutes to 5+ minutes.**

### Root Cause 1 (🔴 MAJOR): `wait_for_exit()` forces 15-second minimum timeout

File: `tests/acp_runtime_rpc_integration.rs` line 335
```rust
let timeout = timeout.max(Duration::from_secs(15));
```

Every caller passes `Duration::from_secs(8)`, but the method **ignores it** and waits minimum 15s per test. With ~40 tests spawning child processes, if even a few need the timeout, the cost is enormous.

**Impact: ~40 tests × 15s = 600s worst case. Fixed to respect caller's parameter.**

### Root Cause 2 (🟡 MODERATE): `request()` has 15-second response timeout

File: `tests/acp_runtime_rpc_integration.rs` line 261
```rust
let deadline = Instant::now() + Duration::from_secs(15);
```

With 3 retries, a single test can wait 45s for one request. Reduced to 10s.

### Root Cause 3 (🟡 MODERATE): `#[serial] mod advanced` double-serializes ~40 tests

The `RpcHarness` already acquires a `_suite_guard` (MutexGuard) AND a `CrossProcessLock` (file lock) at spawn time. The `#[serial]` module attribute adds a **third** serialization layer, forcing all ~40 tests in `advanced` to run one-at-a-time.

**Impact: Prevents Cargo's native test parallelism from working at all within this module.**

### Root Cause 4 (🟢 MINOR): Meaningless sleeps in e2e tests

Multiple e2e tests contained `sleep(Duration::from_millis(10)).await` as "teardown" with zero assertions following them. Also one benchmark test used `thread::sleep(10ms)` to "simulate chat latency."

## 1. std::sync::Mutex vs tokio::sync::Mutex Analysis

### Answer: No — the current distribution is correct and optimal.

**Why std::sync::Mutex is correct for sync-only paths:**
- `std::sync::Mutex` is *faster* than `tokio::sync::Mutex` for synchronous code (~10ns vs ~25ns + allocation)
- Rule: use `std::sync::Mutex` when lock is NEVER held across `.await`; use `tokio::sync::Mutex` when it IS
