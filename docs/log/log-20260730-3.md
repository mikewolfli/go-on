## 一、🔴 关键发现 (Critical)

### 1.1 `consecutive_allows` 竞争条件 — `harness_bus/mod.rs:299-321`

**原则违反**: Rule #15 (不完整修复 — 锁设计缺陷导致可观测行为不可靠)

**文件**: `src/governance/harness_bus/mod.rs`

```rust
// L299-301 — fetch_add + store(0) 不是原子操作
let prev = self.consecutive_allows.fetch_add(1, Ordering::SeqCst);
if prev >= 2 {
    self.consecutive_allows.store(0, Ordering::SeqCst);  // ⚠️ 非原子比较并交换
    let engine = self.evaluator.rule_engine.lock()...;
    let level = engine.de_escalate("...");  // ⚠️ 可能被执行两次
    ...
}
```

**问题分析**:
- 两个并发调用者可以同时看到 `prev=2` 和 `prev=3`，都满足 `>=2` 条件
- `store(0)` 不与 `fetch_add` 同步 — 两个调用者都会执行 `de_escalate()` 和 `record_learning_update()`
- 导致 **双重降级**，PUA 策略状态不一致

**修复建议**: 使用 `AtomicU32::compare_exchange` 或 `fetch_update` 实现原子检查-重置：
```rust
// 使用 compare_exchange 确保只有一个调用者成功重置
let _ = self.consecutive_allows.fetch_update(
    Ordering::SeqCst, Ordering::SeqCst,
    |prev| if prev >= 2 { Some(0) } else { None }
);
// 或者简化为 compare_exchange(3, 0)
```

### 1.2 `continuous_learning.rs` — `LazyLock<Runtime>.block_on()` 违规 🔴

**原则违反**: Rule #23 (block_in_place + block_on 清零), Rule #24 (Handle::current().block_on 清零)

**文件**: `src/intelligence/continuous_learning.rs:506-544`

```rust
// L506-515 — 静态后台 Runtime
fn shared_background_runtime() -> &'static tokio::runtime::Runtime {
    static RT: std::sync::OnceLock<tokio::runtime::Runtime> = ...;
    RT.get_or_init(|| {
        tokio::runtime::Builder::new_multi_thread()
            .worker_threads(1)
            .enable_all()
            .build()
            .expect("...")
    })
}

// L518-544 — 在同步上下文中使用 block_on
pub fn consolidate_experience_with_distill(...) -> Result<String> {
    ...
    let rt = Self::shared_background_runtime();
    rt.spawn(async move {   // ⚠️ 从同步上下文向 Runtime 提交异步任务
        let count = center.llm_distill().await;
        ...
    });
    Ok(id)
}
```

**问题分析**:
- 如果此函数从 tokio 运行时上下文调用（大概率如此，因为整个项目是异步的），`LazyLock<Runtime>` 从现有 tokio 运行时内部创建一个新的 `Runtime` **不会 panic**（它与 `block_on` 不同）。但 `spawn` 返回的 `JoinHandle` 被直接丢弃（fire-and-forget），**可能吞掉 panic**。
- 注释说"non-blocking: kicks off LLM distillation in the background"，使用单独的 runtime thread 增加了不必要的 OS 线程。

**修复建议**: 
- 将 `consolidate_experience_with_distill` 改为 `async fn`，用 `tokio::spawn` 替代静态 Runtime
- 或使用 `spawn_blocking` 桥接

## 四、🟡 串行瓶颈 (Medium)

### 4.1 `PolicyEvaluator::evaluate()` — 9 个顺序锁获取

**文件**: `src/governance/harness_bus/evaluator.rs:226-499`

评估管道顺序获取 9 个锁：
1. `self.policies.read()` (RwLock)
2. `reloader.lock()` (Mutex)
3. `self.policies.write()` (RwLock)
4. `self.rule_engine.lock()` (Mutex)
5. `self.budget.lock()` (Mutex)
6. `self.runtime_control.lock()` (Mutex)
7. `self.guard.lock()` (Mutex)
8. `SecurityGovernor::evaluate()` (内部锁)
9. `runtime_ctrl` re-lock (Mutex 再借用)

**影响**: 在高压并发下，每个锁可能争用，总延迟是所有 9 个锁的累加。

**修复建议**:
- 将所有 `std::sync::Mutex` 替换为 `tokio::sync::Mutex`（已明确文档化使用 `std::sync::Mutex` 因为锁持有时间短，但在异步上下文中这可能导致 tokio 工作线程阻塞）
- 或评估是否可以批处理/合并某些检查

---

### 4.2 `BrainLoop::run_async` 步进完全串行

**文件**: `src/orchestration/brain_loop/planning.rs:741-943`

虽然代码中存在 `parallel_groups` 的概念，但实际执行是顺序的 `while` 循环遍历步骤。`join_all` 仅在单个组内有效，但组与组之间串行。
