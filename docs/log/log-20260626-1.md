## 发现的问题与修复

### ✅ 变更1: 移除 `memory_persistence.rs` 中无意义的原子自增操作

**文件**: `src/memory/memory_persistence.rs:1199-1200`

**问题**: `store()` 方法中执行了 `self.sequence.fetch_add(1, Ordering::Relaxed)` 并立即丢弃结果到 `let _ = seq;`（注释"available for future ordering needs"）。此原子自增在每个 `store()` 调用中执行，但结果从未使用。

**修复**: 删除无意义的 `sequence.fetch_add` + `let _ = seq` 代码行。

**效果**:
- 消除每次 `store()` 调用的无用原子操作开销
- 删除对应的 `sequence: AtomicU64` 字段
- 删除不再使用的 `use std::sync::atomic::{AtomicU64, Ordering}` 导入

### ✅ 变更2: 合并 `memory_persistence.rs` 中重复的条件导入

**文件**: `src/memory/memory_persistence.rs:11-15`

**问题**: `#[cfg(feature = "backend-postgres")]` 和 `#[cfg(not(feature = "backend-postgres"))]` 两个分支导入了完全相同的 `anyhow::{Context, Result}`。两个分支互斥且内容一致。

**修复**: 合并为单个无条件的 `use anyhow::{Context, Result};` 导入。

**效果**: 消除冗余代码，降低编译复杂度。

### ✅ 变更3: 移除 `config_validation.rs` 中从未填充的结构体字段

**文件**: `src/core/config_validation.rs:419-420`

**问题**: `DependencyAnalysis.internal_dependencies: HashSet<String>` 字段定义在结构体中，但没有任何代码对其写入。全局搜索确认 `internal_dependencies` 在整个代码库中仅在结构体定义处出现。该字段始终为空，浪费内存和序列化空间。

**修复**: 删除 `DependencyAnalysis.internal_dependencies` 字段。

### ✅ 变更4: 修复 `fault_tolerance/mod.rs` 多用户服务器 Profile 编译错误

**文件**: `src/fault_tolerance/mod.rs:42`

**问题**: `FaultToleranceSnapshot` 结构体缺少 `serde::Serialize` 派生，导致 `cargo build --features multi-users-server` 编译失败（`serde_json::to_string_pretty(snapshot)` 调用失败）。

**修复**: 添加 `#[derive(Serialize, Deserialize)]` 派生 + `use serde::{Deserialize, Serialize};` 导入。

**效果**: **使 multi-users-server Profile 从编译失败修复为编译通过**，这是之前所有扫描轮次未能发现的问题。

### ✅ 变更5: 修复 `FUTURE5.MD` 未解决的 Git 合并冲突

**文件**: `docs/design/FUTURE5.MD`

**问题**: 文件包含 4 处 Git 合并冲突标记（`<<<<<<< Updated upstream` / `=======` / `>>>>>>> Stashed changes`），导致文档不可读。

**冲突详情**:
1. 第4-8行：描述段落（"主从AI闭环思维运作体系" - 有无空格差异）
2. 第65-143行：全部 P0-P7 复选框清单（`[ ]` vs `[x]` 状态冲突）
3. 第158-162行：能力矩阵表格行（"全链路" vs "全链"）
4. 第172-182行：风险表（"失配" vs "失准" / "崩溃" vs "崩塌" / 细节措辞差异）

**修复**: 采用 `Stashed changes` 版本（已全部标 `[x]` 的完成态版本）作为最终版本，删除所有合并冲突标记。

**效果**: 文件现在可正常阅读。

### 新增修复（7项）

#### ✅ 变更6: 修复同步 `execute_loop` 在 async 上下文中阻塞 tokio worker 线程

**问题**: 4个调用点在 async 函数中使用同步 `execute_loop()`，阻塞 tokio worker 线程：

| 调用点 | 文件行 | 严重性 |
|--------|--------|--------|
| `acp/impl/chat.rs:1094` | `execute_loop()` 在 async fn 中 | **CRITICAL** |
| `orchestration/dag_driver.rs:349` | 在 `tokio::spawn(async move {})` 内部 | **CRITICAL** |
| `autonomy_loop.rs:860` | 在 `tokio::spawn` + `join_all` 内部 | **CRITICAL** |
| `pipeline.rs:346` | `run_single_tool` 是 async fn 但调用同步 `run_with_fallback` | **HIGH** |

**修复**: 全部改为调用 `execute_loop_async()` / `run_with_fallback_async()` 并 `.await`

#### ✅ 变更7: 修复 `tool_bus.rs` 中锁跨越 await 点的 clippy 错误

**文件**: `src/intelligence/capability_bus/tool_bus.rs:340-351`

**问题**: 变更6中改为 `run_with_fallback_async().await` 后，`std::sync::MutexGuard` 跨越 await 点，触发 `clippy::await_holding_lock` 错误。

**修复**: 改为 `tokio::task::spawn_blocking` 中调用同步 `run_with_fallback`，通过克隆 `Arc<Mutex<ToolRegistry>>` 移入闭包。

#### ✅ 变更8: 修复 `verify-blue26-closure.ps1` 未定义变量

**文件**: `scripts/verify-blue26-closure.ps1:14`

**问题**: `$blue26Path` 变量在使用前未定义（typo），导致脚本运行时立即崩溃。

**修复**: 添加 `$blue26Path = Join-Path $rootDir "docs/blueprints/blue26.md"` 定义，并添加路径存在性检查。

#### ✅ 变更9: 修复 `run-blue22-benchmark-snapshot.sh` 引用了不存在的测试

**文件**: `scripts/run-blue22-benchmark-snapshot.sh:48`

**问题**: `cargo test --test e2e_contract_tests` — 测试文件 `tests/e2e_contract_tests.rs` 不存在。注释说明 `step2_three_endpoint_contract` 已重命名，但替换测试从未创建。

**修复**: 改为 `cargo test --test contract_tests`（指向 `tests/contract_tests/` 目录）。

#### ✅ 变更10: 修复 `office.rs` 模块缺乏 feature gate

**文件**: `src/orchestration/tool/extended/mod.rs:59`

**问题**: `pub mod office;` 无条件编译，导致 `calamine`、`zip`、`quick-xml` 等依赖即使在不使用 office 功能时也被编译，增加编译时间和二进制体积。

**修复**: 添加 `#[cfg(any(feature = "document-excel", feature = "document-docx", feature = "document-excel-write", feature = "document-ppt"))]` 条件 gate。

#### ✅ 变更11: 清理3个未使用的 `execute_loop` 导入

**修复**: 在 `chat.rs`、`dag_driver.rs`、`autonomy_loop.rs` 中将 `execute_loop` 导入替换为 `execute_loop_async`，消除3个 `unused import` 警告。
