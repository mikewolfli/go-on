## 二、核心架构借鉴点

### 2.1 模块分层设计（最重要的借鉴）

**Codex 的分层**：
```
codex-skills (基础模型层) → codex-core-skills (加载/发现/服务层) → codex-core (编排层)
codex-plugin (基础模型) → codex-core-plugins (市场/加载/管理) → codex-core
codex-tools (工具定义) → codex-core (注册/编排)
codex-extension-api (接口层) ← 各个 ext/* (实现层)
```

**go-on 现状**：go-on 将 `agents/`, `core/`, `orchestration/`, `hub/`, `intelligence/` 等模块平铺在 `src/` 下，缺少 `*-core-*` 这种"基础层 → 核心服务层 → 编排层"的**三层分离**。

**借鉴建议**：
1. **抽取独立层**：将 `core/skills` 拆分为类似 `codex-skills`（纯数据结构 + 序列化）和 `core-skills`（加载/发现/缓存逻辑）
2. **插件的基础层**：将插件相关数据结构抽取为独立 crate（类似 `codex-plugin`）
3. **工具定义层**：将工具定义、JSON Schema 等工具元数据抽取为独立 crate（类似 `codex-tools`）
4. **扩展 API 接口层**：定义 trait-based 扩展接口层（类似 `codex-extension-api`）

### 2.2 协议层分离

**Codex**：`codex-protocol` 是**所有 crate 共享的协议定义**，包含：
- `config_types` (所有配置类型)
- `models` (OpenAI 响应模型)
- `exec_output` (执行输出)
- `approvals` (审批)
- `permissions` (权限)
- `error` (统一错误)

**go-on**：go-on 的 `protocol/` 没有这样分级。`mcp_server` 和 `rpc_protocol` 在同一个模块下。

**借鉴建议**：
1. 将 `protocol/` 拆分为独立 crate（如 `go-on-protocol`）
2. 在 protocol crate 内按功能分 modules（`config_types`, `models`, `error` 等）
3. 所有 crate 统一依赖此 protocol crate

### 2.3 工具定义（Tool Definition）体系

**Codex** 的工具链非常成熟：

```
codex-tools crate:
  ├── tool_definition.rs    — ToolDefinition 核心结构
  ├── tool_spec.rs          — 工具规范（含 Responses API 格式）
  ├── tool_call.rs          — 工具调用抽象
  ├── tool_executor.rs      — ToolExecutor trait
  ├── tool_payload.rs       — 工具负载
  ├── tool_output.rs        — 工具输出格式化
  ├── tool_discovery.rs     — 工具发现
  ├── tool_search.rs        — 工具搜索
  ├── tool_config.rs        — 工具配置
  ├── json_schema.rs        — JSON Schema 解析
  ├── mcp_tool.rs           — MCP 工具
  ├── dynamic_tool.rs       — 动态工具
  ├── responses_api.rs      — Responses API 工具适配
  └── function_call_error.rs— 错误类型

core/src/tools/handlers/:  每个工具类型的 handler
  ├── shell.rs              — shell 命令执行
  ├── apply_patch.rs        — patch 应用
  ├── multi_agents.rs       — 多 agent 管理
  ├── plan.rs               — 计划工具
  ├── tool_search.rs        — 工具搜索
  ├── mcp.rs                — MCP 调用
  ├── sleep.rs              — 睡眠工具
  └── ... (20+ handers)
```

**go-on 现状**：go-on 在 `orchestration/tool.rs` 中有基本的工具定义，没有形成完整的工具生命周期管理。

**借鉴建议**：
1. 创建独立的 `go-on-tools` crate
2. 实现完整的工具生命周期：定义 → 发现 → 调用 → 输出 → 搜索
3. 实现 `ToolExecutor` trait + 注册表模式（类似 codex 的 `ToolRouter`）
4. 支持动态工具和 MCP 工具统一

codex-extension-api crate:

每个 `ext/*` 都是一个独立的 crate 实现这些 trait：

## 四、多 Agent 系统

### 4.1 Agent Control 架构

**Codex** 的多 agent 系统非常成熟：

```
AgentControl (session 级)
  ├── AgentRegistry — agent 注册表（限制、追踪、路径解析）
  │   ├── agent_tree              — agents 树形结构
  │   ├── max_threads             — 最大并发限制
  │   ├── spawn_reservation       — 预留插槽（原子操作）
  │   └── agent_id_for_path()     — 路径 → ID 解析
  ├── AgentExecutionLimiter — 执行能力限制器
  ├── V2Residency — V2 常驻管理
  ├── RolloutBudget — 回滚预算
  └── AgentCommunication — agent 间通信
      ├── spawn    — 子 agent 生成
      ├── message  — 普通消息
      ├── followup — 跟进
      └── result   — 结果传递
```

**关键设计**：
- `AgentPath` 路径解析（如 `alice/deep-dive/coding`）
- `AgentCommunicationContext` 通信追踪
- `SpawnReservation` 预占模式（先预订 → 再提交）
- 执行能力限流（`AgentExecutionLimiter`）
- 自动完成通知（`completion_watcher`）

**go-on 现状**：go-on 在 `agents/` 中有 agent 定义，架构较简单，缺少：
- 树形路径管理
- 通信上下文追踪
- 执行能力限流
- 子 agent 完成通知

### 4.2 子 agent 生成（Spawn）

**Codex** 支持：
1. **V1 fork**: 完整历史或最后 N 轮
2. **V2 proactive**: 自动判断何时 spawn
3. **V2 explicit**: 仅按需 spawn
4. `MultiAgentVersion` 和 `MultiAgentMode` 配置
5. `rollout_budget` 限制总轮次
6. 深度限制（`spawn_depth_limit`）

## 六、配置系统

### 6.1 Codex 的多层配置

**Codex 的配置层堆叠**（`ConfigLayerStack`）：

```
层顺序（优先级高→低）：
1. cloud config (云端配置)
2. CODEX_REQUIREMENTS environment
3. CODEX_CONFIG environment
4. requirements.toml (项目根)
5. config.toml (项目根)
6. 用户级 config
7. 系统级 config
8. 默认值
```

**Key 类型**：
- `ConfigLayer` / `ConfigLayerSource` / `ConfigLayerMetadata`
- `ConfigRequirements` — 约束配置
- `McpServerConfig` — MCP 配置
- `PluginConfig` — 插件配置
- `HooksFile` — 钩子配置
- `SkillsConfig` — 技能配置
- `CloudConfigBundle` — 云端配置包

**go-on 现状**：go-on 有 Profile 系统（local/simple-server/multi-users-server/full），但缺少多层堆叠。

**借鉴建议**：
1. 引入配置层概念，支持层间合并（merge）
2. 支持 "requirements" 约束层（项目管理员可锁定某些设置）
3. 支持云端/远程配置下发
4. 每层可追踪来源以便诊断

## 七、Hooks 生命周期

**Codex 的 Hook 系统**：

```
HookEventName:
  PreToolUse       — 工具调用前
  PermissionRequest— 权限请求
  PostToolUse      — 工具调用后
  PreCompact       — 历史压缩前
  PostCompact      — 历史压缩后
  SessionStart     — 会话启动
  SessionEnd       — 会话结束
  UserPromptSubmit — 用户提交
  SubagentStart    — 子 agent 启动
  SubagentStop     — 子 agent 停止
  Stop             — 停止
```

每个钩子可以被：
1. 从 `config.toml` 配置
2. 从插件清单声明
3. 从 `requirements.toml` 锁定
4. 组合成 `HookListEntry` 按顺序执行

**借鉴建议**：go-on 可以设计类似的**生命周期钩子系统**，挂接在 `orchestration/flow` 的各个阶段。

## 十三、结论

Codex 作为 OpenAI 的旗舰产品，在以下方面远超 go-on：
1. **模块化 crate 组织** — 100+ crates 的清晰分层
2. **工具系统** — 完整的工具定义 → 注册 → 调用 → 输出 → 搜索生命周期
3. **扩展 API** — Trait-based 扩展模式
4. **插件市场** — 完整的市场发现、安装、升级、迁移体系
5. **配置层叠** — 多层配置合并与约束
6. **多 Agent** — 树形路径、通信上下文、执行限制

go-on 在**治理、国际化、韧性、多端统一**方面有独特优势。短期收益最大的借鉴是**工具定义层独立**和**Extension API 架构**，这能让 go-on 的核心与扩展彻底解耦，实现真正的插件化。

#### 14.8.1 工具生命周期 Hook 系统（唯一采纳项）

**设计原则**：极简 Observer 模式，零侵入现有执行路径。

```rust
pub trait ToolHook: Send + Sync {
    fn pre_execute(&self, _tool_name: &str, _input: &ToolInput) -> Result<()> { Ok(()) }
    fn post_execute(&self, _tool_name: &str, _input: &ToolInput,
                    _output: &ToolOutput, _duration_ms: u64) -> Result<()> { Ok(()) }
}

pub struct ToolHookRegistry { hooks: Vec<Arc<dyn ToolHook>> }
```

**实现要点**：

| 组件 | 位置 | 功能 |
|------|------|------|
| `ToolHook` trait | `src/orchestration/tool/types.rs` | 观察者接口，默认 no-op |
| `ToolHookRegistry` | `types.rs` | 线程安全 hook 集合，register/run_pre/run_post |
| `ToolRegistry.hooks` | `types.rs:ToolRegistry` | 注册表内嵌 hook registry |
| Pre-execute 调用 | `executor.rs:298` | ToolInput 构造后，retry 循环前 |
| Post-execute 调用 | `executor.rs:401` | duration_ms 计算后，ToolExecItem 构造前 |
| Pre/Post 调用（备选路径） | `mod.rs:1801,1867` | `run_with_fallback` / `run_with_fallback_async` |

**覆盖的调用路径**：`execute_single_tool()`（覆盖 ACP 自主循环、代理运行时、CLI 聊天 3 条路径）+ `run_with_fallback*()`（覆盖 TAO 循环、工具流水线、工具总线等 5 条路径）= **8/8 路径全覆盖**。

**预期收益**：
- 可注册 PreToolUse hook 实现 URL 策略检查、参数校验、日志增强
- 可注册 PostToolUse hook 实现自动总结、向量嵌入、审计追踪
- 所有 hook 非侵入（fail → only warn），不阻塞执行
