## 🔴 修复清单

### 1. DriftProtectionEngine: 5个独立Mutex → 合并为1个 ✅

**文件**: `src/governance/drift/drift_protection.rs`

**问题**: `DriftProtectionEngine` 有 **5个独立 `Mutex` 字段** — `policies`, `metrics`, `metric_history`, `alerts`, `alert_counter`。每个公共方法顺序锁定 2-4 个，产生不必要的锁开销且没有任何并发收益。每个锁都配有其独立的 poison recovery 模板代码。

**修复**: 合并为 `Mutex<DriftProtectionInner>` 单一内部结构体。所有方法锁定一次，通过 `inner.field` 统一访问。
- 创建 `DriftProtectionInner` 持有所有字段
- 替换 `5 × Mutex<T>` 为 `1 × Mutex<DriftProtectionInner>`
- 所有公共方法 API 签名和行为零变化
- 移除 ~60 行重复的 lock/unwrap_or_else 样板代码
- `check_for_drift()` 中 auto-remediate 部分正确释放锁后再重入

**验证**: `cargo check --features local` ✅

---

### 2. 工具文件锁集成: 消除 `#[allow(dead_code)]` ✅

**文件**: 
- `src/orchestration/tool/lock.rs`
- `src/orchestration/tool/mod.rs`

**问题**: `ToolLockManager` 完整实现了读写锁（带超时、指数退避、RAII handle），但整个管理器从未被接入任何工具，导致 `LockMode::Read`, `LockMode::Write`, `ToolLockManager::acquire()` 全部被 `#[allow(dead_code)]` 标记。

**修复**: 
- 创建全局 `TOOL_LOCK_MANAGER: OnceLock<ToolLockManager>`
- 在 `ReadFileTool::run()` 中：读取文件前获取 `LockMode::Read` 锁
- 在 `WriteFileTool::run()` 中：写入文件前获取 `LockMode::Write` 锁
- 移除 `lock.rs` 中不再需要的 3 处 `#[allow(dead_code)]`
- 保留 `try_acquire()` 和 `release()` 的 `#[allow(dead_code)]`（公共API，等待F-GAP-12进一步集成）

**影响**: 现在同一文件的并发写操作会正确串行化，读操作可并发。

**验证**: `cargo check --features local` ✅, `cargo check --features full` ✅

## 核心教训

1. 大量 `#[allow(dead_code)]` 并非真的"无意义 dead code"，而是 F-GAP 计划内的脚手架代码。真正的清理目标应当是那些已重复、已废弃、或被绕过验证的代码路径。
2. 5个独立 Mutex 比 1个聚合 Mutex 更糟糕 — 更多的样板代码，更多的 poison recovery 分支，却没有实际的并发收益。
3. ToolLockManager 的读/写锁集成是低风险高价值的行为变化 — 它直接消除了文件操作竞态条件并且验证了锁管理器是生产就绪的。
