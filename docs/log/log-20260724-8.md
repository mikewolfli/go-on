## 🔴 新发现 & 修复

### 问题1: hyper_resilience.rs 的锁辅助函数仍为私有实现（漏修）

**发现**：
- `hyper_resilience.rs` 第29-42行定义了私有的 `lock_mutex` 和 `read_lock` 函数
- 函数体包含 poison recovery 的模式匹配代码，未使用 `crate::lock_or_recover!` 宏
- 该文件有 ~27 个 `lock_mutex()` 调用点和 4 个 `read_lock()` 调用点
- 第7轮的日志声明"已完成"但此文件被遗漏

**修复**：
- 将 `lock_mutex` 和 `read_lock` 的函数体改为委托 `crate::lock_or_recover!` / `crate::read_or_recover!`
- 所有 ~31 个调用点自动受益于统一宏实现

### 问题2: 4个残留的 raw `SystemTime::now()` 函数

**发现**（以下文件中的私有 timestamp 函数仍然直接使用 `SystemTime::now()`，而非共享的 `shared::timestamps`）：

| 文件 | 函数 | 原实现 | 修复 |
|------|------|--------|------|
| `optimization/failure_prevention.rs` | `now_epoch_seconds()` | `SystemTime::now().duration_since(UNIX_EPOCH).as_secs()` | → `shared::timestamps::now_ts() as u64` |
| `orchestration/brain_loop/mod.rs` | `now_epoch_ms()` | `SystemTime::now().duration_since(UNIX_EPOCH).as_millis()` | → `shared::timestamps::now_ts_ms() as u64` |
| `orchestration/council/types.rs` | `now_epoch_ms()` | `SystemTime::now().duration_since(UNIX_EPOCH).as_millis()` | → `shared::timestamps::now_ts_ms() as u64` |
| `orchestration/omnipotent.rs` | `now_epoch_ms()` | `SystemTime::now().duration_since(UNIX_EPOCH).as_millis()` | → `shared::timestamps::now_ts_ms() as u64` |

**修复**：全部改为委托 `crate::shared::timestamps::now_ts_ms()` / `now_ts()`。
清理了 `brain_loop/mod.rs`、`council/types.rs`、`failure_prevention.rs` 中不再需要的 `use std::time::{SystemTime, UNIX_EPOCH}` 导入。

### 问题3: intelligence/capability_bus/core.rs inline `SystemTime::now()`

**发现**：`record_event` 方法中有一处 inline 的 `SystemTime::now().duration_since(...)` 调用，未使用共享函数。

**修复**：改为 `crate::intelligence::now_ms()`。

## 🟠 未完成的架构级合并（需谨慎设计）

以下项目为第7轮日志列出但未完成的架构级重构。经仔细分析，它们**不是简单的重复冗余**，而是设计上确实不同的组件。强行合并会造成 API 恶化：

### 1. resilience + fault_tolerance 合并 (~3000行)
- `resilience::hyper_resilience` → 熔断器 + 故障切换 + 自愈引擎（侧重请求级容错）
- `fault_tolerance` → 节点心跳 + 隔离组 + 集群健康（侧重节点级故障管理）
- 两者功能互补而非重叠。熔断器状态有交叉引用（`CircuitState` 通过 re-export 共享），但引擎本身处理不同抽象层
- **建议保持现状**，仅确保类型共享（已通过 `pub use` 实现）

### 2. 三个熔断器系统
| 位置 | 用途 |
|------|------|
| `acp::prelude::circuit_breaker::CircuitBreakerRegistry` | ACP 协议层熔断器注册表 |
| `resilience::hyper_resilience::CircuitBreaker` | 超弹性引擎内部熔断器（含故障模式追踪） |
| `optimization::failure_prevention::CircuitBreaker` | 遗留兼容包装器（标记为 "legacy"，有 `UnifiedCircuitBreaker` re-export） |

- ACP 熔断器是通用的注册表模式，hyper_resilience 熔断器是引擎内部的专用类型
- `CircuitState` 已通过 `pub use` 在两者间共享
- **建议保持现状**，legacy 包装器可在未来的清理中删除

### 3. 三个缓存系统
| 缓存 | 后端 | 用途 |
|------|------|------|
| `memory/cache.rs::ResponseCache` | SQLite/PostgreSQL | 持久化响应缓存 |
| `memory/memory_response_cache.rs::MemoryResponseCache` | In-memory IndexMap | 进程内 TTL 缓存 |
| `memory/semantic_cache.rs::SemanticCache` | In-memory + bigram Jaccard | 语义近似匹配缓存 |

- 三个不同用途、不同后端的缓存，统一为单一 trait 会造成不必要的抽象开销
- **建议保持现状**

### 4. 四个审计/溯源系统
| 模块 | 职责 |
|------|------|
| `governance::audit::ThreadSafeAuditLog` | agent/tool/phase 决策审计 |
| `governance::harness_bus::audit` | 策略审计 |
| `security::audit_integrity::HashChainAuditor` | 哈希链防篡改审计 |
| `observability::provenance::ProvenanceLedger` | 工具调用溯源 |

- 每个系统有不同的安全需求和数据模型。`security::audit_integrity` 的哈希链功能是安全审计的增强，`governance::audit` 是操作审计日志，`observability::provenance` 是工具调用追踪
- **建议保持现状**

### 5. Governance security_governor vs security 模块
- `governance::security_governor` → 安全策略执行引擎（允许/拒绝/审查）
- `security/` → 实际安全操作（漏洞扫描、注入检测、mTLS、密钥轮换）
- 策略执行器与实际安全操作的分离是好的架构设计
- **建议保持现状**
