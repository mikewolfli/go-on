## 1. 🟡 性能瓶颈

### 1.1 `hub/server.rs` — `set_nonblocking` 在 `from_std` 之前被调用

**文件**: `src/hub/server.rs` 第78行
**问题**: `listener.set_nonblocking(true)` 在 `TcpListener::from_std(listener)` 之前被调用。标准库的 `TcpListener::set_nonblocking` 转换到 tokio 后不再需要，tokio 的 `from_std` 会自动处理。
**影响**: 低（仅 hub 模块，非热路径），但违反了正确性模式。
**已有状态**: 此前日志已有记载，尚未修复。

### 1.2 全局静态锁竞争 — 多模块使用 `OnceLock<Mutex<T>>`

**文件**:
- `src/orchestration/tool/executor.rs:73` — `GOVERNANCE_CACHE: OnceLock<Mutex<GovernanceCache>>`
- `src/intelligence/hub.rs:47-57` — `GLOBAL_RATIONALIZATION: LazyLock<Mutex<...>>`, `GLOBAL_AUDIT: LazyLock<...>`

**问题**: 这些全局静态 Mutex 会在高并发下成为争抢点。虽然当前规模下影响不大，但在 multi-users-server 配置文件下多用户同时操作时可能成为瓶颈。

**建议**: 对 `GovernanceCache` 使用 `dashmap` 或 `RwLock` + 分片；对 `GLOBAL_RATIONALIZATION` 使用原子操作而非 Mutex 包裹整个 guard。

### 1.3 `ContinuousLearningCenter` 固定 5 分钟轮询间隔

**文件**: `src/main/mod.rs` 第294行
**代码**: `let mut interval = tokio::time::interval(std::time::Duration::from_secs(300));`

**问题**: 固定 5 分钟间隔，无法根据系统负载动态调整。空闲时期浪费资源，繁忙时期可能不够。

**建议**: 实现自适应间隔：低负载时 10 分钟，高负载时 2 分钟。或使用事件驱动触发而非轮询。

## 2. 🟡 冗余/重叠功能分析

### 2.1 BrainLoop vs PlannerExecutor — 深度重叠

| 维度 | BrainLoop | PlannerExecutor |
|------|-----------|-----------------|
| 位置 | `src/orchestration/brain_loop/` | `src/orchestration/planner_executor/` |
| 核心职责 | Plan→Execute→Reflect→Replan | Planner→Executor 分离 |
| Plan 生成 | `plan_construction::Planner` | 内部 `Planner`（已标记 `#[deprecated]` 指向 brain_loop） |
| 执行 | `execution::StepExecutor` | `execution::Executor` |
| DAG | `core_dag` 统一 DAG | `ExecutionPlan` 自包含 DAG |

**分析**: `planner_executor/mod.rs` 已标记 `Planner`、`TaskComplexity`、`DagMetrics` 为 deprecated 并指向 brain_loop。但 `Executor` 仍然是独立的。这意味着：
- `PlannerExecutor` 的 `execution.rs` 和 `BrainLoop` 的 `execution` 模块完全并行
- `ExecutionPlan`（PlannerExecutor 侧）和 `BrainLoopPlan`（brain_loop 侧）是两套计划类型
- 调用方需要知道使用哪个，增加认知负担

**结论**: `PlannerExecutor` 的 `Executor` 应重定向到 `BrainLoop::execution`，`ExecutionPlan` 应弃用并统一到 `BrainLoopPlan`。

### 2.2 FullAutoFlow vs MultiAgentPipeline — 功能重叠

| 维度 | FullAutoFlow | MultiAgentPipeline |
|------|-------------|-------------------|
| 位置 | `src/orchestration/full_auto/` | `src/orchestration/multi_agent_pipeline.rs` |
| 任务分解 | `intent` 模块 + skill 匹配 | `TaskDecomposer` |
| 并行执行 | `Semaphore` 控制并发 | `JoinSet` + 按 phase 分组 |
| 技能/工具 | skill_registry + tool_registry | AgentRegistry |
| 结果合成 | `report` 模块 | 内置 merged_output |

**分析**: 两者都做"接收任务 → 分解子任务 → 并行执行 → 合成结果"，但面对不同抽象层次：
- FullAutoFlow 面对 skill/tool 层
- MultiAgentPipeline 面对 agent 层

**建议**: 二者应共享同一套任务分解和并行执行核心。可将 `TaskDecomposer` 的 subtask → phase 映射抽象化，使 FullAutoFlow 也可以重用。目前 FullAutoFlow 有自己的 `intent` 模块做任务意图解析，与 `TaskDecomposer` 重叠。

### 2.3 三个工具执行引擎重叠

| 组件 | 功能 | 文件 |
|------|------|------|
| `loop_executor` | Think→Act→Observe 循环 | `src/orchestration/tool/loop_executor.rs` |
| `executor` (concurrent) | 批量并发工具执行 | `src/orchestration/tool/executor.rs` |
| `pipeline` | 顺序/并行 pipeline | `src/orchestration/tool/pipeline.rs` |

**分析**: 
- `loop_executor` 调用 `ToolRegistry::run_with_fallback_async` 做单工具执行 + 重试/切换
- `executor` 做批量工具并发 + 重试 + 熔断
- `pipeline` 做顺序 + 并行 groups

**重叠点**:
- `executor.rs` 和 `pipeline.rs` 都实现了 governance gate 检查（`check_tool_in_pipeline` 和 `is_low_risk_tool`）
- `executor.rs` 和 `loop_executor.rs` 都实现了重试逻辑
- `pipeline.rs` 的并行组功能和 `executor.rs` 的并发批处理重复

**建议**: 统一重试/熔断/governance 逻辑到 `exec/` 子模块，三个执行器都调用同一套原语。

### 2.4 两个 Flow 管理器

| 组件 | 文件 |
|------|------|
| `FlowManager` | `src/orchestration/flow.rs` |
| `FlowModelSelector` | `src/orchestration/flow_with_models.rs` |

**分析**: `FlowManager` 做 phase resolve，`FlowModelSelector` 做 model selection。但 `flow_with_models.rs` 又从 `flow.rs` 导入 `ResolvedRouting`，造成 `orchestration` → `flow` 的耦合。

**建议**: 将 model selection 逻辑内联到 `FlowManager`，或者作为 `FlowManager` 的一个可选扩展 trait。

## 3. 🔵 工具/Skill 调用链审查

### 3.1 工具注册和调用链路

```
识别任务 → 用户/系统请求
  → main/mod.rs run()
    → server::handle_validation_mode() / handle_chat_mode() / start_server()
      → ACP handler 接收请求
        → mode selector (orchestrator::select_mode_runtime_with_registry)
          → GenericModeRuntime::run()
            → 工具调用: execute_tools_concurrent() [executor.rs]
              或 loop_executor [loop_executor.rs]
              或 ToolPipeline [pipeline.rs]
                → ToolRegistry::get()
                  → Tool 实现 .run()
                    → Governance gate (check_tool + is_low_risk_tool)
                      → 结果返回
```

**阻塞点分析**:
1. **Governance gate 双重检查**: `executor.rs` 的 `is_low_risk_tool`（同步跳过）和 `pipeline.rs` 的 `check_tool_in_pipeline` 各自实现了类似逻辑。没有统一的 governance 入口。
2. **重试逻辑重复**: `executor.rs` 在 `execute_single_tool` 中实现了重试（208-245行），`loop_executor.rs` 也有自己的重试逻辑。
3. **缓存不一致**: `executor.rs` 有 `GovernanceCache`，但 `loop_executor` 和 `pipeline` 没有使用它。

### 3.2 Skills 注册和调用链路

```
启动 → bootstrap::perform_bootstrap()
  → SkillRegistry::discover_and_register_local_skills()  [扫描 ~/.agents/skills/]
  → SkillRegistry::register_builtin_skills()              [注册内置 skill]
  → 返回 SkillRegistry
    → main/mod.rs 包装在 Arc<RwLock> 中
      → 传给 server::start_server()
        → ACP 注册 skill_list / skill_execute 工具
          → 外部请求 → skill_list 列出 / skill_execute 执行
```

**阻塞点分析**:
1. **双重 Discovery**: `bootstrap.rs` 在启动时扫描本地 SKILL.md，之后在 `ToolRegistry` 初始化时还会注册工具。但技能和工具的发现路径没有统一。
2. **技能刷新**: 当前仅启动时发现一次，没有热刷新机制（虽然有 `spawn_skill_refresh_task`，但 bootstrap 中没有调用）。
3. **技能评分**: 技能评分数据在内存中，重启后丢失。没有持久化机制确保评分历史延续。

### 3.3 Skill 与 Tool 的调用流

当前的调用流中，Tool 和 Skill 是两个独立的 Registry：
- `ToolRegistry`（在 `orchestration/tool/mod.rs`）
- `SkillRegistry`（在 `orchestration/skill/registry.rs`）

两者没有共享的接口抽象。FullAutoFlow 同时持有两者，但各自独立执行。

**建议**: 统一 Tool 和 Skill 的执行接口，使它们可以通过同一套调度逻辑执行。
