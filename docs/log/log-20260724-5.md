### 蓝图匹配度：诚实评估

**Steer — 部分实现（75%），保留**

- 蓝图要求：`Mid-turn Steering` — 在 agent 处理过程中注入指令
- 实际实现：`Pre-turn instruction buffer` — 存入 `pending_instructions`，下一条 `UserMessage` 时注入 system prompt
- **差距**：无法中断正在进行的 `agent.chat()`。当前 Agent trait 不提供 `chat()` 中断 + 指令注入接口
- **保留理由**：在当前架构约束下是最佳可行方案。在 conversation 层级提供了指令注入能力（影响下一条响应）
- **诚实的文档注释**：已标注 "Not true mid-turn steering (cannot interrupt active agent.chat())"

**Checkpoint — 已重构为完整方案**

先添加了基础设施，再重新实现 Checkpoint：

1. `ConversationHistory::to_checkpoint_json()` — 将历史序列化为 JSON
2. `ConversationHistory::from_checkpoint_json()` — 从 JSON 反序列化恢复
3. Checkpoint handler：将序列化后的历史存入 `graph_store.upsert_edge()` 的 `task` 字段，status 标记为 "checkpoint"
4. `SessionHandle::checkpoint()` — 触发 checkpoint

**可观测行为**：checkpoint 后 graph_store 包含完整序列化历史，可通过 `list_descendants()` + `task` 字段读取用于恢复。

**差距**：当前是 InMemoryAgentGraphStore，进程重启后丢失。替换为 SQLiteAgentGraphStore 后即可实现完整持久化恢复。

## 5. 正收益重构

基于全面扫描，实施以下有确切正收益的重构：

### RF-1: `spawn_session` 返回 `Result` 替代 `panic!`

**文件**: `src/agents/session.rs:305-310`

**问题**: `AgentPath::parse("root").unwrap_or_else(|_| panic!(...))` — 路径解析
失败会导致服务器崩溃。

**重构**: 返回 `Result<SessionHandle, String>`，调用者决定错误处理。

**收益**: 防止服务器因路径解析崩溃，API 更规范。

### RF-2: 缓存 `root_path` 避免重复解析

**文件**: `src/agents/session.rs:250`

**问题**: `session_main_loop` 中 3 处独立的 `AgentPath::parse("root")` 调用。

**重构**: 将 `root_path` 存入 `SessionState`，所有 handler 使用 `state.root_path`。

**收益**: 减少 3 次冗余路径解析，消除 3 个可能的 `panic!` 点。

### RF-3: 移除 `#[allow(dead_code)]` 声明的 `EchoAgent`

**文件**: `src/orchestration/tool/extended/spawn_agent.rs:651`

**状态**: 已在 Round 3 完成。

### 重构影响

| 改动 | 文件 | 行数 | 风险 |
|------|------|------|------|
| `spawn_session` → `Result` | session.rs | ~8 | 低 — 所有调用点同步更新 |
| cache `root_path` | session.rs | ~15 | 低 — 纯替换，无逻辑变化 |
| 测试更新 | session.rs | ~10 | 低 — `.await.unwrap()` 模式 |

**结论**: 以上重构都是低风险、正收益的改进。无需大规模重写。

## 6. Steer 完美方案分析

### 问题

当前是 pre-turn 指令缓存（注入下一条 ChatRequest）。蓝图要求 mid-turn steering（
正在处理时注入）。

### 完美方案需要的架构变更

要让 `steer` 能在 agent `chat()` 进行中注入指令，需要修改 `Agent` trait：

```rust
pub trait Agent: Send + Sync {
    // 当前 —— 一次性调用，不可中断
    async fn chat(&self, messages, principles, options, sender) -> AppResult<()>;

    // 完美方案需要 —— 支持运行时指令注入
    async fn chat_with_steer(
        &self,
        messages, principles, options, sender,
        steer_rx: watch::Receiver<String>,  // ← 新增：steering channel
    ) -> AppResult<()>;
}
```

所有 25+ provider 实现需要在 HTTP 请求的 token 流式读取循环中增加 `steer_rx.try_recv()` 
检查。token 到达间隔通常是 10-50ms，在这个间隙检查 steering channel 是可行的。

### 成本收益分析

| 维度 | 当前（pre-turn） | 完美（mid-turn） |
|------|----------------|-----------------|
| 实现成本 | 0（已完成） | **极高** — 改 Agent trait + 25+ provider |
| 运行时开销 | 无 | 极低（每 token 间隔一次 try_recv） |
| 可用性提升 | 下一条消息生效 | 当前消息立即调整 |
| 实际使用场景 | 用户纠正 agent 方向 | 用户纠正 agent 方向 |
| 行为差异 | 先完成错误响应再纠正 | 立即纠正，节省一轮对话 |

**结论**: 收益有限（节省一轮对话），成本极高（改 25+ provider）。**当前 pre-turn 
方案是最优选择。**

## 7. Checkpoint 持久化层分析

### 问题

当前 `InMemoryAgentGraphStore`，进程重启后 checkpoint 丢失。

### 已实施的方案

`SqliteAgentGraphStore` 已在 `graph_store.rs` 中实现，通过 `#[cfg(feature = "backend-sqlite")]`
条件编译。

| 特性 | InMemory | SQLite |
|------|----------|--------|
| 依赖 | 无 | `rusqlite`（已存在） |
| 持久化 | ❌ 进程重启丢失 | ✅ 磁盘持久化 |
| 激活方式 | `Arc::new(InMemoryAgentGraphStore::new())` | `SqliteAgentGraphStore::open(path).await` |
| trait 接口 | 相同 | 相同 |
| 数据格式 | 相同 | 相同（JSON 序列化） |

### 切换方式

`SessionActor` 中只要替换一行：

```rust
// 当前（内存）
graph_store: Arc::new(InMemoryAgentGraphStore::new()),

// 切换为 SQLite
graph_store: Arc::new(SqliteAgentGraphStore::open("/path/to/graph.db").await?), 
```

无需修改任何其他代码。trait 多态隔离了存储实现。

### 成本收益

| 维度 | 当前 | SQLite |
|------|------|--------|
| 实现成本 | 0 | ~150行（已完成） |
| 运行时开销 | 0 | spawn_blocking（非阻塞） |
| 收益 | 进程内可用 | ✅ 进程重启恢复 |
| 迁移成本 | — | 0（trait 多态） |

**结论**: 正收益。已实现，按需激活即可。无需强制切换，`InMemory` 适用于开发，
`Sqlite` 适用于生产。
