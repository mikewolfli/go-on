## 第三部分：ZED Agent Server 启动延迟根因 — 最终结论

### 3.1 ZED vs go-on 架构本质差异

| 维度 | ZED（客户端） | go-on（服务端） |
|------|-------------|-------------|
| 核心瓶颈 | **外部子进程** fork+exec + LLM 模型加载 | **自身 SQLite 连接创建** + 组件初始化 |
| 延迟范围 | 3-10s | 优化后预估 <100ms |
| 是否可优化 | ❌ ZED 无法控制外部 agent 进程 | ✅ go-on 已在 S1-S6 优化 |
| block_task 数量 | **18 处**（桥接 Send→!Send） | **0 处** |
| 进程模型 | `Child::spawn()` 外部 ACP 进程 | 单进程内全部 async |

### 3.2 ZED 启动延迟分解（基于 `acp.rs:796-1006` `stdio()` 方法）

```
S1: ShellBuilder (~1ms)                  — 构建命令字符串
S2: Child::spawn (~30-100ms)             — fork+exec 外部 agent 子进程 ← 关键延迟
S3: connect_client_future (~10ms)        — 注册 ACP handlers
S4: await connection_rx (可变)            — 等待子进程 stdin/stdout 就绪
S5: InitializeRequest.send (~1ms)        — 发送 ACP 握手
S6: await initialize_response (2-8s)      ←★★★ 真正瓶颈：外部 agent 加载 LLM ★★★
S7: 250ms fallback timer                  — 超时优雅处理
```

**ZED Chat 的"实时"来自 UI 层**：`StreamingTextBuffer`（16ms tick, 200ms reveal）的平滑打字效果。但 **TTFT 仍受 S6 支配**（2-8s）。

### 3.3 go-on 启动延迟分解

| 阶段 | 优化前 | 优化后 | 优化手段 |
|------|--------|--------|---------|
| Bootstrap（i18n, skills） | 20-80ms | 20-80ms | 无变化（文件读不可避免） |
| AgentRegistry::from_config | 10-100ms | 10-100ms | 无变化 |
| try_join!(cache, vector, autotune) | 30-200ms | 30-200ms | spawn_blocking 已异步 |
| **new_acp_server MemoryPersistence ×2** | **100-400ms (SQLite)** | **~0ms (Lazy)** | S1+S5: OnceLock 延迟到首次使用 |
| wire_server (scheduler, skills, hub) | 10-50ms | 10-50ms | 无变化 |
| RBAC 注册 | 10-50ms | ~0ms (Background) | S2: 延迟到首次认证 |
| PolicyReloader 文件读取 | 5-20ms | ~0ms (Lazy) | S3: 存储路径，reload_all 时读取 |
| flow_manager TOML 解析 | 1-5ms | ~0ms (OnceLock) | S4: 全局缓存 |
| 背景任务初始化 | 30-80ms | ~0ms (Deferred) | S6: spawn 后 100ms 再启动 |
| **总计** | **170-830ms** | **~60-230ms** | **S1-S6 综合** |

### 3.4 go-on 能否做到与 ZED Chat 一样的"实时"？

**能，而且更快。** 因为：

- **go-on 启动关键路径更短**：无需子进程，`<100ms` vs `3-10s`
- **go-on 的 0 block_task**：全部 async，无 `Send→!Send` 桥接开销
- **go-on 的流式响应**：已有 ACP chunk 流支持，可对接 StreamMarkdownRenderer
- **go-on 的 TTFT**：仅取决于 LLM API 延迟，与 ZED Chat 完全一致（甚至更短，因为少一次 stdio 往返）

**ZED Chat 不可超越的优势**：UI 层集成度（GPUI Entity 系统 + StreamingTextBuffer 即打字机效果）。go-on 作为服务端，此能力需由客户端实现。

## 第四部分：GOON_THREAD 终极分析

### 4.1 什么是 GOON_THREAD

对标 ZED `AcpThread`：一个 GPUI Entity（Actor 模型），管理单个 ACP session 状态 + UI 渲染。它不是 OS 线程，而是事件驱动的 UI 组件。

### 4.2 为什么 GOON_THREAD 对 go-on 没有价值

| 权衡项 | 评分 | 解释 |
|--------|------|------|
| **消除 block_task** | 0/5 | go-on 无需 Send→!Send 桥接，全部 async |
| **状态管理** | 0/5 | 服务端无需管理 pending request 映射 |
| **事件循环统一** | 1/5 | tokio 已经在做这件事 |
| **与现有架构匹配度** | 0/5 | go-on 是服务端，不是编辑器 UI |
| **代码侵入性** | 4/5 | 需重建 dispatch 路径 |
| **性能开销** | 2/5 | 多一次 mpsc send + select |
| **可维护性** | 3/5 | 增加间接层，新成员需要学习 Actor 模式 |

**结论：不建议创建 GOON_THREAD**。go-on 的纯 async 函数式架构是正确选择。等价功能（Actor 式状态管理）已在 `AcpServer` + `SessionContext` 中通过 tokio 原生机制实现。

### 4.3 Transport Trait 统一 — 建议实施的替代方案

**比 GOON_THREAD 更实际、收益更高的替代方案**：

```rust
#[async_trait]
pub(crate) trait Transport: Send + Sync {
    async fn send_response(&self, response: JsonRpcResponse) -> Result<()>;
    async fn send_notification(&self, method: &str, params: Value) -> Result<()>;
    async fn send_sse_event(&self, event: &str, payload: &Value) -> Result<()> { Ok(()) }
}

struct StdioTransport;
struct RpcBufferTransport(Arc<Mutex<Vec<u8>>>);
struct SseTransport(tokio::net::TcpStream);
```

**收益**：
- 消除 `RPC_BUFFER` 隐式任务局部机制
- `StreamObserver` 可直接持有 `Arc<dyn Transport>`
- 为未来新增传输（WebSocket, Unix socket）提供清晰扩展点

**优先级**：🟢 低（下一轮实施）。当前架构已工作且零警告。

**核心优势**：安全中间代理 + ACP 协议穿透
- 企业级审计/审批/PII 脱敏
- 会话全生命周期管理
- 工具执行沙箱

**与 go-on 契合度**：**非常高**。go-on 的 `AcpServer` 实际上已经实现了 Claude Code Gateway 的所有核心功能：
- `harness_bus` + `capability_bus` → 企业治理
- `approval_engine` + `PuaRuleEngine` → 审批和策略执行
- `session_persistence` + `checkpoint` → 完整会话管理
- `InjectionDetector` + `SafetyChecker` → PII 脱敏和安全检查

**建议位置**：如果实现 Gateway 中间件层，应插入在 `transport_factory.rs` 的 `dispatch_server()` 之后、外部客户端之前。
