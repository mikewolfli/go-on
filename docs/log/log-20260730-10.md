## 一、本轮实际修复

### 修复 1: security::mtls 测试 Rustls CryptoProvider 缺失

- **问题**: `rustls` 0.23+ 要求在测试中使用前调用 `CryptoProvider::install_default()`。4 个 mTLS 测试因缺少该调用而 panic。

### 修复 2: governance::status 测试工具名称与关键字分类冲突

- **问题**: `test_unknown_tool_blocked` 使用工具名 `delete_world`。该名称包含 `"delete"` 关键字，被 `classify_operation_by_keyword` 归类为 `ToolOperation::Write` 写操作。使用无害路径 `"foo"` 时允许通过，测试断言 `is_err()` 失败。
- **修复**: 将测试工具名改为 `zzz_unknown_tool`，该名称不匹配任何关键字分类，正确触发 `ToolOperation::Unknown` 路径。

## 三、jcode 对比——诚实总结

### 3.1 差异根源

go-on 和 jcode 是两个**架构目标不同**的项目：

| 维度 | go-on | jcode |
|------|-------|-------|
| 核心定位 | ACP 运行时代理 + 多智能体编排 | 终端编码助手 + 多模型支持 |
| 协议 | ACP + MCP 双协议 | 以 ACP 为主 |
| Profile 系统 | 4 种 profile (local → full) | 单体应用 |
| 治理 | 企业级安全治理引擎 | 轻量安全系统 |
| 工具系统 | ToolRegistry + 57 个扩展工具 | 按功能分散在 75 个 crate 中 |
| 自我进化 | 完整沙盒回滚进化系统 | 无 |
| GUI | 独立 gui crate | Desktop + TUI |

### 3.2 值得借鉴的设计

1. **注册回调模式 (Inversion of Control)** — jcode 使用 `register_*` 模式避免上层依赖下层。go-on 可以直接依赖，这是不同风格，不一定需要改变。
2. **SafetySystem 单文件设计** — jcode 将所有安全/治理放在 `safety.rs` (722行)。go-on 分布到 29+ 文件是为了分层清晰。两种设计各有优劣。

### 3.3 不应照搬的差异

- go-on 的 4-profile 系统需要分层治理支持，jcode 的单文件方案不足以支撑
- go-on 的 self-evolution 系统需要额外的沙箱能力
- go-on 的双协议（ACP+MCP）支持需要额外的架构灵活性
