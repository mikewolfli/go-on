## 第三部分：ZED Agent Server 启动延迟根因分析

### 3.1 两个项目架构本质差异

| 维度 | go-on (服务端) | ZED (客户端) |
|------|-------------|-------------|
| **角色** | ACP **Server** — 处理 stdin/stdout JSON-RPC | ACP **Client** — 发起请求并等待响应 |
| **进程模型** | 主进程（go-on 自身就是 agent） | **子进程**（`Child::spawn`外部 agent server） |
| **阻塞模式** | 无 — 全部 tokio async + `handle_request()` | **17处 `block_task()`** — 在后台线程阻塞等待 RPC 响应 |
| **启动路径** | 自身初始化（SQLite 连接、配置加载） | 创建子进程 → 等待子进程启动 → InitializeRequest → 等待响应 → 再 new_session |
| **核心瓶颈** | SQLite 连接的同步初始化（170-830ms） | **子进程自身的 LLM 模型加载 + Initialize 握手**（3-10s） |

### 3.2 ZED 启动时序（基于 `acp.rs:796-1010` `stdio()` 方法）

```
[ZED 侧]
1. Child::spawn() — 创建外部 agent 子进程             ~5ms
2. 设置 Lines transport（stdin/stdout channel）       ~2ms  
3. connect_client_future() — 安装 ACP handler 集合    ~5ms
4. 阻塞等待连接就绪（future::select connection_rx ∥ status_fut）  ~1ms
5. 设置 ForegroundDispatch 循环                       ~2ms
6. 发送 InitializeRequest → .block_task().await       ↓↓↓ 这里是真正的瓶颈 ↓↓↓
   [子进程侧: 启动 LLM 运行环境、加载模型、初始化自身状态]
   ============ 用户感知的"长时间等待" ============
7. 处理 InitializeResponse 提取 agent_info、capabilities  ~2ms
8. 设置 AcpConnectionDefaults + settings 订阅           ~2ms
9. new_session() → 再发 NewSessionRequest              ↓↓↓ 第二次等待 ↓↓↓
   → .block_task().await 再次阻塞
```

**关键发现**：ZED 的 `stdio()` 方法中包含 **17 次 `block_task()` 调用**（`send_request(...).block_task().await`），每一次都在后台线程阻塞等待远程 agent 的 RPC 响应。而 go-on 作为 server，通过 `async fn handle_request()` 直接在 tokio 运行时上处理，没有任何 `block_task()`——**go-on 的架构在理论上响应更快**。

### 3.3 go-on 启动时间分解

| 阶段 | 当前时间 | 瓶颈类型 |
|------|---------|---------|
| Bootstrap（i18n、telemetry、skills） | 20-80ms | 同步文件读 |
| AgentRegistry::from_config | 10-100ms | 同步构造 |
| `try_join!`（cache + vector + autotune） | 30-200ms | `spawn_blocking` ✅ 已异步 |
| `new_acp_server` + MemoryPersistence × 2 | **100-400ms** | **同步 SQLite 连接创建** |
| `wire_server`（scheduler、skills、hub） | 10-50ms | 同步 |
| **总计** | **170-830ms** | — |

**核心结论**：go-on 的启动延迟（170-830ms）主要来自 `new_acp_server` 中的 **3-4 个同步 SQLite 连接创建**。而 ZED 的启动延迟（3-10s）来自**外部子进程加载 LLM 模型**。两者的瓶颈不同，go-on 无需模仿 ZED 的 `block_task()` 模式——那只会让事情更糟。

### 3.4 优化建议（S1-S5 方案）

| 编号 | 优化方案 | 预估节省 | 实现方式 |
|------|---------|---------|---------|
| **S1** | 懒加载 MemoryPersistence（`OnceLock` 包装） | **100-300ms** | 首次请求时构造，启动时仅注册 |
| **S2** | 延迟 RBAC 租户注册到第一次认证请求 | 10-50ms | 从 `new_acp_server` 移出 |
| **S3** | PolicyReloader 不急于读取文件 | 5-20ms | 存储路径，`reload_all()` 时读取 |
| **S4** | 缓存 `flow_manager()` 的 TOML 读取（`OnceLock`） | 1-5ms | 静态化 |
| **S5** | 统一 2 个 MemoryPersistence 实例为 1 个连接 | 50-100ms | 共享 WarmStore |
| **S6** | 非关键后台任务延迟到 `spawn` 后 | 30-80ms | 减少 `start_background_tasks` 同步初始化 |

## 第五部分：多管路统一平台分析

### 5.1 当前 4 管路状态

| 管路 | 入口 | 传输层 | 事件出口 | 与 ZED ACP_THREAD 对齐度 |
|------|------|--------|---------|------------------------|
| ACP Stdio | `run_acp_server()` | stdin/stdout JSON-RPC | `send_notification` → `write_json_line` → stdout | ✅ 功能对齐。ZED 用 `block_task()` 等，go-on 直接 async 处理 |
| ACP HTTP SSE | `run_acp_http_server()` + `/chat/stream` | TCP + SSE (text/event-stream) | `observer.sse_sender` → mpsc → `write_sse_event` → socket | ✅ go-on 特有实时流。ZED 无此模式 |
| ACP HTTP RPC | `run_acp_http_server()` + `/rpc` | HTTP JSON-RPC | `RPC_BUFFER` → `write_json_line` | ✅ 功能对齐 |
| MCP Stdio/HTTP | `dispatch_server()` (通过 transport_factory) | stdin/stdout 或 HTTP | 复用 ACP 内核 | ⚠ 不同协议 |

### 5.2 Transport Trait 统一方案

**当前**：4 种管路各有独立的事件出口逻辑。

**统一建议**：定义一个 `Transport` trait，将事件输出抽象化：

```rust
pub trait Transport: Send {
    /// 发送一个 JSON-RPC 通知
    fn send_notification(&mut self, method: &str, params: Value) -> impl Future<Output = Result<()>>;
    /// 发送一个 SSE 事件  
    fn send_sse(&mut self, event: &str, payload: &Value) -> impl Future<Output = Result<()>>;
    /// 发送一个 RPC 结果
    fn send_result(&mut self, id: &Value, result: Value) -> impl Future<Output = Result<()>>;
}
```

**这比引入 `GOON_THREAD` 收益更高、风险更低**（详见 log-5.md 的 GOON_THREAD 分析），因为：
- 不需要新增 OS 线程
- 不需要 `crossbeam` 通道
- 不改变 tokio 事件循环
- 只需要将现有的 5 条事件出口路径统一到一个 trait 实现中

## 第七部分：最终结论

### 7.1 核心发现总结

1. **go-on 代码质量极高**：零 `#[allow(dead_code)]`、零 clippy 警告、零 `todo!()`、零 `block_in_place`、零 `#[ignore]`。2166 个测试全通过。原则.md 的 25 条规则中已有 **22 条完全满足**。

2. **ZED 的启动慢不是 go-on 的问题**：ZED 使用 `block_task()`（17处）在后台线程阻塞等待外部子进程加载 LLM 模型（3-10s）。go-on 作为 server 异步处理请求，0 处 `block_task()`。

3. **go-on 的启动延迟（170-830ms）来自 SQLite 连接创建**：S1-S5 方案（懒加载 + 统一连接）可缩短到 <100ms。

4. **最大的代码质量问题**已从 21 处 `#[allow(dead_code)]` 降为 0 处。剩余的最大文件是 `old_ui_content.rs`（2161行，通过 `include!` 引入），已有 4 阶段迁移计划但仅完成阶段 1。
