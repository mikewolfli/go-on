# Log 2026-08-14 #2 — go-on × Hermes × Codex 三方全面对比分析

> 对比对象：
> - **go-on**（本仓库，Rust）：AI 智能体编排运行时
> - **Hermes Agent**（`/home/mikeli/workspace/hermes-agent/`，Python，Nous Research）：自我改进的个人 AI 员工
> - **Codex CLI**（`/home/mikeli/workspace/codex/`，Rust+TS，OpenAI）：编码执行器
>
> 民间定位："用 hermes 编排任务，用 codex 完成任务"。本报告验证此定位、做三方全维度对比，并给出 go-on 的**精炼 / 增加 / 清理**三份行动清单。
> 分析方式：三方均基于源码实证（行数、模块、关键函数），hermes 与 codex 由独立子代理深扫，go-on 为本仓库实测。

## 1. 执行摘要

| | **go-on** | **Hermes** | **Codex** |
|---|---|---|---|
| 定位 | 本地优先、生产级**编排运行时**（治理+多协议+韧性） | **个人 AI 员工**（常驻、记忆、技能自我进化、多平台） | **编码执行器**（单任务到底、极简循环） |
| 语言 | Rust（449 文件 / 21.2 万行） | Python（4136 文件 / 89.1 万行） | Rust（3065 文件 / 75.8 万行，~120 crates） |
| 核心循环 | OODA 四阶段（observe→think→act→reflect）+ 模式运行时 | 会话循环 + 后台学习线程 + cron ticker | 模型驱动的 turn loop（采样→工具→再采样） |
| 治理 | ✅ HarnessBus / RBAC / 审计链 / 注入检测 / 韧性 / 混沌 | ❌ 无（单用户） | ⚠️ 弱（requirements.toml 组织约束 + 诊断级审计） |
| 记忆 | 会话压缩 / 上下文预算 / AgentMemoryBus / warm.db | ✅ FTS5 跨会话搜索（CJK 分词）+ 8 家记忆提供商 | 会话持久化（thread-store），无学习型记忆 |
| 技能 | 34 个内置 + GitHub/URL/本地导入 + 自动发现 | ✅ 81 个 + **从经验自动创建 + 自我改进 + 策展** | 无独立技能系统（prompt 模板化） |
| 多平台 | GUI / CLI / Zed / VS Code | ✅ **28 平台网关**（Telegram/Discord/Slack/…） | CLI / IDE / 桌面 / 云 |
| 供应商 | 37 家（6 家原生 function call） | 声明式 ProviderProfile，多端 | 重心 OpenAI（Bedrock/ollama 适配） |
| 协议 | ACP + MCP（stdio/http）+ SSE + OpenAI 兼容 | ACP 服务器 + MCP（client/server） | Responses API + MCP + app-server JSON-RPC |
| 沙箱 | shell 沙箱（bwrap 检测）+ 写沙箱（50MiB+系统路径拦截） | 8 种终端后端（local/docker/ssh/…），子代理**进程内无隔离** | ✅ 三平台沙箱（bwrap/seatbelt/windows）+ 网络 MITM + apply_patch 收口 |
| 测试 | 1724 测试声明（lib 实测 1646 全绿） | 207 测试文件 | Bazel+Cargo 双轨 |

**定位结论**："用 hermes 编排、用 codex 完成"的说法基本成立，且三方是**互补三角**而非竞争：hermes 强在**长时记忆与任务编排的广度**（跨会话、无人值守、多平台），codex 强在**单任务执行的深度与确定性**（可编程接口、沙箱、事件契约），go-on 强在**生产级治理与协议面**（RBAC/审计/多协议/韧性）——但 go-on 在"编排智能"（记忆/技能闭环）和"执行器接口"（可编程、沙箱收口）两头都还有可借力之处。

## 2. 架构哲学对比（核心洞察）

### 2.1 循环边界由谁决定

| | 循环驱动 | 含义 |
|---|---|---|
| go-on | **编排器**决定（OODA 状态机 + 模式运行时 + DAG 工具图） | 可预测、可治理，但灵活性依赖编排器的正确性 |
| Hermes | 会话循环 + **后台线程**（学习/策展/压缩异步化） | 主循环保持轻，学习行为异步收敛 |
| Codex | **模型**决定（`end_turn=false` → 继续采样） | 极简、贴近模型能力，循环终止完全交给模型 |

**洞察**：codex 证明"模型驱动循环 + 单一事件流"可以支撑完整编码任务；go-on 的 OODA 更适合**高风险/多租户场景**（需要阶段化管控），但 observe/think 阶段若只是"等模型"，则编排器的价值主要体现在 act 阶段的工具编排与治理。

### 2.2 输出契约（codex 最值得学的一课）

```
go-on:   StreamFrame(chunk/done/telemetry/status/phase/sub_agent/command/tool_approval/error/result)
          → ACP bridge（session.rs 手写 match）
          → GUI（runtime.rs 手写 match）
          → CLI（cli/chat.rs 又一套 classify_token）
          → dispatch.rs（JSON-RPC 通知）        # 四套独立解析同一语义流
codex:   EventMsg（core 内部）→ ServerNotification（JSON-RPC）→ ThreadEvent（对外 JSONL 契约）
          TUI / TS SDK / IDE 消费同一条语义流；类型由 Rust ts-rs 生成，SDK 零手写类型
```

**go-on 的问题**：同一个流式语义在 ACP bridge / GUI / CLI / dispatch 被**解析四遍**，且已出现漂移（上一轮修复：GUI 忽略 status/phase 帧并计入 sse_errors；ACP bridge 丢 done 事件 response 字段——同一类缺陷在四处各自为政）。codex 的"单一契约 + 类型生成"是根治法。

### 2.3 安全边界（codex）vs 隔离缺口（hermes）

- codex：沙箱即第一公民（三平台），文件写**收口到 apply_patch 单一工具**并预验证 + `TurnDiffEvent` 可审查
- hermes：子代理**进程内线程**（GIL、共享全局状态、无隔离），靠 `_sanitize_*` 打补丁；8 种终端后端是执行环境隔离的主力
- go-on：有 shell 沙箱 + 写沙箱（50MiB + 系统路径拦截，R45 F8 补的 edit_file 漏洞），但**文件写未收口**（write_file/apply_patch/edit_file 三套入口、各自沙箱），缺少 codex 式"所有修改都可 diff 化审查"的闭环

### 2.4 记忆与技能：hermes 的护城河，go-on 的差距

| 能力 | Hermes | go-on 现状 | 差距 |
|---|---|---|---|
| 跨会话记忆搜索 | FTS5 + **CJK bigram 分词** + BM25 | 会话压缩/上下文预算（仅单会话窗口） | go-on 无跨会话全文检索 |
| 技能从经验创建 | 会话后后台线程自动提炼（`background_review.py`） | 技能是**预置 34 个** + 手动导入 | go-on 无"用后沉淀"闭环 |
| 技能自我改进 | 使用计分 + curator 合并/归档 + 图谱可视化 | 无 | 技能是静态资产 |
| 无人值守编排 | cron 文件锁 tick + 结果回送平台 + durable delegation（崩溃恢复） | 有 background tasks（进化/维护）但**无用户级 cron**、无"结果投递" | 编排深度差距 |

## 3. go-on 需要**精炼**的功能（向 codex 的极简哲学对齐）

> 原则：codex 用"采样→工具→再采样"单循环 + 单一契约支撑了 75 万行工程，说明**核心语义的精简**比功能堆叠更能抗复杂度。

### P1-1. 统一流式事件契约，消灭四套重复解析
- **现状**：StreamFrame 已统一事件载体，但消费方各写一套：`session.rs` bridge（ACP）、`gui/.../runtime.rs process_stream_events`、`cli/chat.rs classify_token`、`dispatch.rs`。
- **动作**：抽出单一 `stream_event_consumer`（事件类型 + chunk 字段提取 + reasoning/token 分离），四处改为调用同一实现；把 `extract_chunk_text`（GUI）与 bridge 的 reasoning/token 分支、CLI 的 `classify_token` 三合一。上一轮发现的 GUI 漏处理 status/phase、bridge 丢 done.response，正是分叉漂移的实例。
- **收益**：同类缺陷只修一处；为"类型生成"打基础。

### P1-2. 供应商适配从"每家一个 agent 文件"精炼为声明式 Profile
- **现状**：37 家供应商分散在 `agents/*.rs`（anthropic/deepseek/gemini/…各一文件），仅 6 家原生 function call，其余 31 家是 OpenAI 兼容适配。
- **借鉴**：hermes 的 `ProviderProfile` dataclass（一个声明描述供应商全部怪癖）+ codex 的 `ModelProvider` trait。
- **动作**：把"url / api_format / 认证方式 / function_call 支持 / 流式格式"收敛为一张声明表（如 `shared/provider_profiles.rs`），每家一个 Profile 条目，删除逐家重复的 normalize/thinking/streaming 样板。**同时评估 31 家弱适配中无真实用户的是否降级为"配置可注册"而非"代码内建"**。

### P1-3. 文件写操作收口（向 codex apply_patch 对齐）
- **现状**：write_file / apply_patch / edit_file / read_file_lines 多入口，沙箱规则三份（R45 F8 已补 edit_file 漏洞，说明是打补丁式维护）。
- **动作**：定义单一"写操作中间表示"（path + 目标内容 + 模式），所有写工具经同一沙箱校验 + 同一 diff 记录；输出"变更事件"（类似 `TurnDiffEvent`）供 GUI/审计消费——让每次修改都可审查。

### P2-4. 大文件拆分（对照 codex 单文件 1.2 万行的反面教材与 hermes 3 万行 god file）
- **现状**：go-on 最需关注 `chat_phases.rs`（2354 行，4 个 phase + 大量辅助函数）、`session.rs` 等大文件；R45 已拆 `chat.rs`、`main.rs` 的一部分。
- **动作**：把 `chat_phases.rs` 按 phase 拆为 `phases/observe.rs`、`phases/think.rs`、`phases/act.rs`、`phases/reflect.rs` + 共享 `phases/helpers.rs`。**控制单一职责文件 ≤ 1500 行**。

### P2-5. 消息/思维流标记双轨合一
- **现状**：后端 `TOKEN_THINKING_PREFIX = "__thinking__"` 协议标记，GUI 又维护一份 `THINKING_MARKER` + `split_thinking_from_content`，两端对"thinking 如何嵌入 token 流"各自理解。
- **动作**：让 GUI 只消费 SSE 的 `reasoning` 字段（后端已在 chunk 里分离），删除 GUI 的 marker 拆分逻辑；若保留 marker 兼容，则常量下沉到共享契约文档。

## 4. go-on 需要**增加**的功能（借鉴 hermes 的编排智能 + codex 的执行器接口）

### P1-A. 技能从经验自动创建的闭环（hermes 核心护城河）
- **现状**：go-on 有 34 个内置技能 + 导入/发现，但技能是**静态资产**。
- **借鉴**：hermes `background_review.py`（会话结束后台线程提炼技能/记忆）+ `skill_manager_tool.py`（agent 可直接 create/update/delete 技能）+ `skill_usage.py`（使用计分）。
- **动作**：
  1. 会话结束后（reflect 阶段旁路）异步提炼"本任务可复用方法"→ 生成 SKILL.md 草稿（agentskills.io 格式，go-on 已兼容）；
  2. `skill_execute` 增加 `skill_create/update` 权限（受 RBAC 门控）；
  3. 技能使用计分 → 低频技能自动归档/合并（`curator` 状态机），高频技能置顶。
- **收益**：从"预置技能库"进化为"越用越强的技能市场"——这是 go-on 与 hermes 差距最大的单点。

### P1-B. 跨会话记忆全文搜索（hermes FTS5 + CJK）
- **现状**：go-on 记忆是"当会话上下文"（压缩/预算），无跨会话检索。
- **借鉴**：hermes `hermes_state_search.py`——SQLite FTS5 外部内容表 + **CJK bigram 分词器**（中文 2 字符查询必须） + BM25 + LIKE 降级。
- **动作**：基于现有 warm.db 消息表加 FTS5 索引（Rust 侧 SQLite 已具备，sqlite-vec 已引入，FTS5 是内置扩展）；新增 `memory.search` 工具（跨会话关键词检索 + LLM 摘要）；纳入上下文预算门控（防注入过长历史）。
- **收益**：跨会话连续性（用户："之前那个 bug 后来怎么修的？"可检索）。

### P1-C. 可编程执行器接口（codex `exec --json` 式）
- **现状**：go-on 有 ACP stdio / MCP / SSE，但对"外部程序调用一次拿结果"的场景，无 codex 那种**非交互、JSONL 严格输出、headless 默认放行、可输出 schema** 的入口。
- **借鉴**：codex `exec/src/` —— `--json` 时 stdout 只允许 JSONL（`#![deny(clippy::print_stdout)]`），事件契约稳定（turn.started/completed + item.*）。
- **动作**：新增 `go-on exec` 子命令（或 `--one-shot` 模式）：`go-on exec --json "prompt"` → 单轮或有限轮执行 → stdout 纯 JSONL（thread/turn/item 事件）→ stderr 日志；默认 `AskForApproval::Never`（可配置）。让 hermes 这类编排器能像调 codex 一样调 go-on。

### P1-D. 审批链路分层（codex hook → 自动审核 → 用户）
- **现状**：go-on 有 SafeGuard 模式 + 审批门控（`ensure_tool_permission` / `request_client_permission`），但缺"**hook 预决策层**"和"**独立 reviewer 模型自动审核层**"。
- **借鉴**：codex `approvals.rs` 优先级链：permission hooks（可 Allow/Deny/改写）→ Guardian reviewer 会话（模型审模型，适用于 strict 模式）→ 用户弹窗。
- **动作**：新增 `permission_hooks` 配置（外部命令/脚本预审批，返回 allow/deny/override）；Guardian 层可选启用（低风险调用自动放行、高风险才弹窗），降低 SafeGuard 的交互打断频率。

### P2-E. 无人值守编排：用户级 cron + 结果回送 + durable delegation
- **现状**：go-on 有 background tasks（内部维护/进化），无用户级定时任务。
- **借鉴**：hermes `cron/scheduler.py`（文件锁 tick、job 防重叠、usage 审计、**结果镜像投递到平台会话**）+ `async_delegation.py`（SQLite 持久化子代理、崩溃恢复、claim 交付）。
- **动作**：`workflow` 增加 cron 触发器（croniter 解析，复用现有 workflow.execute 契约）；`spawn_agent` 工具增加 durable 模式（任务落盘 + 崩溃后恢复 + 结果回执）；结果投递优先接 GUI 通知 + 后续平台网关（见 P2-F）。

### P2-F. 多平台接入（hermes 28 平台网关的架构模式）
- **动作**：若 go-on 要做常驻助手，复制 hermes 的**架构模式**而非代码：platform registry + adapter 接口 + 会话哈希（平台+chat_id）+ turn 租约锁 + 送达账本。先支持 1-2 个平台（Telegram/企业微信）验证模式。**不建议**模仿其单进程 3 万行 god file。

### P2-G. 事件类型从 Rust 生成 SDK 类型（codex ts-rs）
- **现状**：go-on 有 Rust/Python/TS 三个 SDK，事件结构手写三份，漂移风险。
- **动作**：对流式事件/工具描述引入类型生成（Rust 侧 `#[derive(TS)]` 或同类），TS SDK 直接 import 生成类型；工具描述（JSON Schema）也由 Rust 侧结构导出而非手写字符串（消除 R45 F4 那类"描述与实现不符"）。

## 5. go-on 需要**清理**的功能（对照三方实证）

### P1-①. 流式/工具协议的死分叉（立刻做，见 3.P1-1）
四套解析各自为政已产生真实缺陷（上一轮两处），合并后自然消灭重复。

### P1-②. 弱适配供应商的占位面
31 家非原生 function call 供应商中，若有从未被配置/测试触达的，从"代码内建"降级为"配置注册"（`agents.<name>.type = "openai_compat"` + base_url/模型表），减少每供应商一个文件的维护面。**保留声明入口但删除独占代码路径**。

### P2-③. 未消费的治理/韧性边缘
- R45 记录"code_repo_analyzer 死错误变体、ResilienceLevel::Enhanced 死枚举变体"等因 pub API 保留——**评估收紧为 crate-private**；
- 混沌测试 14 种故障注入、5 个容错恢复动作：保留核心（熔断/故障切换），清除未接入调度器的注入点；
- `F-GAP-49` 系列 `#[allow(dead_code)]`：逐个验证后**要么接线要么删除**，不许长期挂着 allow。

### P2-④. 前端重复（go-on 相对较轻，但可防）
GUI / VS Code / Zed 三端对同一 SSE 契约各写解析；统一事件契约（P1-1）后，三端只保留"渲染"差异。

### P3-⑤. 技能市场的展示合并名
README 已注明 analyze-text←classify-text 等合并展示名——**技能名与实现名不一致是技术债**，统一命名或明确别名表。

### P3-⑥. 文档与代码的漂移
README 统计（1555 vs 实测 1646 测试、37 供应商等）随每次变更漂移；建议把统计改为 CI 生成（`scripts/` 里加一个统计脚本，回写 README）。

## 7. 一句话总结

- **go-on 的不可替代性**：治理（RBAC/审计链/注入检测）+ 协议面（ACP/MCP/SSE）+ 韧性——这是 hermes 和 codex 都没有的"生产级编排"底座。
- **go-on 最大的两个差距**：① **编排智能**——没有 hermes 的技能自我进化闭环和跨会话记忆检索（"编排"目前更多是流程编排，而非智能编排）；② **执行器接口**——没有 codex 的单一事件契约和可编程 exec 入口（"完成"的落地路径不够顺滑）。
- **go-on 最该防止的**：向 hermes 学习时**只学模式不学 god file**；向 codex 学习时**只学契约不学平台绑定**（保持多供应商/多协议中立，这是 go-on 相对 codex 的优势）。
- **精炼、增加、清理的优先级**：先精炼（统一契约、供应商 Profile 化）→ 再增加（技能闭环、记忆搜索、exec 接口）→ 最后清理（dead_code、弱适配降级）。精炼是增加的前提，否则新功能会继续落在四套分叉之上。

## 8. deepseek-harness（`dsh`）："一切都是插件"架构专项分析

> 对比对象：`/home/mikeli/workspace/deepseek-harness/`（TypeScript，1981 文件 / 42.9 万行，pnpm workspace）。
> 定位：DeepSeek 官方 agent harness，预发布（明言会有兼容性破坏）。核心卖点：**everything is a plugin**，基于自研/内嵌的 [Cordis](https://github.com/cordiverse/cordis) 框架。

### 8.1 它是什么：不是"插件系统"，而是"插件即一切"

普通项目的"插件"是核心之外的附加物；dsh 的**核心本身也是插件**——模型适配器、工具注册表、会话日志、甚至 agent 主循环都以插件形式挂在 Cordis 插件树上，**没有特权核心**（架构文档原文："There is no privileged core to patch"）。

- **运行时插件树**：一次运行 = 从有序层组合出的插件树。profile（命名组合）→ bundle（可分发配置层）→ `cordis.patch.yml`（用户补丁，按行 id 替换/插入）逐层叠加；`dsh --profile web --dump-config` 可打印整棵树，**任何一行都能被补丁替换**。
- **能力缝（seam）**：一个可替换能力 = 三件套：**Service Definition**（接口声明）+ **Service Provider**（实现）+ **Consumer**（模型工具）。换一个 provider 即改变全产品行为。实例：`fs` seam 拆成 `fs`(定义) + `fs-local`(本地) + `fs-sandbox`(沙箱) + `tool-fs`(消费工具) + `fs-observation-policy`(策略) 五个子包；`e2b/subprocess-e2b` 让远程沙箱复用同一套 subprocess 接口。
- **三层事件域**：`session/*`（持久事实，落盘可重放）、`agent/*`（live：inbox/step/status/request/continuation，可观察/拦截/注入）、`capability/*`（策略与适配器挂接缝）。其中 `agent/pre-step`、`agent/request`、`llm/stream`、`tools/*` 是**瀑布事件**（监听者必须 `next()` 委派），`agent/turn-stopping` 是串行拦截点。
- **强不变式："Model-visible means logged"**——任何进入模型请求的内容必须能从 append-only 会话日志重建（fork/resume/重放/审计/UI 全从日志派生），并有运行时断言强制。
- **step/turn 模型**：step = 一次模型请求+其工具调用；turn = 0..n 个 step，turn 在首个输入认领时开启、无欠账时关闭——循环边界由"模型是否欠工具结果"决定（与 codex 同哲学）。

### 8.2 优势（"一切是插件"到底好在哪里）

| # | 优势 | 机制 | 对应 go-on 现状 |
|---|---|---|---|
| 1 | **无特权核心**：扩展无需 fork/patch 核心，所有扩展点同构 | 核心（session/tools/agent-loop）也是插件 | go-on 扩展主要靠 trait + 特征门控，改行为需改核心代码 |
| 2 | **配置即组合**：同一二进制，profile/bundle/patch 组合出不同产品（web/headless/ACP/JSON-RPC） | 分层补丁树 + `--dump-config` | go-on 用 config.toml + 特性门控（编译期），无"运行时组合"概念 |
| 3 | **可替换性**：换 provider 全产品跟随（远程沙箱移动 Bash/PTY/LSP） | seam 三件套 | go-on 沙箱/fs/shell 逻辑分散在多个工具里（R45 已发现沙箱规则三份） |
| 4 | **卸载即回滚**：注册是可逆 effect，插件卸载自动展开，无残留状态 | Cordis 效果系统 | go-on 无运行时卸载概念 |
| 5 | **事件即扩展点**：观察/拦截/注入不用改循环 | 三层事件域 + 瀑布事件 | go-on 事件主要在传输层（StreamFrame），无 agent 生命周期事件域 |
| 6 | **日志即事实源**：会话可 fork/resume/重放，审计与 UI 同源 | Model-visible means logged + 运行时断言 | go-on 有审计链但模型上下文不从日志派生 |
| 7 | **self-modification 潜力**：agent 可挂载/卸载自己的插件（AGENTS.md 有 `packages/self-modification/` 条目，本 checkout 未落地） | 运行时插件树 | go-on 的 self_evolution 是改源码重编译，非运行时 |

### 8.3 劣势（代价是什么）

| # | 劣势 | 证据/机理 |
|---|---|---|
| 1 | **样板与间接层重**：每个能力都要设计三件套 + 事件域；连 todo/plan 这种小功能也做成 seam + 工具双包 | 每个 pkg 恒有 `src/index.ts` + `src/invariant.ts` + `tests/*.spec.ts` |
| 2 | **调试与溯源难**：行为分散在插件树，运行时谁挂载了什么只能靠 `--dump-config` 静态看，动态交互难追踪 | 插件树 + 瀑布事件链 |
| 3 | **类型安全靠运行时补**：TS 无编译期保证，每个包用 `invariant.ts` 运行时断言兜底——本质是用测试补偿类型系统 | 1981 文件里 invariant.ts 遍布 |
| 4 | **性能**：事件广播 + 动态注册 + 解释执行；对高吞吐流式不友好 | TS + Cordis 运行时 |
| 5 | **安全面**：运行时补丁 + self-modification = 插件能改一切，治理（RBAC/审计）若不做在插件层即失效 | 无内置 RBAC |
| 6 | **兼容性成本**：预发布明言 break；"一切可替换"让生态稳定前内耗大 | README："THERE WILL BE COMPATIBILITY-BREAKING CHANGES" |
| 7 | **过度抽象风险**："一切是插件"会诱使简单问题复杂化；50 个包维护面巨大 | 1981 文件 / 42.9 万行 |

### 8.4 对 go-on 的启示：能改什么、不能改什么

**Rust 的天生优势**（dsh 用 TS 运行时机制补的，go-on 编译期就有）：类型安全、无 GC、单二进制部署。所以 go-on **不应**照搬"运行时补丁改一切"——那会丢掉 Rust 的安全与可审计性。**应该**借鉴的是 dsh 的**架构形态**：

| 借鉴点 | 落地方式（Rust 版） | 优先级 |
|---|---|---|
| **能力缝（seam）三件套** | 把 fs / subprocess / sandbox / terminal 抽成统一 seam：`trait XxxService`（定义）+ provider 实现（local/remote/sandbox 可插拔）+ 工具作为 consumer。R45 已发现沙箱规则三份、shell 执行与文件写各管各的——seam 化正是根治法。**一个 seam 换 provider，全产品跟随**（如：沙箱从 bwrap 换成远端，Bash/PTY/文件同步一起换） | **P1** |
| **配置补丁层** | 配置加载器支持分层（内置 → 项目 → 用户 → `--patch` 覆盖，每行可溯源），替代"改代码加配置项"。go-on 已有热重载与 schema 版本，补"分层合并 + 来源追踪"即可 | P1 |
| **会话日志即事实源** | 强化现有审计/checkpoint：声明不变式"模型可见 ⇒ 日志可重建"，fork/resume/UI 都从会话日志派生（go-on 已有 conversation checkpoint/distillation 基础） | P2 |
| **agent 生命周期事件域** | 新增 `agent/pre-step`、`agent/request`、`tools/pre-execute` 类瀑布事件（在 StreamFrame 之上），让第三方插件观察/拦截/注入而不用改循环——go-on 的编排循环（OODA）是它相对 codex 的价值，事件域让它可扩展 | P2 |
| **工具可见性由注册决定** | 工具注册点 = 单一 schema 源（R45 F4 已修描述与实现不符），再进一步：注册时声明"模型可见/仅服务端"，schema 自动进 prompt 组装 | P2 |
| **技能即插件** | 技能从 SKILL.md 静态资产升级为"可注册能力包"（SKILL.md + 配置 + 工具 + 上下文片段），运行时注册/卸载（Rust 侧用 trait object registry，非动态代码） | P2 |
| **卸载即回滚（轻量版）** | 工具/技能注册返回 RAII guard（go-on 已有 SpawnGuard 先例），drop 即注销——实现"无残留扩展" | P3 |

**明确不要学的**：
1. 不要"运行时补丁任意改"（安全面）；Rust 用**配置分层 + 编译期类型 + 特性门控**实现可组合，保持 RBAC/审计在插件层之上；
2. 不要 `invariant.ts` 式运行时断言文化——go-on 用编译期类型 + 现有 1646 测试覆盖；
3. 不要"小功能也做 seam"的过度抽象（todo/plan 直接做工具即可）；
4. 不要 50 个 workspace 包——Rust 模块 + 已有 crates 拆分足够，避免维护面爆炸。

### 8.5 结论

- dsh 的"一切是插件"是**对 agent 产品不确定性的对冲**：模型能力、工具面、协议都在快速变化，运行时插件树让产品不用重编译就能重组——这是它相对 codex（重绑定 OpenAI）和 hermes（重绑定 Python 单进程）的架构优势。
- 代价是**动态性换来的复杂度**：样板、调试难、安全面、兼容性成本，且其优势场景（个人/研究工具）与 go-on（生产级编排+治理）不同。
- **go-on 的更改方向**：不做"一切是插件"，做**"能力缝系统化 + 配置补丁层 + 日志即事实源 + agent 事件域"**——用 Rust 的编译期保证拿到 dsh 的"可组合、可替换、可观测"收益，同时保住治理底座。其中 **seam 化（P1）** 是最大单点收益：它同时解决 R45 发现的沙箱规则分散、执行路径三份、供应商 Profile 化等既有问题。
