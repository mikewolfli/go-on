## 1. 🟡 性能瓶颈审查

### 1.1 Pipeline 与 Executor 治理检查重叠

**问题**: `pipeline.rs` 的 `check_tool_in_pipeline()` 与 `executor.rs` 的 `low_risk_audit_log()` 实现了 **相似的治理检查逻辑** 但走不同路径。

| 控制器 | 位置 | 检查方式 |
|---------|------|----------|
| `check_tool_in_pipeline` | `pipeline.rs` 第10行 → `governance_gate.rs` | 同步 `request_client_permission` |
| `is_low_risk_tool` + `low_risk_audit_log` | `executor.rs` 第16-18行 → `governance_gate.rs` | 低风险异步审计，高风险同步 |

**分析**:
- `executor.rs` 使用统一的 `governance_gate.rs` 已经去重
- `pipeline.rs` 导入的是 `check_tool_in_pipeline`（在 `governance_gate.rs` 中）
- 但 `pipeline.rs` 的 `parallel_groups` 功能和 `executor.rs` 的 `execute_tools_concurrent` 在并发执行层面重复
- `pipeline.rs` 的 `parallel_groups` 使用 `tokio::join!`（固定并行），而 `executor.rs` 使用 `Semaphore`（动态并发控制）

**建议**: `ToolPipeline.parallel_groups` 应委托给 `execute_tools_concurrent`，由 executor 统一处理并发执行和治理检查。

### 1.2 FastPathCache 未接入全局 `CacheMetricsCollector`

**文件**: `src/orchestration/fast_path_cache.rs`

**问题**: 虽然 `FastPathCache` 已经实现了 `CacheLayer` trait（第11轮完成），但 `src/main/mod.rs` 的启动代码中没有调用 `CacheMetricsCollector::register_cache()` 来注册 `FastPathCache`。

**影响**: `get_aggregate_cache_stats()` 不会包含 `FastPathCache` 的统计信息，治理端点的指标不完整。

**建议**: 在 `main/mod.rs` 启动流程中添加：
```rust
CacheMetricsCollector::global().register_cache(Arc::new(fast_path_cache.clone()));
```

### 1.3 ContinuousLearningCenter 固定 5 分钟轮询（仍存在）

**文件**: `src/main/mod.rs` 第294行
**代码**: `let mut interval = tokio::time::interval(Duration::from_secs(300));`

**分析**: 此发现来自第13轮日志，至今未修复。固定5分钟轮询浪费资源。低负载系统每5分钟醒来做空检查；高负载时期望更高频率。

**建议**: 改为自适应间隔：`Duration::from_secs(if has_recent_activity { 120 } else { 600 })`，或完全切换到事件驱动触发。

## 3. 🔵 工具/Skill 调用链完整审查

### 3.1 完整调用链重现

```
外部请求
  → main/mod.rs run()
    → CLI 解析 / 配置加载
      → bootstrap::perform_bootstrap()
        → 创建 SkillRegistry (discover + register)
          → set_skill_registry() 写入全局 SKILL_REGISTRY
        → 创建 ToolRegistryBuilder::new().with_all().build()
          → 注册 150+ 工具（含 feature-gated）
        → 创建 FlowManager + FlowModelSelector
        → 启动 Server
    → ACP transport 接收请求
      → GenericModeRuntime::run()
        → mode selector (orchestrator::select_mode_runtime_with_registry)
          → FullAutoFlow / BrainLoop / MultiAgentPipeline
            → tool call: execute_tools_concurrent() [executor.rs]
              → Semaphore 控制并发
              → governance_gate::is_low_risk_tool() → 跳过/审计
              → ToolRegistry::get() → tool.run()
                → governance_gate::check_tool_in_pipeline() (仅 pipeline)
              → 重试 (executor 内置)
              → 结果合并返回
            → skill call: SkillRegistry::get() → skill.execute()
              → 模糊匹配 + 执行
```

### 3.2 阻塞点分析

| 阻塞点 | 位置 | 影响 |
|--------|------|------|
| **Governance 双重路径** | executor + pipeline 各自调用 governance_gate | pipeline 的 governance 检查不走低风险优化路径 |
| **Skill 无热刷新** | `spawn_skill_refresh_task` 未在 bootstrap 中真正启动 | 技能变更需重启 |
| **ToolRegistry + SkillRegistry 无统一抽象** | `tool/mod.rs` + `skill/registry.rs` | FullAutoFlow 需要分别处理 |
| **FastPathCache 未注册到全局指标** | `main/mod.rs` 启动流程 | 治理端点指标缺失 |

### 3.3 治理缓存一致性

- `executor.rs` + `governance_gate.rs` 使用 `ShardedGovernanceCache`（16分片）✅
- `pipeline.rs` 调用 `check_tool_in_pipeline()` 但 **不使用** `ShardedGovernanceCache`
- **结果**: pipeline 每次执行都请求 ACP 权限，没有缓存命中

**建议**: 让 `check_tool_in_pipeline()` 使用 `ShardedGovernanceCache` 与 executor 共享缓存。
