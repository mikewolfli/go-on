# 高级编排

`go-on` 运行时包含一套高级编排模块，用于管理复杂的工作流执行、缓存、恢复和诊断。这些组件构成了 FullAutoFlow 系统的基础，支持多智能体任务分解、依赖感知调度和弹性故障处理。

---

## 1. DAG 执行引擎

DAG（有向无环图）执行引擎负责调度和执行具有显式依赖关系的任务。任务被组织为一个图，其中边表示数据或控制依赖关系。

### 拓扑执行

引擎在执行前计算 DAG 中所有节点的拓扑顺序。没有依赖关系的节点（根节点）首先被调度，只有当所有前驱节点成功完成后，节点才会被分发执行。

### 依赖管理

每个任务将其依赖关系声明为一组上游任务 ID。引擎验证：

- 所有引用的依赖项都存在于 DAG 中。
- 不存在循环依赖（参见下面的循环检测）。
- 依赖项所需的输出与下游任务的声明输入类型匹配。

### 并行组

处于同一拓扑级别的任务（即所有依赖项都已满足且彼此不依赖的任务）被分组为并行执行批次。引擎并发分发批次中的所有任务，受可配置的并发限制约束。

### 循环检测

在开始执行之前，引擎使用深度优先搜索（DFS）和递归栈进行完整的循环检测。如果检测到循环，整个 DAG 执行将被中止，并给出一个明确标识冲突边的错误。

## 2. FullAutoFlow

FullAutoFlow 是一个完全自主的五阶段流水线，接收高级用户目标并在最少人工干预下生成完成结果。

### 五阶段流水线

| 阶段       | 描述 |
|-------------|-------------|
| **解析 (Parse)**       | 解析传入的用户请求，提取意图、约束条件和成功标准。自然语言被转换为结构化目标规范。 |
| **发现 (Discover)**    | 系统从可用注册表中发现相关技能、工具和上下文。技能按与解析目标的关联度排序。 |
| **准备 (Prepare)**     | 生成任务计划，解析依赖关系，构建执行 DAG。收集并验证所需的输入。 |
| **执行 (Execute)**     | DAG 执行引擎运行计划，将任务分派给相应的技能处理器。监控进度并收集中间结果。 |
| **报告 (Report)**      | 将所有任务的结果合并为最终报告。报告包括输出、指标、警告和所做决策的摘要。 |

### 技能感知任务分解

在**准备**阶段，FullAutoFlow 使用可用的技能注册表将高级目标分解为子任务。每个子任务都匹配到可以执行它的技能。分解策略考虑：

- **技能基数**：技能处理一个任务还是多个任务。
- **输入/输出兼容性**：一个技能的输出是否可以输入到另一个技能。
- **执行约束**：技能声明的超时、内存或提供者要求。

结果是一个 DAG，其中每个节点都标注了其分配的技能、输入绑定和期望的输出模式。

## 3. FastPathCache

FastPathCache 提供了一个高性能、多层级缓存层，可减少冗余计算并加速重复请求。

### SHA-256 指纹

每个缓存条目使用从请求的规范表示计算的 SHA-256 指纹作为键。指纹包括：

- 规范化后的原始输入文本。
- 活动的技能和模型标识符。
- 相关的环境变量和提供者配置。
- 路由模板参数。

### TTL / LRU 淘汰

缓存支持两种互补的淘汰策略：

- **TTL（生存时间）**：每个条目在可配置的持续时间后过期（默认：5 分钟）。过期条目在访问时惰性淘汰，并由后台扫描主动淘汰。
- **LRU（最近最少使用）**：当缓存达到容量限制时（默认：10,000 个条目），最近最少访问的条目首先被淘汰。

这些策略是组合使用的：如果条目已过期 OR 在容量超过限制时是 LRU 受害者，则该条目被删除。

### 四层缓存模型

| 层级 | 范围     | 键                                       | TTL     |
|------|-----------|------------------------------------------|---------|
| L1   | 意图 (Intent)     | 用户意图指纹                             | 30 秒   |
| L2   | 技能 (Skill)      | 技能 + 输入指纹                          | 5 分钟  |
| L3   | 环境 (Env)        | 环境 + 配置指纹                          | 10 分钟 |
| L4   | 路由 (Route)      | 路由模板 + 参数指纹                      | 1 分钟  |

按顺序检查层级（L1 → L2 → L3 → L4）。较早层级的命中会短路查找并提供更快的响应时间。

### RouteTemplate 匹配

路由级缓存（L4）使用 `RouteTemplate` 模式匹配来处理参数化路由。诸如 `/skills/{skill_id}/execute` 之类的路由模板与具有具体参数的传入请求匹配。缓存存储以匹配的模板及其参数哈希为键的结果，从而在不同参数值产生相同结果时实现重用。

## 4. 工具事务系统

工具事务系统为工具执行提供事务保证，确保即使在出现故障时副作用也保持一致。

### 幂等性

每个工具调用都包含一个从 DAG 节点 ID、重试次数和会话随机数派生的幂等性键。系统记录已完成的调用，并使用相同的幂等性键拒绝重复请求，返回先前计算的结果。

### 预写日志 (WAL)

在应用任何工具变更之前，都会持久化一条 WAL 条目。该记录记录：

- 工具标识和参数。
- 预期的状态转换（前镜像和后镜像）。
- 幂等性键。
- 事务状态（待定 / 已提交 / 已中止）。

如果进程在事务中间崩溃，则会在启动时重放 WAL 以提交或回滚正在进行的操作。

### 补偿操作

每个工具可以声明一个补偿操作——一个撤销工具效果的逆操作。当事务在某些工具已成功执行后失败时，系统以相反的顺序运行补偿操作以恢复一致的状态。

### TwoPhaseCoordinator (2PC)

`TwoPhaseCoordinator` 实现了分布式两阶段提交协议，用于跨多个工具或提供者的事务：

1. **准备阶段**：协调器向所有参与者发送准备请求。每个参与者验证是否可以提交并锁定必要的资源，然后回复投票（是 / 否 / 只读）。
2. **提交阶段**：如果所有参与者都投票同意，协调器发送提交请求。如果有任何参与者投票反对，协调器向所有参与者发送中止请求。

协调器维护一个事务日志，可以通过查询持久化状态从故障中恢复。

## 5. 恢复编排器

恢复编排器负责处理任务失败，并根据失败上下文、任务元数据和历史结果确定最佳恢复操作。

### 六种恢复策略

| 策略       | 描述 |
|-------------|-------------|
| **重试 (Retry)**       | 重新执行失败的任务，可选地带有退避延迟和递增的重试计数器。适用于瞬态故障（网络超时、速率限制）。 |
| **重新路由 (Reroute)** | 将任务路由到替代提供者或技能处理器。当主要提供者返回提供者级别错误时使用。 |
| **重新规划 (Replan)**  | 重新运行准备阶段以生成避免失败任务的新计划。当失败表明规划错误时使用。 |
| **修复 (Repair)**      | 应用目标修复（例如，修补格式错误的输入、修复模式不匹配）并重试。修复操作来自诊断反馈引擎。 |
| **升级 (Escalate)**    | 将失败的任务交给人类操作员或更高权限的代理。升级包括完整的失败上下文和诊断摘要。 |
| **降级 (Degrade)**     | 放弃失败的任务，以降级的功能继续执行。最终报告会记录降级及其影响。 |

### 策略树

策略被组织成一个决策树，编排器根据失败特征遍历该决策树。每个策略节点将其结果（成功/失败）记录在任务的执行历史中。如果某个策略失败，编排器会回退到树中的下一个适用策略。

## 6. 会话上下文管理器

会话上下文管理器在多轮交互中维护和优化对话上下文，确保在有限的窗口预算内保留最相关的信息。

### 概念提取

每条用户消息都会被分析以提取关键概念——实体、意图和领域特定术语。提取的概念存储在与会话关联的轻量级内存索引中。

概念如果不被后续消息强化，则会随时间衰减。权重低于可配置阈值的概念会被从会话中修剪。

### 消息重要性评分

会话历史中的每条消息在多个维度上评分：

- **时效性**：较新的消息获得较高的分数。
- **相关性**：包含当前查询中出现过的概念的消息得分更高。
- **角色**：系统消息和明确的用户指令比随意对话得分更高。
- **可操作性**：触发了工具调用或产生了可观察副作用的消息得分更高。

### 连续性标记

连续性标记是注入到上下文窗口中的特殊注释，用于指示叙述的进展。它们通过总结已完成的工作和剩余的工作帮助模型在轮次之间保持连贯性。标记在关键里程碑处自动生成：

- FullAutoFlow 的某个阶段完成后。
- 工具事务提交后。
- 恢复操作解决故障后。

### 窗口预算

上下文窗口是有限的。会话上下文管理器通过以下方式强制执行预算：

1. 始终保留最近的 `n` 条消息（可配置，默认：5）。
2. 用得分最高的较旧消息填充剩余预算。
3. 当预算超限时，剥离低重要性的消息。
4. 必要时通过总结来压缩长消息。

## 7. 复杂度评估器

复杂度评估器分析传入任务以预测其计算和结构复杂度，使系统能够分配适当的资源并动态配置 BrainLoop 迭代次数。

### 四信号分析

评估器评估四个独立信号：

| 信号           | 描述 |
|-----------------|-------------|
| **词汇 (Lexical)**      | 令牌数量、词汇多样性和结构标记（例如代码块、项目符号列表）。更长、更多样化的输入表示更高的复杂度。 |
| **语义 (Semantic)**     | 从输入中提取的不同概念数量。更多的概念意味着更广泛的范围和更高的复杂度。 |
| **依赖 (Dependency)**   | 从输入中推断出的隐式任务依赖关系的数量（例如"先做 X，然后做 Y"）。更多的依赖关系表示多步骤工作流。 |
| **历史 (Historical)**   | 类似过去请求的平均完成时间和失败率。更高的方差与不确定性和复杂度相关。 |

每个信号产生一个归一化分数（0.0 – 1.0）。最终复杂度分数是加权组合。

### 动态 BrainLoop 迭代大小

BrainLoop 迭代次数——系统在生成答案前执行的推理次数——基于复杂度分数进行缩放。映射关系可按技能配置，并可由传入请求的 `complexity_hint` 字段覆盖。

## 8. 诊断反馈引擎

诊断反馈引擎（DFE）提供编译器错误、运行时异常和测试失败的自动分析。它解析错误输出，匹配已知模式，并推荐目标修复策略。

### 编译器错误解析

DFE 包含常见编译器和解释器输出的解析器：

- **Rust**（`rustc`）：提取错误代码（例如 `E0308`）、定位位置和类型不匹配的详细信息。
- **TypeScript / JavaScript**（`tsc`、`node`）：提取堆栈跟踪、语法错误位置和类型错误。
- **Python**：提取回溯条目、异常类型和行号。
- **通用**：对于未处理的格式，回退到行列提取和消息去重。

### 模式匹配

解析后的诊断与已知错误模式库进行匹配。每个模式包括：

- 针对诊断字段的正则表达式或结构匹配器。
- 严重性分类（信息 / 警告 / 错误 / 严重）。
- 零个或多个候选修复策略。

模式从技能注册表加载，并可由自定义技能扩展。匹配引擎使用基于 trie 的数据结构实现高效的查找。

### 修复策略推荐

根据匹配的模式，DFE 推荐一个或多个修复策略：

| 策略             | 描述 |
|------------------|-------------|
| **类型修复**         | 建议类型标注更改或类型转换。 |
| **导入修复**       | 建议添加缺失的导入或更正模块路径。 |
| **语法修复**       | 建议语法修正（例如缺少分号、括号不匹配）。 |
| **签名修复**    | 建议将函数或方法签名与其调用点对齐。 |
| **生命周期修复**     | 针对 Rust 借用检查器错误建议生命周期标注调整。 |
| **自定义策略**  | 由技能或用户编写的补丁模板定义的策略。 |

每条建议包括：

- 错误的人类可读解释。
- 建议的具体代码更改（作为差异或编辑操作）。
- 基于模式匹配特异性和历史修复成功率的置信度分数（0.0 – 1.0）。

DFE 与恢复编排器集成：当工具执行因诊断输出失败时，恢复编排器会调用 DFE 以确定**修复**策略是否合适，然后再回退到升级或降级策略。
