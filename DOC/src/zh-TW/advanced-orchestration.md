# 高級編排

`go-on` 運行時包含一套高級編排模組，用於管理複雜的工作流執行、快取、恢復和診斷。這些元件構成了 FullAutoFlow 系統的基礎，支援多智能體任務分解、依賴感知排程和彈性故障處理。

---

## 1. DAG 執行引擎

DAG（有向無環圖）執行引擎負責排程和執行具有明確依賴關係的任務。任務被組織為一個圖，其中邊表示資料或控制依賴關係。

### 拓撲執行

引擎在執行前計算 DAG 中所有節點的拓撲順序。沒有依賴關係的節點（根節點）首先被排程，只有當所有前驅節點成功完成後，節點才會被分發執行。

### 依賴管理

每個任務將其依賴關係宣告為一組上游任務 ID。引擎驗證：

- 所有引用的依賴項都存在於 DAG 中。
- 不存在循環依賴（請參閱下面的循環檢測）。
- 依賴項所需的輸出與下游任務的宣告輸入類型匹配。

### 並行組

處於同一拓撲級別的任務（即所有依賴項都已滿足且彼此不依賴的任務）被分組為並行執行批次。引擎並發分發批次中的所有任務，受可配置的並發限制約束。

### 循環檢測

在開始執行之前，引擎使用深度優先搜索（DFS）和遞迴堆疊進行完整的循環檢測。如果檢測到循環，整個 DAG 執行將被中止，並給出一個明確識別衝突邊的錯誤。

## 2. FullAutoFlow

FullAutoFlow 是一個完全自主的五階段管線，接收高階使用者目標並在最少人工干預下生成完成結果。

### 五階段管線

| 階段       | 描述 |
|-------------|-------------|
| **解析 (Parse)**       | 解析傳入的使用者請求，提取意圖、約束條件和成功標準。自然語言被轉換為結構化目標規範。 |
| **發現 (Discover)**    | 系統從可用註冊表中發現相關技能、工具和上下文。技能按與解析目標的關聯度排序。 |
| **準備 (Prepare)**     | 生成任務計劃，解析依賴關係，構建執行 DAG。收集並驗證所需的輸入。 |
| **執行 (Execute)**     | DAG 執行引擎運行計劃，將任務分派給相應的技能處理器。監控進度並收集中間結果。 |
| **報告 (Report)**      | 將所有任務的結果合併為最終報告。報告包括輸出、指標、警告和所做決策的摘要。 |

### 技能感知任務分解

在**準備**階段，FullAutoFlow 使用可用的技能註冊表將高階目標分解為子任務。每個子任務都匹配到可以執行它的技能。分解策略考慮：

- **技能基數**：技能處理一個任務還是多個任務。
- **輸入/輸出相容性**：一個技能的輸出是否可以輸入到另一個技能。
- **執行約束**：技能宣告的超時、記憶體或提供者要求。

結果是一個 DAG，其中每個節點都標註了其分配的技能、輸入綁定和期望的輸出模式。

## 3. FastPathCache

FastPathCache 提供了一個高效能、多層級快取層，可減少冗餘計算並加速重複請求。

### SHA-256 指紋

每個快取條目使用從請求的規範表示計算的 SHA-256 指紋作為鍵。指紋包括：

- 規範化後的原始輸入文字。
- 活動的技能和模型識別碼。
- 相關的環境變數和提供者配置。
- 路由模板參數。

### TTL / LRU 淘汰

快取支援兩種互補的淘汰策略：

- **TTL（生存時間）**：每個條目在可配置的持續時間後過期（預設：5 分鐘）。過期條目在訪問時惰性淘汰，並由後台掃描主動淘汰。
- **LRU（最近最少使用）**：當快取達到容量限制時（預設：10,000 個條目），最近最少訪問的條目首先被淘汰。

這些策略是組合使用的：如果條目已過期 OR 在容量超過限制時是 LRU 受害者，則該條目被刪除。

### 四層快取模型

| 層級 | 範圍     | 鍵                                       | TTL     |
|------|-----------|------------------------------------------|---------|
| L1   | 意圖 (Intent)     | 使用者意圖指紋                           | 30 秒   |
| L2   | 技能 (Skill)      | 技能 + 輸入指紋                          | 5 分鐘  |
| L3   | 環境 (Env)        | 環境 + 配置指紋                          | 10 分鐘 |
| L4   | 路由 (Route)      | 路由模板 + 參數指紋                      | 1 分鐘  |

按順序檢查層級（L1 → L2 → L3 → L4）。較早層級的命中會短路查找並提供更快的響應時間。

### RouteTemplate 匹配

路由級快取（L4）使用 `RouteTemplate` 模式匹配來處理參數化路由。諸如 `/skills/{skill_id}/execute` 之類的路由模板與具有具體參數的傳入請求匹配。快取儲存以匹配的模板及其參數雜湊為鍵的結果，從而在不同參數值產生相同結果時實現重用。

## 4. 工具事務系統

工具事務系統為工具執行提供事務保證，確保即使在出現故障時副作用也保持一致。

### 冪等性

每個工具呼叫都包含一個從 DAG 節點 ID、重試次數和會話隨機數派生的冪等性鍵。系統記錄已完成的呼叫，並使用相同的冪等性鍵拒絕重複請求，返回先前計算的結果。

### 預寫日誌 (WAL)

在應用任何工具變更之前，都會持久化一條 WAL 條目。該記錄記錄：

- 工具識別和參數。
- 預期的狀態轉換（前鏡像和後鏡像）。
- 冪等性鍵。
- 事務狀態（待定 / 已提交 / 已中止）。

如果程序在事務中間崩潰，則會在啟動時重放 WAL 以提交或回滾正在進行的操作。

### 補償操作

每個工具可以宣告一個補償操作——一個撤銷工具效果的逆操作。當事務在某些工具已成功執行後失敗時，系統以相反的順序運行補償操作以恢復一致的狀態。

### TwoPhaseCoordinator (2PC)

`TwoPhaseCoordinator` 實現了分散式兩階段提交協議，用於跨多個工具或提供者的事務：

1. **準備階段**：協調器向所有參與者發送準備請求。每個參與者驗證是否可以提交並鎖定必要的資源，然後回覆投票（是 / 否 / 唯讀）。
2. **提交階段**：如果所有參與者都投票同意，協調器發送提交請求。如果有任何參與者投票反對，協調器向所有參與者發送中止請求。

協調器維護一個事務日誌，可以通過查詢持久化狀態從故障中恢復。

## 5. 恢復編排器

恢復編排器負責處理任務失敗，並根據失敗上下文、任務元資料和歷史結果確定最佳恢復操作。

### 六種恢復策略

| 策略       | 描述 |
|-------------|-------------|
| **重試 (Retry)**       | 重新執行失敗的任務，可選地帶有退避延遲和遞增的重試計數器。適用於瞬態故障（網路逾時、速率限制）。 |
| **重新路由 (Reroute)** | 將任務路由到替代提供者或技能處理器。當主要提供者返回提供者級別錯誤時使用。 |
| **重新規劃 (Replan)**  | 重新運行準備階段以生成避免失敗任務的新計劃。當失敗表明規劃錯誤時使用。 |
| **修復 (Repair)**      | 應用目標修復（例如，修補格式錯誤的輸入、修復模式不匹配）並重試。修復操作來自診斷反饋引擎。 |
| **升級 (Escalate)**    | 將失敗的任務交給人類操作員或更高權限的代理。升級包括完整的失敗上下文和診斷摘要。 |
| **降級 (Degrade)**     | 放棄失敗的任務，以降級的功能繼續執行。最終報告會記錄降級及其影響。 |

### 策略樹

策略被組織成一個決策樹，編排器根據失敗特徵遍歷該決策樹。每個策略節點將其結果（成功/失敗）記錄在任務的執行歷史中。如果某個策略失敗，編排器會回退到樹中的下一個適用策略。

## 6. 會話上下文管理器

會話上下文管理器在多輪互動中維護和優化對話上下文，確保在有限的視窗預算內保留最相關的資訊。

### 概念提取

每條使用者訊息都會被分析以提取關鍵概念——實體、意圖和領域特定術語。提取的概念儲存在與會話關聯的輕量級記憶體索引中。

概念如果不被後續訊息強化，則會隨時間衰減。權重低於可配置閾值的概念會被從會話中修剪。

### 訊息重要性評分

會話歷史中的每條訊息在多個維度上評分：

- **時效性**：較新的訊息獲得較高的分數。
- **相關性**：包含目前查詢中出現過的概念的訊息得分更高。
- **角色**：系統訊息和明確的使用者指令比隨意對話得分更高。
- **可操作性**：觸發了工具呼叫或產生了可觀察副作用的訊息得分更高。

### 連續性標記

連續性標記是注入到上下文視窗中的特殊註釋，用於指示敘述的進展。它們通過總結已完成的工作和剩餘的工作幫助模型在輪次之間保持連貫性。標記在關鍵里程碑處自動生成：

- FullAutoFlow 的某個階段完成後。
- 工具事務提交後。
- 恢復操作解決故障後。

### 視窗預算

上下文視窗是有限的。會話上下文管理器通過以下方式強制執行預算：

1. 始終保留最近的 `n` 條訊息（可配置，預設：5）。
2. 用得分最高的較舊訊息填充剩餘預算。
3. 當預算超限時，剝離低重要性的訊息。
4. 必要時通過總結來壓縮長訊息。

## 7. 複雜度評估器

複雜度評估器分析傳入任務以預測其計算和結構複雜度，使系統能夠分配適當的資源並動態設定 BrainLoop 迭代次數。

### 四訊號分析

評估器評估四個獨立訊號：

| 訊號           | 描述 |
|-----------------|-------------|
| **詞彙 (Lexical)**      | 令牌數量、詞彙多樣性和結構標記（例如程式碼區塊、項目符號列表）。更長、更多樣化的輸入表示更高的複雜度。 |
| **語義 (Semantic)**     | 從輸入中提取的不同概念數量。更多的概念意味著更廣泛的範圍和更高的複雜度。 |
| **依賴 (Dependency)**   | 從輸入中推斷出的隱式任務依賴關係的數量（例如"先做 X，然後做 Y"）。更多的依賴關係表示多步驟工作流。 |
| **歷史 (Historical)**   | 類似過去請求的平均完成時間和失敗率。更高的方差與不確定性和複雜度相關。 |

每個訊號產生一個歸一化分數（0.0 – 1.0）。最終複雜度分數是加權組合。

### 動態 BrainLoop 迭代大小

BrainLoop 迭代次數——系統在生成答案前執行的推理次數——基於複雜度分數進行縮放。映射關係可按技能設定，並可由傳入請求的 `complexity_hint` 欄位覆蓋。

## 8. 診斷反饋引擎

診斷反饋引擎（DFE）提供編譯器錯誤、執行時期異常和測試失敗的自動分析。它解析錯誤輸出，匹配已知模式，並推薦目標修復策略。

### 編譯器錯誤解析

DFE 包含常見編譯器和直譯器輸出的解析器：

- **Rust**（`rustc`）：提取錯誤碼（例如 `E0308`）、定位位置和類型不匹配的詳細資訊。
- **TypeScript / JavaScript**（`tsc`、`node`）：提取堆疊追蹤、語法錯誤位置和類型錯誤。
- **Python**：提取回溯條目、例外類型和行號。
- **通用**：對於未處理的格式，回退到行列提取和訊息去重。

### 模式匹配

解析後的診斷與已知錯誤模式庫進行匹配。每個模式包括：

- 針對診斷欄位的正規表示式或結構匹配器。
- 嚴重性分類（資訊 / 警告 / 錯誤 / 嚴重）。
- 零個或多個候選修復策略。

模式從技能註冊表載入，並可由自訂技能擴充。匹配引擎使用基於 trie 的資料結構實現高效的查找。

### 修復策略推薦

根據匹配的模式，DFE 推薦一個或多個修復策略：

| 策略             | 描述 |
|------------------|-------------|
| **類型修復**         | 建議類型標註更改或類型轉換。 |
| **導入修復**       | 建議添加缺失的導入或更正模組路徑。 |
| **語法修復**       | 建議語法修正（例如缺少分號、括號不匹配）。 |
| **簽名修復**    | 建議將函數或方法簽名與其呼叫點對齊。 |
| **生命週期修復**     | 針對 Rust 借用檢查器錯誤建議生命週期標註調整。 |
| **自訂策略**  | 由技能或使用者編寫的修補程式模板定義的策略。 |

每條建議包括：

- 錯誤的人類可讀解釋。
- 建議的具體程式碼更改（作為差異或編輯操作）。
- 基於模式匹配特異性和歷史修復成功率的置信度分數（0.0 – 1.0）。

DFE 與恢復編排器整合：當工具執行因診斷輸出失敗時，恢復編排器會呼叫 DFE 以確定**修復**策略是否合適，然後再回退到升級或降級策略。
